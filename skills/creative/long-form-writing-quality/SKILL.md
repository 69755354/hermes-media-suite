# 长篇写作质量改进方案（2026-08-13 Codex+Claude 定稿）

## When to Use

触发：写长篇/小说质量差/客户反馈错误多/相同错误反复出现/语法错误越来越多/考虑降字数/担心跨章上下文脱节/要建错例门禁。写任何 5 万字以上、跨多章、需长期维护的文本（小说/传记/回忆录）前先过本流程。

> 来源：三层衣长篇项目（106119 字/20 章），Codex 与 Claude 互评收敛至 92% 一致率定稿。客户原话：「长篇错误太多了，每次相同问题提示后仍出现，语法错误越来越多」。

## 核心原则

1. **重心从「更多标准」移到「更小单元 + 独立审校 + 错例对照表 + 反馈计数」**
2. **字数不是连续性的载体，写下来的交接信息才是**——跨章上下文靠交接件，不靠上下文长度
3. **没有独立检查者 = 最大结构性漏洞**——写作/审校/签PASS 不能同一执行者
4. **先救资产再谈质量**——无版本控制的长篇资产，第 0 步必须做
5. **可度量**——主指标=客户确认修改数/千字（归一化），不靠 PASS/BLOCKED 自述

## 第 0 步：先救资产，建立可回滚基线（最高优先）

1. 项目从临时目录复制到耐久目录（如 `/home/ubuntu/workflow/projects/<项目名>`）；暂不删原目录
2. 源目录和耐久副本做文件数/总字节/逐文件 SHA-256 校验
3. 耐久副本 `git init`，全部文件原样提交为 `raw-import` 基线（先于任何改名/归档）
4. 建 `ACTIVE_MANIFEST.yaml`：活跃章节列表/唯一权威文件/冲突优先级
5. 所有脚本只从活跃清单取文件，禁止 `第*章_*.md` glob 全量扫描
6. 旧版移入 `_archive/`（不删除），提交 `manifest-and-archive`

验收：副本 20 章/总字符数一致/哈希一致/git 可检出/旧版不再进扫描。

## 第 1 步：统一内容事实源

- 姓名/称谓/地名/时间线定唯一权威（历史映射写「原称X，现统一为Y」，禁机械替换成自指）
- 冲突裁定先于登记（如「通知书 ch20 已用 or 留 ch55」需作者拍板）
- 权威优先级：客户最新确认 > 主数据 > 章节卡 > 大纲 > 旧素材

## 第 2 步：错例回归表（17条原则 → 可执行门禁）

字段固定：`case_id｜类别｜错误原句｜正确改句｜判定理由｜严重级别｜来源｜机器可检/人工检`

- 只有客户真实指出或校对确认的错误才能进表，不凑数
- **没有正例/反例/预期结果的规则，不得晋升硬门禁**（先软告警或人工审校）
- 门禁初期真实拦截力接近零是正常的，靠回归表逐步长出来
- 每次客户新增意见：先归类 → 去重 → 加入回归集

## 第 3 步：小型确定性门禁（重写脚本）

硬阻断并非零退出（只限机器能明确判断的）：
- 废弃别名/违反人物主数据
- 客户明确禁用词/已确认错误短语
- 重复标点/编码异常/空文件/正文疑似截断/精确重复句

只报警告（不阻断）：
- AA 型叠词（奶奶/慢慢/一点点——正常叠词误报，删掉）
- 长句比例（降为风格观察项，非硬指标）
- 跨词边界语义重复（正则判不了，只报警）

陷阱：`check_grammar.py` 曾对任意相邻同字报警（20 章 289 项误报），且返回退出码 0 不阻断。

## 第 4 步：生成单元缩小 + 跨章连续性

- 生成单元降到 **2000-2500 字**（或按场景边界切分，不取字数刻度）
- **交接卡**：每章结束写本章末尾状态/时间点/人物位置/待续动作；下一章开写前必须读；缺字段不许开写（物理卡点）
- **章节年龄与身份表**：人物年龄/身份随时间推进（显式年龄标记归机器，行为年龄归人）
- **伏笔台账**：登记每章埋的线（**只登记未回收的**，控成本）；第 N 章要收线时查得到
- 用 1-20 章倒建台账（先登记已存在的伏笔）

## 第 5 步：独立审校

- **新会话/新上下文**审校，只给正文 + 错例对照表，**不给创作意图和控制卡**
- 输出格式：`位置 | 原句 | 问题 | 建议`；写作者只负责改
- 审校者不知道你想表达什么，才可能发现指代不清和主体漂移
- 更独立：换模型审（写用 codex，审用 Claude/DS）

## 第 6 步：整章回归 + 度量

- 分段写作后**必须整章回归**（可暂缓 60 项人工清单和全书通读，不能暂缓整章回归）：
  - 段间重复/时间跳变/衔接断裂检查
  - 逐接缝比对交接卡
  - 时间线挂年龄表
  - 伏笔台账检查
- 唯一验收指标：客户确认修改数/千字 + 历史错误复发数
- **记三章数据再定参数**（2000 字是否合适/门禁阈值）——不凭感觉加规则
- 连续三章数据对比，决定生成单元保留/缩小/放大

## 行动顺序（定稿）

1. 耐久迁移 + git 基线（第 0 步）
2. 活跃清单/归档
3. 姓名与冲突双裁定（需作者拍板的标注「待确认」）
4. 错例回归表（从校对报告倒出，不新写）
5. 修脚本（删 AA 叠词/补非零退出）
6. 伏笔台账（只登记未回收）
7. 场景试行 + 交接卡 + 独立审校
8. 整章回归（逐接缝比对）
9. 三章数据 → 首版参数

## 踩坑（实测）

- **客户「错误越来越多」根因未量化**：规则膨胀/上下文下降/单次生成过长/主数据冲突/自审，都是候选——先建错误基线再排序，别写成因果
- **「2000-2500 字最有效」未验证**：是三章试行对象，不是定论
- **通知书类冲突**：结构表里两处可能自相矛盾（一处禁一处准）——先裁定再登记，别把未定事实写进主数据
- **/tmp 30 天清理**：客户资产绝不能只放 /tmp，git 也要跟项目一起在耐久目录
- **glob 扫到废弃版**：唯一正文禁词命中旧版（_明黄色）——活跃清单是唯一防线
- **正文零改动**：姓名统一可能只需改规则/素材文件（16 个），正文 20 章零改动——先核准范围
