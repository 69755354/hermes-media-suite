# 工作流优先纪律（Workflow-First Discipline）

## 核心原则

收到**任何**任务，第一动作是「定位管辖这个任务类的工作流 / skill / 框架文档」，不是直接动手。

```
先问：这个任务属于哪个节点/轨？哪个 skill/文档已经写了做法？
再动：加载 → 按节点/流程走 → 过出口闸 → 交付
禁止：既有标准存在时自创框架（重复造轮子 = 用户最恨）
```

## 接「XX 的工作流/流程」任务：先确认是哪个系统的工作流（2026-08-21 血泪，连续四次纠正）

用户说「把 X 的工作流流程做出来」时，**「工作流」指哪个系统必须先定位，不要默认脑补**。同一句话在不同上下文指完全不同的东西：

| 用户原话 | 实际指 | 我画错了什么 |
|:--|:--|:--|
| 「广州机的工作流流程」 | ai-video-factory 客户短视频生产端到端流程（12 步） | 第一版画了对一半，但用户要的是更具体的 |
| 「node 0 to node 1」 | WORKFLOW_REGISTRY 语义节点 0→1（PROJECT_CHARTER→BUSINESS_DIAGNOSIS） | 画成全流程，画窄了 |
| 「火山工作流，从节点零到最后」 | 以为是扣子 Coze 7 节点概念图 | 画了扣子图，用户说缺打法分析/平台策略/自动发布/数据分析 |
| 最后澄清 | **19 节点语义主链**（GROWTH_STRATEGY=打法分析、PUBLISH_OPERATE=自动发布、WEEKLY_REVIEW/MONTHLY_CLOSE=数据分析） | 才画对 |
| 「是小鹿的最新工作流」 | 广州机 customer profile SOUL.md 做视频流程 v2（①搜信息→②画像→③平台→④打法→⑤爆款→⑥选题→⑦文案→node4确认→权限配额→三通道出片→node12确认→交付→复盘） | 火山工作流也不对，小鹿才是目标 |

**纪律**：接「XX 工作流/流程」任务，第一动作是问清或查清「哪个系统的工作流」：
- ai-video-factory（广州 8090 网页平台）≠ WORKFLOW_REGISTRY 语义节点 ≠ 火山/扣子工作流 ≠ 小鹿 SOUL 工作流程
- 每个系统有自己的注册表/文档：`WORKFLOW_REGISTRY.yaml`（语义节点）、小鹿 `profiles/customer/SOUL.md`（做视频流程 v2）、`coze-workflow-diagram.html`（扣子概念图）
- 用户点名的节点名（打法分析/自动发布/数据分析）是定位线索——对照注册表找，不脑补

## 跨平台简短指令：先定位该对话的业务线，再找上下文（2026-08-21 血泪：串台把飞书的活拿到微信干）

用户在某个 IM（微信/飞书）发一句**无上下文的简短指令**（如「改」）时，第一动作是判断**这个渠道负责哪条业务线**，再决定从哪找上下文。**禁止拿 session_search 最近会话（可能是另一个平台的）当当前任务**——session_search 是回忆工具，不是任务定位工具。

| 用户原话 | 我错在哪 |
|:--|:--|
| 「改」（微信） | session_search 拉到飞书端头条产线会话（朱雀/云南/加粗），以为用户要改头条加粗，查了半天根因 |
| 「你发错地方了，这个东西是飞书机器人在搞」 | 头条产线 = 飞书机器人的活，不该在微信端处理 |
| 「你要搞得是教课这个事」 | 微信端业务线 = AI 教课（ai-teacher-bot），不是头条 |

**已知渠道归属（截至 2026-08-21）**：飞书 = 头条产线/客户业务（toutiao-shoufa-tools 朱雀/云南/加粗修复）；微信 = AI 教课线（ai-teacher-bot：课次包 14 个/课程介绍/招生广告/教案已完成，待 SOUL 改装+测试群+预算账户）+ 其他业务。归属可能随用户调度变化，拿不准就问，别猜。

**纪律**：
1. 简短指令无上下文 → 先按「本渠道负责的业务线」确认要改哪个交付物，再动手
2. 定位靠渠道归属 + 真实项目目录（`workflow/projects/<项目>/`），不靠跨平台最近会话
3. 跨平台拿上下文前先自问：这个任务属于当前对话所在的机器/渠道吗？
4. 指代不明的名词（「那个东西」「这个」「它」）**连猜两次不中 → 立即用 clarify 给候选选项**，别继续搜索硬猜（2026-08-21：「自动发布」先猜成教学模式的课堂展示，用户纠正「我是说自动发布那个东西」两次；clarify 一选即中 = 工作流节点13自动发布环节的 NewMe 适配）。猜两次是上限，第三次必须换交互方式

## 标准流程（任何任务，含分析/写作/技术/归因/指挥）

1. **定位**：读 `HERMES_NODE_MAP.yaml` / `WORKFLOW_REGISTRY.yaml` / 相关 skill（huoshan、video-content-extraction 等），确认任务归属哪个轨/节点
2. **查框架**：确认该节点现有框架文档存在（例：拆解 → `huoshan/references/video-deconstruction-framework.md`；AI 视频逆向 → 该文档第八章）
3. **加载**：加载对应 persona/规则 → 按节点顺序走 → 过出口闸（workflow_gate.py / ticket）
4. **交付**：查交付规则再发（飞书视频可直接 MEDIA 发，见下）

## 关键误区

- ❌ 「这个任务是新的，没有现成做法」→ 先查再下结论（拆解视频就是既有节点2的子类，不是新任务）
- ❌ 「我有方法论（3点法/五智囊），够了」→ 方法论是内容工具，不是流程替代品
- ❌ 遇到问题才回头查规则 → 应该先查再动手，规则查询是前置步骤不是拖延
- ❌ 用户夸了新做法就确信它对 → 正反馈会强化自创，更要回头查有没有现成标准

## 打包任务书前必读规则（2026-08-18 血泪：谁打包谁先读）

**派 codex/claude/DS 写内容/分析/方案前，打包方（Hermes）必须先读管辖该任务类的 skill——执行器照任务书执行，任务书错了执行器不会纠错。**

| 用户原话 | 我错在哪 |
|:--|:--|
| 「知道什么叫复刻吗？」 | 打包复刻任务书时没读 video-remake skill（白纸黑字写着「复刻=完全照抄原片」），把复刻做成按剧情切镜改编 |
| 「意思就是你根本没去读给你的规则是不是」 | 规则全在 skill 里，我没读就凭印象打包 |
| 「你镜2的提示词不是按照红果的那一套来的吧」 | 没读 seedance-voice-params 红果三要素（台词英文双引号嵌入/开场停顿/负面词），DS 生成的分镜 prompt 全缺 |

**纪律**：
1. 打包任务书 = 写「怎么做」的说明书。**先读管辖 skill（video-remake / seedance-2-0-mini-workflow / huoshan / content-redlines...），把关键约束写进任务书**，执行器才不会自由发挥
2. 任务书里写条件规则（如「若超15s才拆」）时，先验证条件是否真实存在——永不触发的条件写进去 = 埋雷（DS 会把「14s拆2段」当默认动作执行）
3. 物理兜底已落地：`task_brief_gate.py` 主对话打包卡点（见 agent-framework-layer），但**先读 skill 再打包**仍是第一道防线，卡点是第二道

## 项目目录检查（2026-08-18 血泪：接任务先查真实项目，别在临时目录重复劳动）

**收到客户任务（复刻/文案/分析/出片）第一动作之二：查真实项目目录，不凭记忆/临时目录碎片拼凑。**

```bash
# 真实项目在 workflow/projects/<项目>/（如 huolong-guide），不是 /tmp/projects/ 或临时会话目录
ls /home/ubuntu/workflow/projects/ | grep <关键词>
ls <项目目录>/        # 查已有产物：人设/定妆图/三视图/成片/分镜/guard/kb_checked.json
```

**2026-08-18 事故**：火龙漫剧复刻任务，真实项目 `huolong-guide` 里人设（芳姐/小芸）、定妆图、彩铅三视图、成片、A_STORYBOARD 全做完了；Hermes 却在 `/tmp/projects/复刻_中年下沉/`（8-16 临时目录）从零写分镜，用「中年女性A/B」泛称——与真实人设脱节，纯重复劳动。用户连问三句才暴露：「人设不是搞了吗」「他刚刚不是生成了三视图？」「图不是都发给我了？」

**纪律**：
1. 项目目录 = `workflow/projects/<项目>/`，已完成的节点产物就在里面（artifacts/、assets/characters/、guard/）
2. 接任务先 `ls` 真实项目 + 读 `workflow_state.json` / guard，确认已有什么、缺什么，再动手
3. 客户项目有真实产物时，**在临时目录重做 = 重复劳动 + 目录错乱**，等于自创流程
4. 没授权不动生产文件（不擅自备份/合并/删除 artifacts）；改前先汇报，改完留备份
