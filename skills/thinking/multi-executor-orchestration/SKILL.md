# 多执行器编排（指挥 codex/claude/DS 一起建系统）

## When to Use

触发：让多个 AI（codex/claude/DS）一起做方案、建系统、写 PRD、分工协作、或审核它们产出时。核心场景：老板要建一个系统（如归因系统），Hermes 负责调度 + 审核，执行器负责产出。

## 核心定位（2026-08-14 天行者定案）

**Hermes = 指挥 + 审核，不是执行者。** 面对老板 = 汇报 + 执行 + 参谋；面对执行器 = 调度 + 审核（他们自己出方案、自己建，Hermes 审裁决）。判断分析能力必须在执行器之上，否则审不了它们的产出。

## 铁律零：执行器分工（2026-08-15 天行者定案，多次纠正）

**Claude 只做架构/契约/对抗审查/终审；具体执行（写文档/写码/复盘示例/模板/大白话说明/结构化文档）一律 codex（高 effort）。**

- **Claude 默认不用，老板点名才用**——「先不用调用 Claude，Claude 我让你用的时候你再用」。
- 复盘示例、模板、需求说明、大白话翻译、技术文档写作 → **codex**，不是 claude。
- 架构方案、契约设计、对抗审查、终审裁决 → claude（或老板点名时才用）。
- 老板纠正链（本会话实录）：先「这种事情不要交给 Claude，让 Codex 来写」→ 再「Claude 只做一些架构方面的东西」→ 再「具体执行的话，让 Codex 来」→ 最后「Claude 我让你用的时候你再用」。每轮更严格，最终定案如上。
- 产物文件头执行者标注必须与实际执行者一致——codex 会沿袭 prompt 模板里的「> 执行者：claude」不改，审核时发现不符要修正（实测复盘示例被 codex 写成 claude，需 patch 改回）。

## 铁律一：下任务必须定义角色（用户两次纠正，定案）

给 codex/claude 下任务时，`[角色]` 必须按任务定义**具体专业身份**，不能笼统写「后台执行器」。格式五件套：

```
[角色] 你是 <具体专家身份>，负责 <职责>。你只产出 <物>，不对话。
[背景] <现状/三套方法论并存这种>
[硬约束] <不可违反的边界，如"不用TTS"/"消耗量第一指标">
[裁决点] <必须明确回答的争议，逐条列>
[产出要求] <中文结构化markdown、标注「执行者: codex」、结尾OUTPUT标记>
```

**为什么**：不定义角色 → codex 默认当「开发者」→ 方案偏技术实现，缺业务/归因/运营视角。带具体身份去读材料，产出的「我建议/裁决」才有立场。反面教训：给「写归因系统方案」没定义角色 → 两份方案都缺业务视角，只能重跑。

## 铁律二：分层文档顺序（一层层下来，不能乱）

建系统/写 PRD 的文档顺序，老板定死，每层确认再进下一层：

```
业务描述（做什么）→ 条件背景（现状/约束）→ 业务流程（怎么做）
→ 架构（怎么搭）→ 归因逻辑（核心）→ PRD（最终文档）
```

**关键**：① 每一层老板确认通过才进下一层，禁止跳层/合并；② 归因逻辑（或该系统的核心逻辑）必须在写工程前搞清——「归因逻辑不清，工程白搭」；③ 先讲清楚做什么，再讲怎么做，最后才出文档。

## 铁律三：双轨独立产出 + 审核裁决

1. 同一需求让两个执行器（codex vs claude）各写一份，**独立、并行**（分锁，别共锁串行）。
2. 对比两份：谁更贴需求原文 / 更可落地 / 更严谨。
3. 审核裁决用五智囊对抗 + 六顶帽子（见 `decision-framework`）——先实测定位，不信自证。
4. 需要收敛时让两边互评，到 90% 一致才定稿（见 `dual-executor-consensus`）。
5. 忠实度检查：产出 vs 需求原文，有没有擅自改需求/加条件/跑偏。

## 并行 vs 串行

codex 和 claude 是独立程序，可以**并行**（分锁：codex 用 `/tmp/codex.lock`，claude 用 `/tmp/claude_remote.lock`）。但 2GB 内存机器上两个重任务并发有 OOM 风险——内存吃紧时改串行，别硬并行。

**内存升级后（2026-08-14，新加坡机 2GB→4GB）**：4GB 可安全并行 2-4 个重任务（系统+网关约 900MB，每个 codex/claude 重任务约 450MB：3 个占 60%、4 个占 72% 仍有 1GB 余量）。5 个必须排队。memory 或架构变更后先 `free -h` 复核再定并行数，别按旧内存办事。

## 容灾降级

cc/codex 挂了 → DS 降级（见 `ds-fallback` 相关脚本与 `DS_FALLBACK_PLAN`）。核心：DS 能验证不能发现，只顶执行不顶审查；不可逆操作零降级（冻结排队等恢复）。

## 坑点（实测）

- **下任务必须钉死「唯一产出是文件，不写文件=任务失败」**——codex/claude 可能只把回应打在 stdout、不写产出文件（实测 PRD 对质两次跑偏，`tail -30` 只见内容不见文件）。prompt 里写死：`[产出] 用 write_file 写 <绝对路径>，写完执行 echo "OUTPUT: <路径>"`；派完先确认文件落盘再继续下一步。
- **用户问可行性 ≠ 让我实施**——用户问「X 可行吗/是不是搞个 Y 就行了」时，先给判断和方案，等明确「搞/搭/跑」指令再动手。实测用户问 codex 放国内可行否，我直接搭了代理，被纠正「我没说让你搭代理，我是在问你」。
- **收到 codex 设计稿后先用用户硬约束过滤再写实施任务书**——codex 自己出的架构方案可能包含用户已否决的方向（如「搬 Hermes 到另一台机器」）。别直接把 codex 方案打包成实施任务丢回 codex 跑。先把方案跟用户的硬约束（两机独立不搬迁、不改飞书入口等）逐条对一遍，违逆的删掉，只留合规部分写进实施任务书。实测：codex 方案里含「Hermes gateway 从新加坡搬到广州」，用户看到后立刻拦停：「不是说了两边分开吗？hermes还搬广州？」
- **用户说「停下来」/「停」= 立即 kill 后台 codex 进程**——不解释、不反问、不讨价还价。先 process_manage kill 掉正在跑的 codex，再回话。
- **别漏定义角色**——最常犯的错，漏了就重跑（浪费一整轮）。
- **别共锁串行当并行**——两执行器共一把锁会排队，还看不出问题。
- **分层文档别跳**——跳过业务描述直接写 PRD = 后面每层都要返工。
- **审核别自产自评**——Hermes 不亲自写方案再自己审（违反智力活外包铁律）。

## 🚨 大架构审核必须穷尽式——先审透再实现（2026-08-16 血泪，老板纠正两次）

**用户原话：「你先把整个细节审核完，再去做，不然你做了也是白做」+「先把所有可能发生的问题都审核一遍」+ 403 一个错暴露「里面还有很多错」。**

**教训：** 大架构（几百行设计文档）第一轮只做「结构审 + 声称核验」远远不够——Claude 出的 v1.0 架构 593 行看似完整，实际藏 8 个 P0 阻断 + 1 个状态码语义错 + 数据模型/安全/部署/合规 20+ 条。**只审结构不实测 = 把「接口签名当能力」，实现时必然返工。** 老板一针见血：403 该 404（防枚举）——同类的语义错误往往有一批，要系统性地穷举，不是发现一个改一个。

**穷尽式审核流程（三轨并行，产出合并清单）：**
1. **架构 owner 自审**（让 Claude 批判自己的架构）——自己找矛盾/契约不一致/「把接口签名当能力」处
2. **实现方独立评审**（codex 从「能不能落地」挑毛病）——给 7 个维度：可落地性/过度设计/遗漏/技术选型/工作量/数据模型/验收真实性
3. **实现方补漏扫描**（codex 在已有评审上再深挖新维度）——业务运营/表单设计/质量兜底/客户心理/财务/性能/运维/依赖
4. **Hermes 亲自核验关键技术声称**——不信自证，信实测：approve 有没有 cycle/piece、红线门只扫第一个文件（`return` 缩进在循环体内）、脚本到底存不存在（Claude 引用两个不存在的 gate 脚本）、开关是常量还是 env 可覆盖
5. **合并去重 → 分类（P0/P1/P2）→ 修订**：P0 阻断（授权链可绕过/红线漏扫/确认层语义错乱/MOCK 与交付矛盾）必须修，P1 收敛，明确不做（含理由）

**核验发现的典型「接口签名≠能力」类 bug（架构审核必查清单）：**
- 有 `--cycle/--piece` 参数 ≠ 真的按实例隔离（approve 无该参数但 check 有）
- `TICKET_TTL_SECONDS` 常量存在 ≠ TTL 生效（写了从不校验）
- 脚本文件存在 ≠ 有实现（`implemented:false` 的门 = 无判定）
- `produced_by_codex` 正则接受 `codex|claude|cc` ≠ 硬校验（契约撒谎）
- 架构引用 `permission_gate.py`/`feishu_send_gate.py`——实际不存在（v1.0 自证「出口闸本就含」是编的）
- 状态码语义：**「资源存在但不给看/已删除/不存在」一律 404（防枚举），403 会泄露存在性**——客户侧 result_only 模式、C-HIDE 产物、越权访问、过期 token 都是 404，不是 403

**实现顺序纪律（老板定死）：** 审核没完不准实现 → 修订版架构逐条核验过 → 才让 codex 写代码。中途发现架构有错就停 P1 实现、先修架构，**别让 codex 按错的架构写（写了也返工）**。

## 关联

- `decision-framework`：五智囊/六顶/决策分轨（审核裁决方法论）
- `dual-executor-consensus` / `multi-executor-convergence`：互评收敛到 90%
- `review-fix-verify-loop`：审查-修复-验证循环（防 codex 越改越烂）
- `codex-bridge`：单任务打包格式（定义角色五件套的落地模板，如已 adopt 可直接改）
- `long-form-writing-quality`：分层文档顺序在长文场景的应用
