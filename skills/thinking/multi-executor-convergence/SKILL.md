# 多执行器方案收敛（Multi-Executor Convergence）

## When to Use

用户要求「让 X 和 Y 各写一份」「两组分别产出方案/PRD」「让两个 AI 互相评」「一致率到 90% 定稿」——即**方案/文档类产出**（PRD/架构方案/打法策略/产品设计），不是单任务执行。触发词：让 codex+Sol 写、让 Hermes+DS 写、两份对比、互相提意见、一致率定稿、六顶帽子评审。

## 流程（2026-08-13 实测定案）

```
① 两组独立写：不同执行器组合各自独立调研+独立产出（互不参考，禁串结果）
   常见分组：codex+Sol(gpt-5.6-sol) 一组 / Hermes+DS(DeepSeek) 一组
② 评审：Claude 读两份 → 评各自优劣/遗漏/与现有实现冲突（实测优先，不只读文档）
③ 交叉互评收敛：A 的判断发给 B 评、B 的发给 A 评（原话打包，不加 Hermes 判断）
   每轮要求双方明确声明「一致率 XX%」；未到则把对方意见再发回继续（最多 3-4 轮）
④ 汇总终稿 + 确认一致率 + 补残留：让实现方（codex）把双方认领的修正汇总成终稿，
   再由确认方（claude，架构契约角色）逐条核对终稿覆盖了多少共识，给出「一致率 + 残留清单」。
   残留清单里「会改变运行行为」的条目必须补掉才到 100%（见踩坑）
⑤ 六顶帽子终审：Hermes 用六顶帽子（白/红/黄/绿/黑/裁决）做最终把关，用户拍板定稿
⑥ 落地：定稿方案按 P0/P1/P2 分批让 codex 实施，每批验证+commit
```

## 关键机制

### 1. 独立产出（防串味）
- 两组执行器**互相不知道对方的产出**——独立调研、独立写
- 打包 prompt 时明确「独立分析，不要参考别人的结论」
- 差异是价值：不同模型视角暴露单点盲区

### 2. 原话互评（不加判断）
- 用户要求「把两个判断互发对方评」→ **按原话打包**，Hermes 不加自己的判断
- 让 A 评 B 时给 B 的**完整原话**（不是摘要），防止转述失真
- 2026-08-12 双执行器互评定案：用户原话「不要加你的判断，按照我的原话」

### 3. 一致率硬门槛
- 每轮收敛要求双方**明确声明一致率**（如「同意七成」「一致率 92%」）
- **≥90% 才定稿**；未到 → 把对方意见再发回继续收敛（最多 3-4 轮）
- 两边都说「可定稿」才算收敛完（不是一方说了算）

### 4. 评审先找「与现有实现的正面冲突」
- Claude 评审 PRD 时**实测现有代码**（不只看文档）→ 发现三个致命冲突：
  ① 人工门批准通道缺失（门禁只有 check/status，无 approve 命令）
  ② 产物路径装不下多作品（artifact_path 不带 work_id）
  ③ 现有流程发布前收敛成单值（node4 取最高分版）
- 教训：**方案文档再完整，不先解决与现有实现的冲突，建什么都会被推翻**

### 5. PRD 三标签约定
- 合并版 PRD 的**每条需求带三个标签**：优先级（P0/P1/P2）+ 依赖 + **要改哪些仓内文件**
- 第三列（要改哪些文件）两份 PRD 都没给，但它决定工期——评审时补上

### 6. 调度者必须自己终审，不能只转述（2026-08-14 实测）
- 用户会问「你不审核吗」——双执行器收敛不是「派任务→转述结果→请拍板」，调度者（Hermes）必须亲自读产出终审
- 终审动作：读产出文件核对命门（3 个 P0 不被削弱 / AC 可测试 / 防伪造堵洞 / 忠实于基准），用六顶帽子给结论，再交用户拍板
- 本会话 PRD 终审实测：核审批（REVOKED 终态+一次性消费堵重放）、归因（N 只计 rank_eligible=true、硬隔离键分行业）、证据（四级判断不吞 PLATFORM_RACE）、回流（逐条批准+strategy_version 不可变）四块命门，确认可定稿 + 列 2 个实施前置（基准不自洽补丁、越界修正核对）
- 审核结论要分「通过/有条件通过/打回 + 条件」，带白帽事实（行数/AC 数/章节）+ 黑帽风险（前置条件）

## 六顶帽子第三方评审模板

```
⚪ 白帽（事实）：数据/实测/一致率
🔴 红帽（直觉）：第一反应/情绪
🟡 黄帽（价值）：最值钱的点
🟢 绿帽（创意）：替代方案/补充建议
⚫ 黑帽（风险）：执行复杂度/未验证假设/漏掉的
🎯 裁决：通过/有条件通过/打回 + 条件
```

## 架构/方案「穷尽审核」法（2026-08-16 客户运营平台案例·用户两次纠正后定案）

**背景：** 用户问「这个方案你审过了吗？你是怎么审的？」→ 我承认只做了结构审+声称核验；用户再纠正「你先把所有可能发生的问题都审核一遍，让他们」「你先把整个细节审核完，再去做，不然你做了也是白做」——**教训：方案审核不能「读一遍+印象审」就放行，必须穷尽 + 实测。**

**穷尽审核三路并行（产出三方问题清单 → 合并去重 → 总清单）：**

```
① Claude 自审（架构 owner 批判自己）：契约一致性/状态码语义/需求覆盖/自相矛盾/
   边界异常/数据一致性/体验/未来扩展——「承认疏漏不辩解，找得比谁都全」
② codex 评审（实现方挑落地毛病）：可落地性/过度设计/遗漏/技术选型/工作量/
   数据模型/验收路径真实性——「哪些步骤执行不了/依赖不存在」
③ codex 补漏扫描（运营/商业/信任层）：业务运营/表单行业差异/内容质量/客户心理/
   财务成本/性能边界/日常运维/依赖集成——「真实客户进来会不会争议或亏损」
```

**合并规则：** 三方问题清单 → 去重（标注来源）→ 按严重级分类（P0 阻断/P1 重要/P2 改进）→ 每条给位置+问题+为什么+修正建议 → 一份总清单交老板拍板。审核报告落盘（`outputs/三方审核合并总清单_<日期>.md`），老板看总清单，不看散文档。

**实测验证（不信自证，信实测）——这是审核的命门：**
- 执行器声称的每一条「现有代码已支持 X」都要**亲自跑命令验证**（grep 源码/运行脚本/查状态），不能转述
- 本案例实测确认：approve 无 cycle/piece、confirm_gate 无版本、produced_by_codex 接受 claude、红线门只扫第一个文件（`return` 缩进在循环内）、授权链可被空项目占位文件绕过——**全是「看文档以为支持，跑代码才知道不支持」**
- Claude 自认根因一句话，直接写进审核报告：「**我把接口签名当成了能力，凡沿用存量处都没实测**」——这就是架构审核最常见的死法

**状态码语义这类「一类问题」要系统排查，不逐条补：**
- 用户发现 403 应为 404 后追问「403 那个错误应该有好多条吧」→ 教训：**发现一个语义错误 → 全文搜同类场景**（「资源存在但不给看/已删除/不存在」统一 404 防枚举），不是只改一处
- 同理：所有「沿用存量」「现有实现已支持」的表述都要系统核验

**老板视角的三句话收尾（审核报告最后必须有）：**
1. 方向对不对（框架层）
2. 现在能不能做（P0 修完能不能出第一版）
3. 什么时候能开放真实客户（商业化项 + 上线门槛全过之前只做内部测试）

## 审核通过后的实现启动：失败测试先行 + 契约冻结（2026-08-16 客户运营平台·三阶段落地）

穷尽审核出总清单 → 老板拍板 CR → **不要直接写页面**。三步硬顺序（P0-A 测试全红是契约冻结的验收物）：

```
阶段一 失败测试先行：实现方先写「证明存量代码不满足 v2.0 契约」的测试组
        → 全部为红是预期（这就是契约冻结的验收物），每条失败要打印真实失败原因
        → 硬约束：不 mock 被测对象（mocking 门禁=自欺）、不改被测脚本
阶段二 契约冻结：一项目一 piece/视图目录/行业表单/分支产物/DDL/API 状态码判据/
        不变量断言点 固化成 YAML/SQL/OpenAPI（机器可验证，不是散文）
        → 契约冻结后才写实现
阶段三 P1 页面闭环：按 §实现顺序 1-9 步做（登录→导出器→状态机→表单→
        免费适配器真跑→显式确认→交付→巡检）
```

**关键纪律：**
- **写失败测试是「契约验收物」不是「测试负担」**——13 条全红 = 现状不满足契约的实证，修复后同一测试变绿 = 修复真生效。比「实现完再补测试」更能证明契约被遵守
- **架构 v2.0 的「实测基线表」纪律**（Claude 自审固化四条之一）：架构文档里凡引用存量能力，§1 必须有一张「已实测（M 编号，附命令+输出）/ 待实测（U 编号，标谁测）」基线表；**正文任何引用必须能回指某一行，表里没有的一律不得作为承重**——这是「把接口签名当能力」的物理解法
- **每条 CR 带 owner + 批准人 + 终审人 + 降级路径**：v1.0 的 CR 没 owner 导致需求无人落地；无 owner 的依赖=没有这条依赖。不批的 CR 必须有降级方案（平台层断言兜底），不能悬空
- **P0-A 修复顺序按合规底线优先**：先红线全文件扫描（改动最小）→ 确认协议 → status→check → 授权链（最大）——但「平台层前置断言」可并行先行生效，不等脚本 CR 全过
- **用户说「先讨论完再派活」→ 执行器一律停**（2026-08-16 用户原话「你先别让他做那个审核，我们先把这个东西讨论完再让他做，不然你一直停一直跑」）：需求讨论期派活=白烧额度，讨论透了一次性派；方案/架构方向没对齐前，不让任何执行器开工（含正在跑的，先 kill 等讨论）

## 修复-验证循环的文档层验收（2026-08-22 gz-full-fix round2-6 案例）

**代码全 PASS ≠ 交付可部署。** gz-full-fix 六轮循环里代码第 3 轮就稳定了，真正卡住的是**部署说明/范围声明文档层**，且连续三轮同一类漏项没人发现。验证修复循环时，验收维度必须覆盖文档，不只代码：

- **映射表与 staging 目录必须机械对齐**：`execute_api.py` 从部署说明的文件映射表和部署顺序里消失了三轮（round2 有 → round3 起消失），但 `py_compile` 静态检查覆盖了它 → 制造「已纳管」假象。**staging 里有、映射表里没有 = 静默不部署**。修法：S0 加机械断言「staging 下每个 *.py/*.sh/*.yaml 必须在映射表出现一次、条数相等」，靠人眼核对必然漏。
- **静态检查覆盖 ≠ 部署路径存在**：语法检查通过的代码若没有部署步骤/白名单创建步骤/回滚项，等于没交付。验收时逐要件对照「代码交付 / 部署说明」两栏（P0-H 案例：代码 9 hunk 全对、白名单逻辑全对，但部署说明不部署它）。
- **事实陈述必须实跑后写**：MD5、行数、hunk 数、计数（WEAK_COUNT）全部要跑命令取数，禁止「估计/假设/凭印象」。codex 写「容器已收缩只剩 1 个弱标记」被验收方原文照跑脚本当场打脸（实为 17 个，flag mtime/ctime 全早于文档落盘）。写文档前实跑验证，验证结果贴进文档。
- **同一个错误数字会换位置复活**：P1-I（17 vs 1）修好后，同一错误在下一轮以「当前状态 WEAK_COUNT=1」形式复活（P1-M）。修事实错误时**全文档族 grep 该数字/表述**，不只改验收点名的那一处；验收复验时也要 grep 全文确认无残留。
- **文档事实错误可能有停产量级后果**：迁移类前置（如弱标记清单）若被错误写成「只剩 1 项」，执行者按错误清单操作 → 批量停产。事实陈述错误 ≠ 小问题，验收要核对它对下游操作的触发条件。

## 循环止损与节奏（2026-08-22 天行者反馈固化）

- **用户说「改个没完了啊」时**：如实说清现状（代码已 PASS、卡在文档层、每轮验收都在文档挑出新漏项），给止损选项（继续修到 PASS / 代码层直接部署 / 下轮再 FAIL 就停），让用户拍板，不擅自继续循环。
- **小修不必再派执行器**：验证方（claude）给了精确 ≤5 行文本修法且不涉及代码时，Hermes 直接 patch + 同轮复验，省掉一次 codex 派发（round6 三处文档修正共 5 行，patch 3 次 + claude 复验即可）。
- **每轮验收范围要显式要求「不回归核查」**：round4 已 PASS 项必须逐条复跑（token 层、错类全拦、v11 拦截等），防止修 A 坏 B。

## 踩坑

- **分组不要同质化**：codex+Sol 与 Hermes+DS 模型不同才有对比价值；同模型两组=白做
- **DS 档位落差**：DS 走 codex-slot 只能用 flash（比 pro 弱一档）——写 PRD 这类大文档会偏浅，但作为独立视角仍有价值
- **不判胜负的首版定位**：量级小（如 17 条/月产能）时严格 A/B 永不触发——首版定位应为「身份链+证据+结构化记忆」而不是判胜负（2026-08-13 PRD 评审）
- **归因/数据系统禁模糊匹配**：没有确定性映射键的数据进异常队列，不做相似度归因/比例均摊
- **「不做多触点归因」这类否定要老板确认**：PRD 首版曾写「不做多触点归因」，老板明确否定——归因需求最终定为「从信息流投放数据归因到素材级、多触点归因要做但触点=1、目标①单条视频消耗量②播放量③完播率、循环周期找 top25% 素材（1/2/3/4 天可配、起始固定、矩阵式）」。教训：方案里「明确不做 X」的条款，必须先跟老板确认再写死，别替老板拍板技术方向
- **承载方式别替老板定**：PRD 首版建议 CLI 命令承载，老板否定——「不能靠记忆，还是得靠文件和流程，写个后端单独子容器」。承载方式（CLI vs 后端 vs 容器）是老板决策项，先问
- **人工门保留待指定**：新系统人工审核节点先全保留（approval_role=PENDING_SPEC），老板后续指定哪些需要人批——不默认全批也不默认全自动
- **一致率 ≥90% ≠ 直接定稿，要看残留清单**（2026-08-14 实测）：claude 确认一致率 97.5%（过了 90% 门槛），但给出 2 条残留——其中 1 条「N 的计数口径没写明只计 rank_eligible=true 成员」会改变运行行为（12 条含 5 条缺失天被误判样本充足）。做法：确认方（claude）给「残留清单 + 处方」，实现方（codex）按处方补残留，补完才 100% 定稿。别只看一致率数字就拍板——「会改变运行行为」的残留哪怕只有 1 条也要补。确认方给的处方必须原样落进补丁 prompt，不让实现方另起炉灶。
- **派执行器任务必须钉死「写文件」**（2026-08-14 PRD 对质实测）：codex/claude 对质任务第一次「正常完成」（exit 0）但**只输出内容、没写回应文件**（产物 MISSING），白跑一轮。修正：prompt 开头写「你的唯一产出是文件，不写文件=任务失败」，结尾明确「用 write_file 写 <路径> + echo OUTPUT: <路径>」验证。评审/对质/汇总类任务尤其容易跑偏成「打印内容不落盘」，每次都要钉死。
- **prompt 文件放持久目录，别放 /tmp**（2026-08-14 升级重启实测）：/tmp 在实例升级/重启后被清空，prompt 文件全丢，任务报「No such file or directory」要重写。派任务前把 prompt 存到 `workflow/prompts/`（持久目录），任务命令引用持久路径。
- **用户问可行性 ≠ 命令动手**（2026-08-14 实测）：用户问「直接搞个代理就行了把」是问可行性，我误判成指令直接搭了代理，被纠正「我没说让你搭，我是在问你」。规则：用户问「行不行/能不能/是不是就行」→ 先回答可行性+方案+前提，等用户明确「搞/做/跑」再动手。方案类问题默认是咨询不是派活。
- **用户催收尾时按需砍环节**（2026-08-14 PRD 阶段实测）：完整双执行器流程（双方案→评审→对质→汇总→确认一致率）很重，用户说「搞了一天，赶紧搞完」时，砍掉尾段「确认一致率」环节——评审+对质已足够收敛时，直接让实现方汇总终稿，节省一轮。核心纪律保留：3 个 P0 命门必须在汇总终稿里有对应契约+AC。
- **用户要「所有合并的完整版」时再合一轮**（2026-08-14 PRD 定稿实测）：主体终稿已出但后补对质/评审又发现新内容（越界修正、基准自身不自洽 P-01~P-05 补丁）时，用户拍板可能要求「出所有合并的完整版」——把后补内容也吸进最终版。做法：以主体终稿为基础，prompt 明确列出「必须吸收的后补内容」（逐条），产出能直接当实施依据的定稿（不依赖阅读评审/对质文件），合并后快速核命门（3 个 P0 不被削弱 + 越界修正清除 + 补丁列出）再交用户确认。
- **汇总/对质任务注意执行器「打印不落盘」的变体**（2026-08-14 PRD 对质第二轮实测）：即使 prompt 钉死「写文件」，codex 对质任务仍可能完成但产出 MISSING（它打印了分析内容却没写回应文件）；重派时进一步把「产物格式」单独成段、明确 write_file 绝对路径 + echo OUTPUT 验证。同一批任务出现一次跑偏，重派必须比首派更收紧，不能原样重发。
- **拍板后修改要一次重写到位，别挤牙膏式逐条追加**（2026-08-14 星广定稿实测）：老板连续拍板（4 条边界/优先级/定位 + 「物料制作及消耗归因，不是商业归因」澄清）后，我先派「落实 4 条拍板」、又追加「物料归因澄清」，老板叫停「你让他停了重写啊」。教训：**拍板信息汇总齐后合并成一次重写**——综合 prompt 一次列全部拍板 + 澄清 + 重写要求（定位写死、边界、数据范围、优先级、相关章节重写到位、冲突旧表述以新拍板为准），让执行器一次性改到位，再交用户；不要收到一条拍板就派一轮追加。
