# gz-full-fix 六轮验证循环实录（2026-08-22）

execute_api.py + 通用 skill 引用卡点改造项目：codex 改 → claude 独立验收 → FAIL 修 → 复验，共 6 轮 + 1 次复验。**代码第 3 轮稳定，真正卡住 4 轮的是部署文档层。**

## 循环结构

```
round1-2: 方案验收 + 首次实施（claude 出方案 → codex 实施 → claude 验收）
round3-4: 发现整文件重写问题（P0-A 无基线纪律）+ is_checked 收紧未灰度（P0-B）
round5:   代码全 PASS（16/16 断言），卡 3 项文档：P0-H / P1-I / P1-J
round6:   修文档 → claude 验收 → FAIL 3 项新文档问题（P1-M / P2-N / P2-O）→ Hermes 直接 patch 5 行 → 复验
```

## 关键失败模式

### P0-H：交付物从部署清单消失（最隐蔽，三轮无人发现）
- `execute_api.py` 是问题一唯一交付物，相对生产基线 9 hunk
- round2 部署说明有它（映射表 :9 / 基线 MD5 :26 / 部署步骤 :66 / 白名单 :50-56）
- round3 起全部消失，只在 `py_compile` 语法检查行留名 → 静态检查制造「已纳管」假象
- **根因**：三轮验收都聚焦 gate 文件基线纪律，没人回头核对映射表是否掉了行
- **修法**：映射表补行 + 六份基线门禁 + 白名单创建步骤（root:root 0644）+ 部署顺序两步硬约束 + 回滚项 + 回归断言

### P1-I → P1-M：同一个 1 vs 17 错误换位置复活
- round5：文档称「弱标记清单无法重建、只剩 1 个」——实际脚本原文照跑 WEAK_COUNT=17
- round6：清单修对了，但新增「当前复扫只得 1 项、容器收缩」——又是假数（17 个 flag mtime/ctime 全早于文档落盘）
- **教训**：修事实错误必须全文档族 grep；验收复验也要 grep 全文

### 事实陈述纪律
- MD5/行数/hunk 数/计数必须实跑取数，禁止假设
- claude 验收「原文照跑文档自带脚本」是杀手锏——文档里的验证脚本就是给验收方复跑的

## 止损节奏（用户「这改个没完了啊」）
- 如实说清：代码已 PASS、卡在文档层、每轮验收都在文档挑新漏项
- 给 3 个选项：继续修到 PASS / 代码层直接部署 / 下轮 FAIL 就停
- 用户选「跑完这轮」→ 修完复验
- 小修（≤5 行、验证方给了精确修法）Hermes 直接 patch，不再派 codex

## 验收断言模板（round5 16 项可复用）
- P0-A GZ 出片措辞无 marker rc=1 / 纯运维 rc=0（且旧基线 rc=1 净改善）
- P0-B SG 弱标记 WARN rc=0 / BLOCK rc=1
- 模板契约 errors=0（round4 为 17）
- token 二次消费 rc=2、TEST_RUN 双路径、v11 G1 rc=1
- 词表 30 项逐项相等、pyc=0、运维词包裹生产意图仍 BLOCK
