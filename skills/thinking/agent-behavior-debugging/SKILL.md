# Agent 行为偏离排查

**触发：** 用户反馈「小鹿/机器人经常不XX」「完全不会XX」「写文案直接给分镜脚本」等行为偏离。这类问题**不是模型笨**——几乎都是规则/机制/文档层面的系统缺陷。

## 🚨 排查顺序（按此三步，别跳）

```
① 规则在不在？
   - system_prompts 缓存（state.db system_prompts 表）里有没有该规则
   - SOUL.md 速查表 / skill 里有没有覆盖该环节的规则
   - ⚠️ **记忆文件也是规则源（2026-08-07 实战）：** customer 的 `memories/USER.md` 和 `memories/MEMORY.md` 会注入 system_prompt——里面可能躺着旧规则，跟新修的 skill/SPEC 直接打架。症状：规则明明改了但 bot 还是旧行为。必查：grep 记忆文件里的旧规则关键词（如「出片前必须输出分镜脚本」），找到就 patch 记忆（保留意图、对齐新分工），且写 customer 记忆要 cross_profile=true
   - 没有 → 规则缺失（不是执行问题）

② 物理卡点通不通？
   - guard 强制加载列表是否覆盖该环节（如内容生产是否强制加载工作流主 skill）
   - 节点文件模板是否强制产出物格式（模板第一列是什么，产出物就是什么）
   - review_gate/confirm_gate 等校验是否真的检查到了内容
   - 物理卡点挂在错误文件名/错误编号上 = 形同虚设

③ 文档一致性？
   - 执行手册（如 huoshan skill）与权威定义（如 SPEC yaml）的节点编号/文件命名/章节标题是否对齐
   - 执行手册内部是否有自相矛盾（同一产出物关联多个编号）
   - 执行手册是否落后权威定义（缺文件引用/缺新规则）
```

## ⚠️ 用户偏好铁律（2026-08-07 用户明确纠正）

- **禁止直接往 SOUL.md 塞内容**——用户原话「你什么都往soul里加？」。SOUL.md 只放身份/铁律/兜底，方法论进 skill/知识库。
- **修复行为问题用物理卡点**（guard 强制加载、节点模板、文件校验），不靠软规则/提示词堆砌。
- 方法论在 skill 里但模型没加载 = 等于没有 → 用 guard 强制加载（物理）而不是祈祷模型自觉。
- **定产出物格式前先搜行业标准（2026-08-07 用户明确纠正）：** 用户说「你去网上查下文案剧本都是什么样的」——不拍脑袋定义格式。改模板/产出物格式前，先 web_search 该类型内容的行业标准格式（多源验证），再对照修改。已验证标准：文案/口播稿=纯文本台词（EasyClaw 模板）；短剧剧本=场次纯文本（火山引擎标准剧本格式）；分镜=8列表格（中影人/编导教材/掘金多源一致）。行业标准摘要见 references/industry-script-format-standards.md。

## 🔒 物理卡点设计三原则（2026-08-07 实战落地：node3_candidate + node4_review 三版检查）

1. **查 LLM 绕不过的文件存在性，不查它自己写的那份报告**：node4_review 原来只查 `节点4_评审报告.md`（LLM 自己写的）→ 三版盲评被跳过（只评 1 版也放行）。升级为查 `节点4_文案v1/v2/v3*.md` 存在 ≥3 个 → 物理拦死。LLM 要过卡点必须先产出版本文件，绕不过去。
2. **豁免用标记文件，由上游节点写入（不是 LLM 自己写）**：客户自备文案场景 → 节点0 采集时建 `_自备文案.flag` → review_gate 跳过三版检查（评审报告检查保留）。标记文件若让 LLM 自己写 = 自我豁免，无效。
3. **新卡点不进 all 总闸，防历史项目误杀**：node3_candidate 只挂在节点3 后单独调用，不进 all——历史项目没有候选文件，交付时进 all 会被误杀（同 node1_theory 先例）。

**测试方法：** 造临时项目目录（touch 文件 + 写最小报告），逐场景跑 `review_gate.py check <dir> <gate>` 验证 BLOCKED/ALLOWED（4 场景：缺文件/正常/不足/过短），再删临时目录。

**同源模式：** 选题候选（节点3）与三版盲评（节点4）是同一类「流程步骤被 LLM 跳过」问题——`节点3_候选方向.md`（内部文件，≥2 方向，不交付客户）卡点化。客户交付仍只给最终选题+理由，候选记录是内部物。

## 🔍 工作流版本核查（2026-08-09 实战：用户问「你现在的工作流是不是最新的版本」）

**核心：版本号 ≠ 内容新度。** 文件 mtime 新、内容已改，但 meta 版本号没 bump、changelog 没记 = 内容在线但版本账欠着。两者分开说，别混成「是最新的」。

**核查五步（按序）：**
```
① 核心文件 mtime + 大小：SPEC/huoshan/guard 三个文件（date -r + stat -c%s）
② SPEC meta version + update_date vs 文件实际 mtime——版本号没跟上内容 = 欠账
   (实战：SPEC mtime=08-08 12:07，meta 还写 4.8/08-05——8/7+8/8 改动都没 bump)
③ changelogs 目录最新一条 vs 文件 mtime——改版没写 changelog = 欠账
   (实战：wiki/history_archive/changelogs/ 最新停在 08-05，但 8/7 改了 SPEC/huoshan/guard)
④ 内容痕迹 grep：grep -n "2026-08-07" 找日期标注，确认某日改动是否真的在线上
   (实战：8/7 的 node3_candidate/三版盲评/guard五件套/口播铁律/素材归档全在 SPEC+huoshan+guard 里)
⑤ 脚本层物理落地：文档写了 ≠ 脚本有。grep review_gate.py node3_candidate、node4_review_scorer.py
   (实战：L89/93/97/234 全在——文档标注和物理卡点同时验证才敢说「在线」)
```
**输出格式：** 内容在不在（在线/缺失/部分） + 版本账跟没跟上（bump/changelog 欠没欠），两个结论分条给，各带证据。

## 🚨 审计深度铁律（2026-08-07 用户连续两次纠正「每次说没问题，又出来一堆」）

**表层检查 ≠ 审计完成。** 文件存在/md5 一致/脚本能跑 = 只验证了「没断」，没验证「内容对不对」。

**用户纠正链：** 第一轮只查文件存在+md5 → 用户「你看看整个工作流还有什么有问题的地方」→ 第二轮 surface 扫 → 用户「你再仔细检查三轮吧，每次说没问题，又出来一堆」→ 第三轮内容级五方对照才挖出 10 个问题（4 个 P0 卡死级）。

**内容级五方对照法（第三轮实际用到的）：**
```
① 文件名差集：正则提取 SPEC/huoshan/guard 三方所有 `节点N_XX.md` 引用 → 求差集找同物异名
   (实战挖出：节点3_外部校准.md 只在 huoshan；节点16_发布策略.md 只在 SPEC)
② 逐节点 input_deps→post_checks 产出 对照：SPEC 各节点输入输出是否连续（0→17 不断链）
③ 两域/边界关键词全量 grep：Bot域/API域/节点N-M 的所有表述 → 是否收敛唯一
   (实战挖出：两域分工三处矛盾，节点6/7/9 归属不明)
④ 分支路径逐段验证：口播/小红书/剧情每段跳转 → 落点节点职能是否真实匹配
   (实战挖出：口播「跳过6-10进节点11」但节点11=质检不是出片——婵镜调用无对应节点)
⑤ guard 目录树完整性：文件接力树是否覆盖全节点（缺节点=接力文件名未知）
   (实战挖出：guard 树只列到节点11，12-17 缺失)
⑥ 脚本硬编码文件名 vs 流程产出文件名：grep gate 脚本里的 `节点N_XX.md` 与 SPEC 产出对照
   (实战挖出：review_gate 还在查旧名 节点4_正文定稿.md)
⑦ 废弃文档引用：guard 是否还在加载带「已废弃」标注的 references
```

**输出标准：** 每个问题标注影响等级（P0 卡死/P1 打架/P2 隐患）+ 实测证据（哪个文件哪一行/哪个命令输出），不写「可能有问题」这种软话。**说「没问题」之前必须做过内容级对照，不是文件存在性检查。**

## 📋 文档一致性审计三步（找"手册与权威脱节"类根因）

```
① 对照权威定义：执行手册的章节标题 vs 权威编号逐条比对（找整体偏移/重复/缺失）
   实战：huoshan 节点1-9 整体偏移+1（多一个重复节点1），章节标题全错位
② 文件命名清单：正则提取两边所有 `节点N_XX.md` 引用，找同物异名
   实战：分镜=节点5_分镜定稿.md（SPEC）vs 节点6_分镜定稿.md（huoshan）——该偏差已于 2026-08-07 修复（huoshan 已改用节点5_分镜定稿.md），本行保留作历史案例
③ 内部交叉引用：搜「节点N（职能）」模式，找同一产出物被关联到多个编号
   实战：分镜被写成节点5/6/9 三个号；人设写成 5/6/7 三个号
```

## 🚨 审计三大坑（2026-08-07 复查实战新增）

1. **衍生摘要会漂移，权威必须读实际文件**：计划文档/复盘摘要里写的「SPEC 节点11=合规终检」≠ 实际 SPEC 文件（真实=提示词质检）。上次修复照计划文档的错摘要改，把 huoshan 节点11 保留成合规终检，跟权威打架。**审计时逐条 read_file 实际权威文件，不信任何二手转述**——计划文档本身可能就是 bug 源。
2. **章节标题/文件名改了，正文散文引用会漏**：L1994「分镜在节点6，视觉人设在节点7」这类口语化描述不在标题/文件名里，重命名修复扫不到。验证必须额外搜散文模式：`职能+在+节点N`、`读节点N`、`节点N 强制等待 节点M`。
3. **归档目录不算残留**：history_archive/、backup_*/ 里的旧编号是留档，grep 时必须排除，否则全是误报。
4. **职能改名后必须全库扫旧称呼 + 职责挂错节点**（2026-08-07 实战）：把节点11 从「合规终检」改成「提示词质检」后，全文还有 7 处「合规终检」引用（流程总述/人设表/职责速查/两域架构/三级质控）+ 3 处「环境音叠轨」误挂在节点11（实际是节点13 ffmpeg 的活）+ guard 文件清单里的 `节点11_合规检测.md` 旧文件。修职能时：①grep 旧职能名全库（含 guard/ references/ 其他 skill）②搜「旧节点号+职责动词」散文模式——合规/环境音/拦截这类职能词挂在哪个节点③guard 流程图 + 文件清单同步改。环境音叠轨这类「职责描述挂错节点」≠ 编号偏移，单搜编号模式会漏。
5. **SPEC yaml 可能不是严格合法 YAML**（2026-08-07 实战）：WORKFLOW_SPEC.yaml 有裸 `ffmpeg: 1` 之类结构，patch 工具的 YAML 校验会拒写（YAMLError）。改这种文件用 python 字符串替换（cat 读 → str.replace → write），别用 patch。它当文档用没问题，yaml 解析器不一定能吃。 |
