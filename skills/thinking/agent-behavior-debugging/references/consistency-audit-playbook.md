# 文档一致性复查手册（多条目修复计划的验证流程）

> 触发：用户要求「查一遍 N」「复查修复项」——验证一份多条目修复计划（如 A1-C3 清单）是否真实落地。
> 原则：每个结论必须有 grep/read 证据，不凭上次会话的记忆碎片。

## 标准流程（A1 标准）

1. **读计划文档**：`~/wiki/plans/` 或 skill 目录下的修复计划，拿到条目清单与验收口径。
2. **逐项设计证据检查**：
   - 标题类 → `grep -n "^## 节点" <手册>` 对比权威 `name:` 列表（找缺失/重复/错位）
   - 文件类 → 新旧文件名计数：旧名应为 0，新名应 ≥1（`grep -c`）
   - 引用类 → `grep -rn "节点N（职能）\|节点N_XX"` 交叉引用
   - 机制类 → `read_file` 实际文件确认（guard 加载列表 / SOUL.md 兜底规则原文）
3. **权威对读**：执行手册 vs 权威文件（SPEC yaml）**逐条 read_file 实际文件**——不信计划文档里的权威摘要（见坑1）。
4. **全库扫残留**：`grep -rn <旧编号模式> ~/.hermes/skills ~/wiki --include="*.md" --include="*.yaml" | grep -v backup_ | grep -v history_archive`。
5. **同步检查**：`md5sum <default 路径> <customer 路径>` 同名 skill 应一致。
6. **更新计划文档勾选**：只标记已验证项，附日期 + 一句话证据；残留项保持未勾并写明原因。
7. **分级上报**：机械类（改编号/删列/改名）可顺手修；判断类（缺章节补不补、职能冲突听谁的）必须先问用户——动流程定义不能自作主张。

## 散文残留模式（重命名修复最易漏）

- 「职能+在+节点N」：如「分镜在节点6，视觉人设在节点7」（正确应为 5/6）
- 「读节点N、节点M 校对」
- 「节点N 强制等待 节点M 签收」
- 章节开头随手写的编号对照表/流程图

这些不在标题、不在文件名里，`^##` 和文件引用 grep 扫不到，必须按上面模式单独搜。

## 判断类 vs 机械类

| 类型 | 例子 | 处置 |
|:---|:---|:---|
| 机械类 | 改错编号、模板删镜号列、文件名改名 | 可直接修 |
| 判断类 | 缺章节要不要补（设计空白）、两个文件职能冲突听谁的 | 先问用户，列清两边说法 |
