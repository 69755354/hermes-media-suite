# 多 AI 共识收敛流程（2026-08-13 实测）

## When to Use

触发：需要 Claude 和 codex 对同一问题/方案达成一致定稿（分工规则/写作方案/软链方案/技术选型）；用户说「让两边各给判断」「互相讨论」「一致率90%定稿」。核心：**两个 AI 互相评对方的方案，收敛到一致率 ≥90% 才定稿，人（Hermes）用六顶帽子做最终评判**。

## 为什么需要

单模型自产自评会漂移（v11/v12 越改越烂教训）；两个 AI 独立判断 + 交叉互评能暴露各自盲区，收敛到 90%+ 再定稿比任何单方方案都稳。用户（天行者）明确要这个流程：「他们俩互相就方案提出意见，一致率到90%的时候定稿，你用六顶帽子的方法来评判」。

## 流程

```
① 各自独立给判断（按用户原话打包，不加 Hermes 判断）
② 把 A 的判断发给 B 评、把 B 的判断发给 A 评（交叉互评，仍是原话转发）
③ 收敛循环：A 的回应→B 评→A 再评…直到双方明确说「一致率90%+可定稿」
④ 人（Hermes）用六顶帽子法评判定稿（白帽事实/红帽直觉/黄帽价值/绿帽创意/黑帽风险/蓝帽裁决）
```

## 关键技巧

- **按用户原话一字不改打包**（用户明确要求：不加 Hermes 判断，原文转发）——打包时开头写明「【问题（客户原话，一字不改）】」
- **让每个 AI 显式声明一致率**（「一致率90%+可定稿」或列出剩余分歧点）——逼出收敛终点，避免无限循环
- **允许反驳**：codex 评 Claude 时「同意约七成」+ 列出 3 点修正——不是全盘接受，反驳要有事实依据
- **分歧处理**：Claude 评 codex「同意前提不同意定型规则」时，codex 回应要逐条「同意/反对+事实」；剩余分歧点明确列出，下一轮收敛
- **六顶帽子是人的评判工具**，不是 AI 的——Hermes 用它在定稿上做最终把关（黑帽找风险/黄帽找价值/绿帽补替代方案/白帽核对事实）
- 收敛后把定稿写文件 + 沉淀成 skill（如 long-form-writing-quality）
- 用「锁串行」跑互评（claude 和 codex 共用 /tmp/codex.lock），一轮接一轮，别并行

## 六顶帽子评审模板（Hermes 定稿前用）

```
⚪ 白帽（事实）：实测数据/文件证据/双方声明的一致率
🔴 红帽（直觉/情绪）：方案复杂度的直觉判断
🟡 黄帽（价值）：最值钱的 3 点
🟢 绿帽（创意/替代）：还能怎么更好
⚫ 黑帽（风险/批判）：执行复杂度/未验证假设/会被绕过的门
🎯 蓝帽（裁决）：通过 or 带条件通过（列条件）
```

## 实测案例（2026-08-13）

- **分工方案**：Claude 按「可逆性×事实不确定度」路由 vs codex 按「项目大小」——互评后 codex 同意七成、Claude 补「人是第三个代理」→ 92% 定稿
- **长篇写作方案**：Claude 评 codex 方案（「犯了自己诊断出的病」）→ codex 反驳 3 点 + 补第 0 步（git 救资产）→ 92% 定稿 → 沉淀为 long-form-writing-quality skill
- **软链方案**：两边都判「软链技术靠谱、运维机制不靠谱」→ 合并执行（Claude 的报警机制 + codex 的期望清单）

## 踩坑

- **别让 Hermes 自己判断混进转发**——用户要的是「原话打包」，加了 Hermes 判断就污染了独立判断
- **收敛不到 90% 别硬定稿**——列出剩余分歧点，再发一轮；或让用户拍板分歧点
- **每次互评都要带完整上下文**——对方看不到之前的讨论，打包时必须把对方方案要点原文附上
- **「六顶帽子」别让 AI 代做**——那是 Hermes 的最终把关职责，AI 只会自我辩护
