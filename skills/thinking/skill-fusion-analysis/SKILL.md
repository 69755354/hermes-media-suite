# 外部能力/技能融合分析（skill fusion analysis）

## When to Use

触发：蒸馏出新的外部 skill/方法论（如 reverse-video-prompt、DeepSeek Harness）后要分析「怎么跟现有体系融合」；用户给出融合方向定案（如「补缺不是替代」）；要接入新执行器框架/新模型壳。核心目标：**不整份覆盖、切片补缺、闭环完整、分阶段落地**。

## 第一步：先定「补缺不是替代」基调（用户定案）

融合分析前先问清方向。2026-08-23 天行者定案原话：外部能力「不是替代，是补缺。咱强的它没有；它强的咱没有。合起来正好是完整闭环」。**禁止谁覆盖谁——保留现有强项，补入外部增量，串成闭环。**

## 第一步半：先做减法——排除已有覆盖面（2026-08-27 天行者定案）

在铺能力矩阵之前，**先过一遍减法**：把外部工具的能力逐条跟现有方案比对，凡是「我们已有等价方案」的直接划掉，不进正文。用户要的是增量缺口，不是已有能力的替代品清单。

实证（2026-08-27 OpenMontage 评估）：用户问「怎么为我们所用」，我列了 Seedance Ark / Wan / DashScope / 口播管道 / 视频分析等全套能力对接价值——用户一句「感觉都没用上」。因为这些我们全部已有自己的方案在跑。真正的增量只有 Remotion/HyperFrames 合成、Backlot 看板、video_analyzer 工具链三样。

**铁律：先减后加。正文只输出「我们没有且外部有」的增量。已有覆盖面一句话带过不展开。**

## 第二步：能力矩阵对比（只对增量做矩阵）

把减法后剩下的增量能力 + 现有相关 skill 按 维度逐格标状态：已覆盖/缺项/重叠，每格带证据摘要+行号。产出关键缺口清单。

## 第三步：五张总表（KEEP / ADD / BRIDGE / CONFLICT / DEFER / DEDUP）

- **KEEP 保留表**：我方能力，外部内容不得覆盖/改写（每条带保留理由+来源行号）
- **ADD 补入表**：外部增量切片式补入指定归属——每条写源（含行号）、目标归属、切片边界（禁止整份合入）
- **BRIDGE 接缝表**：两侧都有但需显式接口才能串成闭环（上游/下游/接口约定/证据）
- **CONFLICT 冲突表**：双侧均有来源的真实冲突——标是否阻断闭环、建议处置方向（需人裁决的进 U 清单）
- **DEFER 后置表**：外部自带的上传通道/第三方引流/公开发布流程等，整段排除（涉客户素材外传+合规），解除条件写明
- **DEDUP 去重表**：重叠内容定唯一定义源，另两套降为映射/扩展段

## 第四步：闭环落地到真实节点

用户定案的闭环（如：抽帧+反推 → 出片 → 对比诊断 → 迭代 prompt → 沉淀规则）逐环挂到现有节点编号：
- 先核对真实节点名称与编号（不脑补，引用知识库行号）
- 新增动作用「建议子节点」（如节点 2.1/14.1/14.2/17.1）挂既有节点下游，**不新占主链编号**（避免编号映射冲突）
- 每步 8 字段：步骤名/节点落位/输入/执行动作/输出产物/判定通过条件/门禁关系/失败回退

## 第五步：门禁影响分析

- 新增产物 → 必须登记 registry/路由表，否则对门禁不可见
- 新增/改名 skill → 创作预读闸登记，否则预读缺名 BLOCK
- 改闸项单独列：需人批准、单独提交、单独验证、验证须有「闸真的被调用」证据、实现者不得自验

## 第六步：P0-P3 分阶段实施

按可逆性/影响面分四阶段，每阶段独立回滚：
- **P0 只读对齐+冲突裁决**：12 条冲突交由人裁决并留档；零文件改动
- **P1 补 reference 文件**：只改文档；A01-A20 判据/方法类内容切片写入；不改铁律
- **P2 闭环流程落位**：改流程文字（huoshan 等）；仍不改门禁代码；验收=非客户项目跑通一次真实闭环
- **P3 门禁硬化**：每项单独批；末阶段

## 第七步：裁决清单（U 编号）整理

- 所有需人拍板的冲突整理成 **P0_DECISION_LIST**：每项给 A/B/C 选项+影响面+关联冲突编号，**大白话版**逐条一句话解释
- 用户拍板后落盘 **P0_DECISION_LOG**：裁决原文照存（一字不改）+ 含义 + 实现方式 + 关联 + 风险提示
- **编号歧义处理**：用户口述编号与报告 U 编号可能偏移——传话书/任务书写明「双读法」：位置法（按清单排列）+ 语义法（按报告原文）都必须算出，冲突给采纳理由，两法都取不到答案的标 `[NEED_INFO]`，**禁代选、禁按顺序补齐**（2026-08-24 火龙裁决 7-10 条歧义实证）

## Pitfalls

1. **传话书只传 USER_REQ 原话 + DATA_SOURCE + 产出要求**，任务书正文/判断归执行器打包（最强红线：自己写任务书=违纪）
2. **任务书触发词误判**：USER_REQ 含「出片」等词会触发闸要求 READ_SKILL=seedance-2-0-mini-workflow——补加载标记即过，用户原话一字不改
3. **codex 额度尽 → 打包任务书的正确降级链**：先 DS v4 pro 直调（可能吐 tool-call XML 垃圾）→ 失败后用户显式拍板 claude 一条龙（打包+执行同通道=用户批准，非擅自）。禁止反复重试 DS 烧 token
4. **评审报告递归自噬**：融合后新增文件若命中创作文件名模式（含「评审」前缀的报告在 guard/director_review/ 下），会被下一轮导演意图评审递归扫描 → 四维 0 分 → 整体 BLOCK。修复：exclude 加 guard/director_review/（详见 video-render-gate-debugging 坑3b）
5. **外部 skill 自带上传通道/第三方引流内容整段 DEFER**，绝不进正文（客户素材外传合规风险）
6. **用户「经验反哺技能」定案**：沉淀终点是写回 skill 本体让技能进化，文档库只是中间态；第三层写入必须过 Skill Change Gate 六问+人批，防单条经验污染全部项目

## 案例

2026-08-23/24 reverse-video-prompt 蒸馏能力融合分析：项目 `reverse_prompt_merge`，产出 1075 行 12 节报告（能力矩阵/五表/闭环落位/门禁/分阶段/风险），用户 11 条裁决（复刻豁免/经验反哺技能/镜数按原视频/重跑人工确认/融合版为主/字幕底部/首尾帧有用/沉淀落闸）。完整方法论见 `references/reverse-prompt-fusion-method-20260824.md`。

2026-08-27 OpenMontage 评估：用户问「openmontage 怎么为我们所用」。我翻完全部工具/管道/skills后铺了一整张能力矩阵——Seedance Ark/Wan/DashScope/口播管道/视频分析等全列出「对接价值」。用户一句「感觉都没用上」点破：这些全部已有等价方案在跑，正文应只输出增量（Remotion/HyperFrames 合成、Backlot 看板、video_analyzer 工具链三样）。教训：**先减后加，正文只放我们没有的东西。**
