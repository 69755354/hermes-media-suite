# 执行器编排与产出审核（Hermes 指挥位）

## When to Use

触发：要指挥 codex / claude / DS 干活（写方案/分析/PRD/评审）、要审核它们的产出、要对比多个执行器的方案、要让 AI 产出分层的业务/技术文档。核心：**Hermes 是「指挥 + 审核」，不是「干活」**——活外包给执行器，自己负责判断、裁决、把关。

## 核心原则

1. **下任务必须定义角色**（最常犯的错，用户多次指正）
2. **分层文档顺序不能乱**（业务描述→条件→流程→架构→归因→PRD，一层层确认再进下一层）
3. **生产者 ≠ 评审者**——执行器产出的，由另一个视角（Hermes 或另一执行器）审
4. **判断分析能力在审核者身上**，不在执行者身上

## 一、定义角色铁律（下任务前必做）

**没有角色的任务 = 执行器用默认身份干活，视角跑偏。**

对齐飞书 DS 给 codex 下任务的标准格式：
```
[角色] 你是<具体专家身份>，负责<干什么>。<立场：站在谁角度/服务谁>
[背景] <现状/已有素材/要解决什么>
[硬约束] <必须遵守、不可违反的底线，逐条>
[裁决点] <需要明确回答的争议/待定项，逐条列>
[产出要求] <中文结构化 markdown / 标注执行者 / 结尾 OUTPUT 标记>
```

- **角色要具体到能指导判断**：如「广告素材归因系统首席产品架构师」「视频生成提示词方法论评审专家」「全栈运营专家」——而不是「后台执行器」「内容助手」
- **立场要说清**：服务谁、目标是什么（如「老板是素材供应商，收入=消耗×分成」）——决定结论朝哪个方向
- 反例（实测）：让 codex/Claude 写「归因系统方案」没定角色 → 产出偏技术、业务/归因视角缺失；补角色后视角才准
- **裁决点单独列出**：把「还没定、要它们裁决」的点逐条列，让产出明确回答，而不是让执行器自己猜

## 二、分层文档顺序（用户定案，不能乱）

出业务/技术方案文档，必须一层层来，**每层确认了才进下一层**：
```
① 业务描述（做什么，讲清楚给谁、收入怎么来）
② 条件背景（现状/约束/前提/待核验项）
③ 业务流程（怎么做，端到端步骤）
④ 架构（系统怎么搭，模块/数据模型/部署）
⑤ 归因逻辑（最核心：数据怎么对应/怎么分析）
⑥ PRD（最终产品文档，指标/接口/迭代）
```
- 顺序错了 = 前面没定就写后面，全链路返工
- 每层产出后**先给老板过目确认**，别一口气写完六层
- **PRD 层要内嵌「业务背景与条件」章节**（业务角色/链路/第一性原理/条件边界/待拍板项），即使前面有独立业务描述文档——用户看 PRD 不会去翻前面文档（2026-08-14 实测：PRD 直接从实施边界开始，用户指出「前面的业务背景分析那些都没有」）。补法：在标题/版本信息之后、实施章节之前插「## 业务背景与条件」，不占编号、不动后续章节

## 执行器卡片：时间上限与一轮一类（2026-10-16 血本教训）

把「8 条安全必修 + 编码/行尾 + 重打包 + 真机验收」全压给一个执行器 → 它陷入「改—自查—再改」循环：跑到第 14 轮、日志 46MB、重复调用打包脚本 288 次，**3 小时没出包、一次真机都没跑**。

任务书硬规则：
1. **必须写时间上限与产出下限**（「60 分钟内交出一个可交付包，否则 BLOCKED 报告」）；没有上限的执行器不会停。
2. **一轮只做一类**（安全逻辑 / 编码行尾 / 打包），每类自带反例测试。
3. **只在最后打包一次**：禁止每轮重打包（300MB×N，时间全烧在打包上）。
4. **必须交可交付物**：报告 + 产物路径 + 证据；不接受「我已修改了很多文件」。
5. 多个执行器共改同一份代码时，后来者必须**轮询前序 job 结束**再动手；宁可 BLOCKED 也不抢写。

## 二点五、执行器写作分工（用户定案 2026-08-15）

**什么活派哪个执行器写，用户有明确偏好，不按「谁都能写」分派：**

| 文档类型 | 派谁 | 原因 |
|:--|:--|:--|
| **结构化/模板/大白话说明/复盘示例/需求说明**（复盘报告示例、接口申请说明、大白话版翻译、模板类） | **codex** | 用户明令「以后这种事情不要交给Claude，让Codex来写」（2026-08-15，场景：T-OPS 周/月复盘示例） |
| **创作类（小说/攻略/文章，要真人感）** | **codex**（高 effort） | 用户最终定案「Claude只做一些架构方面的东西」「具体执行的话，让Codex来」（2026-08-15 三次强化后）——创作类也从 claude 改派 codex，不再默认 claude |

- 🚨 **默认不调用 Claude**（2026-08-15 用户最终指令「先不用调用 Claude，Claude我让你用的时候你再用」「具体执行的话，让Codex来」——同一天三次强化）：**Claude 默认不派活，用户点名才用**。所有执行类（写文档/写码/复盘示例/模板/创作）默认 codex；Claude 只保留架构/契约/对抗审查/终审这一路由，且除非用户点名，默认也不主动调
- 触发词判断：文档里有「示例/模板/大白话/说明/需求」这类结构化交付 → 默认 codex；任何执行活拿不准 → 默认 codex
- 已派错执行器且任务在跑 → 停掉换 codex（用户明确「先不用调用 Claude」时连跑完都不必等，直接 kill 重派）；**下任务前先按此表选执行器**
- 上表是「写作分工」，与既有「Claude=架构/契约/对抗审查/终审，codex=实现/审计/跑测试」的**路由分工**并列：审查类活仍按路由表走（claude 终审），写作/执行类按本表走（codex 全包）——但 Claude 的调用权在用户手里，用户不点名就 codex 兜底

## 二点八、实施-验收迭代环（codex 改 → claude 验 → 循环到 PASS，2026-08-22 天行者定案）

用户明令的迭代模式（原话「codex改完claude再验收一遍，有问题再丢给codex改，直到改好」）：
```
codex 实施 round 1 → claude 验收 round 1 → FAIL？→ codex 实施 round 2（附上轮问题清单）
→ claude 验收 round 2 → …… 循环到 PASS → 部署
```
与「双执行器对比评判」（各自独立写、Hermes 评判）不同：这是**实施方与验收方交替迭代**，验收方固定 claude、实施方固定 codex，验收结论 PASS 才停。

**落地要点（2026-08-22 广州 execute_api 全量改造实测）：**
1. **每轮独立任务书**：codex 实施任务书复制基础版 + 追加「本轮修正任务：上一轮 claude 验收结论的问题清单 = 必改项，逐条标注『修正自验收结论 round N』」；claude 验收任务书指定「验收对象 = 本轮实施产物」，验收结论写 `验收结论_roundN.md`（带轮次，不覆盖方案文件）。
2. **验收 PASS 判定**：`grep -q 'PASS' 验收结论_roundN.md`；FAIL_WITH_REASONS 的问题清单自动传给下一轮 codex。
3. **迭代上限**：MAX_ROUNDS=4；达上限后部署最后一次产物（不白跑）——用户授权「一次改完不用批准」时，**任何一步失败/验收不过都不停在半路等批准**，记录日志继续走（dispatch 异常/验收缺失/部署异常都只 log 不 exit）。
4. **全自动编排脚本**：`wait_claude1 → dispatch_claude2 → for round: dispatch_codex_impl → dispatch_claude_verify → verify_passed? break`，后台跑 + notify_on_complete；每轮 brief 由脚本从基础 brief `cp` + append 生成。
5. **用户授权语义（重要）**：「一次改完，不用我批准」= 执行阶段全自动闭环，验收不过直接进下一轮修正；「codex 验收有问题就自己改了」= codex 实施任务书里写明「验收结论的 FAIL/P0/P1 问题 = 你的修正任务，修正后直接实施，不需要等任何批准」。**注意区分**：「需求没讨论透不派活」（讨论阶段要追问）与「已授权一次改完」（执行阶段不等待）是两个阶段，不要用讨论阶段的谨慎去卡执行阶段。

## 三、双执行器对比评判

需要重要方案时：让两个执行器（如 codex 和 claude）**各独立写一份**，然后 Hermes 评判。
- 独立写（不同模型/不同视角，不互相参考）
- 评判维度：对需求的忠实度（有没有跑偏）、可落地性、各自的亮点、共同弱点
- 结论：通常「以一份为主干 + 吸收另一份的亮点」合并，不是二选一
- 评判要诚实标出「两份都没给死的」待定项（如具体公式/行业差异），推给老板定
- **用户要「一份文档」= 六层整合成一份完整文档，不是拆六份**（2026-08-14 实测）：老板看 PRD 说「总共不是有好多个内容，业务背景描述那些」→ 引导到六层完整方案 → 拍板「搞成一份文档」——业务描述→条件→流程→架构→归因→PRD 六层全在一份里（一份「完整方案与 PRD」文档）。第五层归因用收敛终稿口径、第六层 PRD 全文纳入（不重写），前置四层从 codex+claude 双方案融合。输出示例：`星广归因系统_六层完整版_20260814.md`（1681 行六层齐全）。
- **双方案必须真融合，用户会问「他们各一份的你融合了吗」**（2026-08-14）：合并 prompt 明确写「从 codex 方案与 claude 方案提取合并（取更完整表述、删重复、OQ 表合并去重、架构层两版合并）」，不是只取一份；出完先核融合证据（OQ 表/架构模块是否双版痕迹）再交付。

## 四、审核者的判断分析能力（Hermes 自己的）

审核执行器产出时，用这些框架（否则审不出深度）：
- **五智囊对抗**：反驳者（最可能怎么死）/ 本质追问者（哪个假设没验证）/ 机会发现者（漏了什么）/ 外行人（不懂的人怎么问）/ 无情执行者（明早第一步）
- **六顶帽子**：白（事实齐不齐）/ 黄（价值面）/ 绿（机会列全没）/ 红（直觉说透没）/ 黑（风险）/ 蓝（流程）
- **第一性原理**：回到本质——这个方案根子上要解决什么问题？（例：归因系统本质=收入=消耗×分成，所以消耗量是第一指标）
- 见 `decision-framework` / `multi-agent-consensus` 等 skill 的完整框架

## 踩坑（实测）

- **用户问可行性/方案探讨 ≠ 授权动手**（2026-08-14 被纠正）：用户问「直接搞个代理就行了把？」是**在问可行性**，我直接上手搭了代理，用户纠正「我没说让你搭代理，我是在问你」。下任务前先确认意图：问句先答结论（可行/不可行+为什么），等明确「搞/跑/做」再动手；已有动作先说明「已顺手搭了，不要可撤」让用户定。
- **没定角色** → 执行器默认开发者/执行器视角，方案偏技术丢业务（本会话最大教训）
- **文档顺序乱** → 前面没定就写后面，全链路返工
- **Hermes 自己干活**（没外包）→ 违反 SOUL 铁律 11，产出作废
- **用户给出风格/语气/角度修改要求 → 必须重新派 codex，禁止 Hermes 自己重写（2026-09-07 用户纠正「让codex写」）**：codex 产出一篇文章后，用户说「写成以你的角度去理解的政策解读，就好像跟身边的朋友大白话解释的那种」——这是风格修改要求，Hermes 必须重新打包 task_brief（含用户原话）→ 派 codex 重写。但 Hermes 自己动手写了一版「大白话解读」，用户随后纠正「让codex写」。教训：①即使用户只说风格要求没说执行器，也要默认走 codex ②即使 Hermes 觉得「我也能写这个」，也必须外包 ③用户的风格反馈 = 新的任务书输入，不是给 Hermes 的创作指令 ④这条与「codex-bridge 边界：Hermes 不自己分析/创作内容」是同一条规则的不同表现——codex-bridge 是 user-owned 无法 patch，本 skill（curator-managed）承载同一纪律
- **评判没框架** → 审不出执行器的真问题，只会说「都挺好」
- **执行器产出有「我建议/统一标准/最终裁决」这类结论时**——那是执行器以角色身份给的判断，不是老板定的也不是 Hermes 定的；审核时要明确这个边界，老板有不同意见直接让它改
- **把「禁止 Hermes 直出」当「Hermes 身份痕迹」删了**（2026-08-14 被用户三次纠正）→「调 codex/claude 产出、禁止 Hermes 直出」（= 动脑活必须调执行器，禁主对话模型直接产出）是**通用质量铁律**，default 和 customer 两个 profile 都遵守，**不是「Hermes 这个 agent 的身份」**。当老板说「让两个 AI 独立、各自重新出 soul 方案」时，指的是**身份/关系独立**（各有各的灵魂文件、是谁/对谁/称呼/职责边界），**不是**去删对方 SOUL 里的工作规则。给别的 profile 重构 SOUL 时：工作规则/铁律/工作流/安全规则/权限配额**一个字不能动**，只改身份定位那一小块。拿不准时默认只动身份，不碰工作方式。

- **只转述不审核 → 用户提醒「你不审核吗」**（2026-08-14 实测）：双执行器收敛完、终稿出来后，Hermes 不能直接把结果转述给老板拍板。要**先自己读产出、用六顶帽子/第一性原理审命门**（P0/安全/核心逻辑），给「通过+前置条件」类审核结论再交老板裁决。本会话 PRD 终稿后用户一句「你不审核吗」点醒——审核是 Hermes 的职责，不是可选步骤。审核时逐块核命门（审批防伪造/归因口径/证据等级/回流链），黑帽列前置条件，再交拍板。
- **Hermes 自己的故障/根因判断也要交执行器独立 RCA**（2026-08-16 用户「你确定是这个原因吗？让 codex 分析」）：排查故障后 Hermes 给出根因结论（如小鹿 DB 反复损坏=OOM→SIGKILL→SQLite 非正常关闭→修复时没等旧进程退出），**用户会质疑这个判断**——正确做法是主动打包全部证据（日志时间线/文件系统/进程状态）给执行器做独立 RCA，prompt 明令「不接受预设结论、独立判断、可以推翻任何现有结论、证据优先、查不到就说查不到」。Hermes 的排查结论是「假设」，不是「定论」；尤其涉及多环节因果链时（资源→进程死亡→DB 损坏→修复加重），自己容易只看到自己参与的那一环。故障修复告一段落后主动问「要我让执行器独立验证根因吗」，而不是等用户质疑。
- **「读过了」≠「审过了」——执行器声称的技术事实必须独立核验再转述**（2026-08-16 被用户追问「这个方案你审过了吗？你是怎么审的？」，当场承认只做了通读+印象审）：审核架构/方案类产出时，Claude/codex 自报的事实性声称（如「workflow_gate.py approve 已可用」「confirm_gate 确认点是 node4/node8/node12」「1889 状态在 /tmp」）**不能直接信并转述给老板**——要亲自跑命令验证（`grep` 源码、`python3 xxx.py` 试跑、`ls` 确认文件），再决定是否转述。审核四件套：①**独立核验**技术声称（跑命令，不信自证）②**交叉验证**（另一执行器独立评同一产出，两边对照）③**六顶帽子终审**（白帽事实/黑帽风险逐顶过）④**忠实度检查**（需求原文 vs 产出逐条比对，找出跑偏/擅自加需求）。只做「读+印象」就汇报 = 审核失职；用户追问「怎么审的」时若答不出验证动作，就是没审。
- **架构审核两轮制：Hermes 四件套还不够，必须加「实现方对抗评审」**（2026-08-16 血泪，用户原话「你先把整个细节审核完，再去做，不然你做了也是白做」）：本会话 Claude 出 593 行架构，我跑完四件套（声称核验全过 + codex 独立评审 + 忠实度 11 条全过）就准备让 codex 实现——结果用户自己抓出 403/404 语义错误，codex 的「可落地性评审」又挖出 **8 个 P0 契约级硬伤**（approve 无 cycle/piece 参数、confirm_gate 只有项目级布尔、D_* 无导出器「前端永不读 A_*」无法成立、produced_by_codex 接受 claude 契约撒谎、MOCK 与交付自相矛盾、O1 approve 可绕过自动检查、注册表产物不分内容分支、persona pending 阻断票据链）。**四件套验证的是「声称是否为真」，抓不到「契约语义是否成立」**——只有实现方知道代码里什么真能跑。正确流程：①Hermes 四件套（核声称）→ ②**实现方（codex）从可落地性角度独立评架构**（会抓到 architect 漏的硬伤）→ ③两边对照 → ④架构 owner 修订 → ⑤逐条核验修订版 → ⑥才让实现方写代码。中途发现架构有错必须 kill 在跑实现（按错架构写 = 返工），先修契约再做 UI。评审要分「产品/UI 验收（可 mock fixture）」与「业务链验收（禁 MOCK，真实成片/真实门禁/真实付费）」两轨，不许用演示骗自己。
- **穷尽式三方审核（2026-08-16 用户要求「把所有可能发生的问题都审核一遍」）：** 架构/系统设计审核要「一次审全」，不能零敲碎打（用户先抓 403，又抓「403 应该有一堆吧」，最后明令「先把所有可能发生的问题都审核一遍」）。三轮并行结构：①**Claude 自审**（架构 owner 批判自己：契约一致性/状态码语义/需求覆盖/自相矛盾/边界异常/数据一致性/体验/未来扩展 8 维——prompt 明令「找得比谁都全，承认疏漏不辩解」）②**codex 补漏扫描**（实现方在已有评审上深挖新维度：业务运营层/需求表单行业差异/内容生产质量/客户心理信任/财务成本退款/性能边界/日常运维/集成依赖——会挖出 architect 完全没想到的运营/商业/信任层问题）③**Hermes 合并去重**成完整问题总清单（P0/P1/P2 分级）→ 交架构 owner 统一修订。codex 补漏尤其抓「真实客户一进来就争议/亏损」类：商业订单收款缺失、事实冻结缺失、行业表单一刀切（美容≠医美）、静默确认知情同意、重任务准入控制、provider 成功但交付失败等。审核输出要含「上线前总门槛」清单（任一项不满足不开放真实客户）——这是把审核从技术正确性提升到商业可持续性的关键。
- **API 语义：隐藏资源存在性用 404 不是 403**（2026-08-16 用户抓出架构错误）：客户选了「不展示过程」后产出物对他应「不存在」——返回 403 泄露「资源存在只是不给看」，404 才彻底隐藏（防枚举）。通用原则：越权/隐藏场景一律 404 防枚举，403 只用于「资源存在但身份权限不足且可公开知道存在」。架构内部自相矛盾（§9.1 说越权要 404，§7.1 同接口却写 403）是审核重点——**同文档内部前后矛盾 = 细节没审透的信号**。⚠️ **用户点醒「403 那个错误应该有好多条吧」→ 发现一类语义错误时，必须系统性扫描同类场景**，不是只改用户抓到的那一处：把「资源存在但不该给看」的所有场景（隐藏模式/越权/已删除/已过期/不存在）全列出来，统一修正为 404（或 410 Gone），并建立「客户侧资源存在性不泄露」的通用审核项。
- **审「过度设计」：文档复杂度必须匹配系统真实复杂度**（2026-08-15 被用户点醒「你怎么审查的，看看你的SOUL。如果只做物料消耗的归因，你那些什么架构什么的都没必要定吧」）：老板拍板把范围缩小后（如「只做物料制作及消耗归因」），必须回头用第一性原理评估——这个系统到底多复杂？之前双执行器按大系统写的架构/门禁/身份链/AC 大表/P0 五阶段可能**全是过度设计**。审查顺序：先定系统真实复杂度（第一性原理：解决什么问题、多简单）→ 再判断文档是否匹配 → 过度就砍到核心（数据→归因→Top25%→行业→输出→边界，如 129 行极简归因逻辑）。机械查「口径落实/章节齐全」不等于审到位——审的是「这套东西该不该存在」。
- **复盘/分析类任务同样防过度设计：有多少数据分析多少，不给数据不碰结论**（2026-08-15 用户纠正「我的意思是，其实你这个数据复盘的东西，你可以跟火山的那个合并……客户给了多少数据，你就分析多少」）：做客户复盘/数据分析时，**不要设计「分级降级表/多档位报告系统」**——用户明确反对「分版本」（原话「不是四套报告，是同一套复盘，客户给什么字段就分析到什么位置」）。客户只给播放/完播 → 只做内容诊断；给到线索 → 加线索分析；给到成交 → 加订单归因。不催客户补齐数据才复盘，缺字段标【数据不足】或整块不显示，**不设假阈值、不做假深度**。设计复盘工具时先问「客户真的会给这些数据吗？拿不到就别建这个模块」——很多客户没时间整理报告，只甩你平台后台数据。复盘口径从简，指标随数据伸缩（详见 content-data-review 的按数据量自适应复盘；该 skill 为 user-owned，改动需 adopt）。
- **prompt 只写「产出写文件 xxx」→ 执行器可能只输出内容不落盘**（2026-08-14 PRD 对质实测：codex/claude 双双跑偏，exit 0 但没写文件，只打印了 PRD 片段）。修复：prompt 里写死「[产出] 用 write_file 写文件（不要只打印内容）：<绝对路径>；不写文件 = 任务失败」，并让第一步就读必读材料、最后 echo OUTPUT 标记。重派即可，不用改内容。
- **prompt 文件别放 /tmp**——升级/变配/重启会清空 /tmp（实测升级内存后 prompt 全丢）。放持久目录：`/home/ubuntu/workflow/prompts/` 或项目目录下。
- **重任务并行度按内存判断，别固守串行老规矩**：2GB 时 codex/claude 必须 flock 串行（防 OOM）；升到 4GB 后可并行（实测：系统+网关≈900MB、每重任务≈450MB，4 个并行 OK、5 个危险）。派任务前先 `free -h` 看内存决定并行度。
- **模糊确认 ≠ 授权停杀，只杀用户点名的执行器任务**（2026-08-14 血泪，用户质问「谁让你停归因的」）：用户说「好 停」这类简短回复是**确认汇报/收尾**（如确认妲己任务已停），不是授权杀清单外的在跑进程。停任何任务前必须确认**用户点名的具体目标**；自己汇报时**不要抛「要停说一声」钩子**（会诱导含糊应答再被过度解读）。杀错在跑任务 = 产出没落盘 + API 额度已烧 + 重启重跑。正确姿势：只处理用户点名的那一个；含糊时反问「确认停 X？还是只确认 Y 那边？」。
- **停任务前先查进程再动手**（2026-08-14）：用户说「把 X 停了」时，先 `ps aux | grep` 确认 X 是否真在跑、X 是谁（可能只是 prompt 文件没启动，可能任务名与用户记忆不符），再决定动作。本会话「写妲己任务」只有 prompt.txt 无进程，用户说停 → 标记取消即可；但「好 停」被误读成停归因互评 → 误杀两个在跑执行器。
- **执行器产物自标执行者 ≠ 实际执行者**（2026-08-15 实测，T-OPS 复盘示例）：codex 写文档时文件头标了 `> 执行者：claude`——它**沿用了 prompt 模板里的模板行没改成自己**。审核时不要信执行器自报的执行者标注，要核对**实际是谁跑的**（process 记录/后台会话），不一致就 patch 修正。prompt 模板行写死 `> 执行者：codex` 时执行器会照抄；但换 claude 模板跑 codex（或反过来）就会抄错——**模板行留占位或审核时必查实际调用方**。
- **codex 高 effort 长文档任务耗时预期**（2026-08-15 实测）：重写 400+ 行文档（如复盘示例四档自适应版）要 **600-900 秒**，属正常不是卡死；用户问「好了没」时如实报进度即可，不要中途反复 poll 或杀掉重派（已付额度跑完为止，不满意再重派 codex）。
- **并行派活先查覆盖重叠——三个重叠任务=三倍时间三份钱**（2026-08-23 xiaolu-bug-sweep 实测）：同一项目同一批修复，先后派了 sg-fix-rework（新加坡 R1-R7 返工）、sg-gz-fix（广州 G1-G7 修复）、sg-unified-fix（综合分析两边自己改）——第三个任务书范围天然覆盖前两个（写着「新加坡返工项 + 广州修复项」），等于同一批活在并行做三遍，每个都跑 ~50 分钟，用户催「这么慢」。教训：**同项目多任务派活前，先列每份任务书覆盖范围，有覆盖关系就只派最全的那份**（或被覆盖的直接砍掉），并行只留给真正不重叠的工作流；已派出去的重叠任务按纪律不杀，等全跑完用覆盖最全的做主干、其余当交叉验证。
- **慢任务诊断：wrapper 日志只有「开始」≠卡死，查 staging 产出时间戳**（2026-08-23 实测）：claude-wrapper 的日志开头只有一行「[claude-wrapper] 开始 region=us-east-1」是**正常的**——claude 实际输出写在 /tmp/claude_remote_output/claude_remote_*.log，产物直接写项目 staging 目录，wrapper 只在结束时才落日志。用户喊慢时正确诊断链：①`process action=list` 看哪些在跑、跑了多久 ②`find <staging> -type f -newermt "<启动时间>" -printf "%T@ %p" | sort -rn | head` 看有没有**刚刚**写入的文件（有=在干活，没有=可能真卡）③`ps` 看 claude 进程 CPU 2-5% 在读写文件=正常干活 ④已提交任务绝不杀，如实报进度+预计剩余，不催不杀。跑完收文件时：`tail` 派发日志找 `OUTPUT:` 行、核对产物目录结构（MANIFEST/REPAIR/diff/TEST_RESULT 齐全）、注意 wrapper 可能 WARN「未找到可证明的产物路径，跳过 attestation」——产物存在但 wrapper 没验到，不影响产物有效性。**CPU 增量法（2026-08-23 G07 验收实测，比 ps 瞬时 %CPU 可靠）**：`cat /proc/<pid>/stat | awk '{print $14+$15}'` 隔 5 秒对比，utime+stime 明显增长（如 2633→2650）= 在持续推理；同时 `ls -lt /proc/<pid>/fd` 看 fd 时间戳有更新 = 在读写。claude -p 模式是「干完活一次性落盘输出」，中间日志空是正常形态，不是卡死。
- **打包完不做机械预检：codex 自审即闸（2026-08-23 用户「让他自己检查」实测）**：codex 打包完任务书后，Hermes 想跑「标记格式/判断词/attest 预检清单」再派下一环——用户一句「让他自己检查」叫停。纪律：打包流程本身带 attest 自审（codex 自检标记格式、判断词、触发词、结构），Hermes 的机械预检是重复劳动。打包完只核对三样：产物文件存在、attest 记录在、结论行 PASS/FAIL；合格直接派下一环，不合格丢回 codex 自己改。用户要的是「让执行器自己检查」，不是 Hermes 再设一道人工闸。
- **验收 FAIL 数量 ≠ 改动量：先按根因归并再报范围（2026-08-23 G07 F01-F06 实测）**：claude 验收 FAIL_COUNT=6，用户追问「为什么改动要这么大」——实际 6 条里有同根因（F01/F02 是一个 git apply cwd bug 的两个表现）、有补测试非改逻辑（F06 实现全对只缺回归护栏）、核心逻辑零改动。报改动量前先归并三件事：①同根因合并（几条 FAIL 一个根因 = 一处修复）②区分「改逻辑」vs「补护栏/测试」③明确核心零改动。给用户的改动量表按「问题/根因/实际改动/危险等级」组织，让用户看到真实改动面远小于 FAIL 数——否则用户以为要动一大堆，实际只改部署脚本几行。
- **派活后立即回客服位，禁蹲守进度（2026-08-31/09-03/09-06 用户多次纠正「说了多少次了」）**：用 terminal background=true + notify=true 派给 codex 后，立即回客服位，不 poll/wait 盯进度。蹲守浪费 token 还会被用户骂「你在干嘛」「说了多少次了」。notify=true 会在跑完时自动通知，收到通知再处理结果。用户主动问「跑到哪了」时可以 poll 一次看状态——但不要连环 poll/wait。**0906 再次纠正**：即使是很小的改动（箭头 y 值移 80px），也要写任务书丢 codex 跑全链路（sed→render→抽帧验证→发飞书），不要自己在 terminal 里一步步跑 sed→bash→ffmpeg→vision_analyze→hermes send——那等于自己当执行器，违背派活纪律。正确：写清改什么参数丢 codex exec 跑，回客服位等通知。
- **🔴 派活后零工具调用——notify=true 后直接返回（2026-09-06/09-08 屡教不改）**：dispatch 后用 `process action=wait`/`process action=poll` 是蹲守；用 `ls`/`ps aux`/`sleep`/`file`/`stat` 查输出文件、用 `vision_analyze` 看图好了没——**同样是蹲守**，只是换了个壳。物理闸只拦 `process poll`，readonly 命令和 vision_analyze 全绕过（见 agent-framework-layer 坑 54）。**notify=true 的机制是：进程退出后系统自动推送通知到对话里——收到通知才处理，在收到通知前零工具调用**。用户说「物理闸失效了吗」「为什么屡教不改 物理闸也挡不住你」= 又在蹲守。**唯一例外**：用户主动问「好了没」时，可以 poll 一次报状态，报完立即回客服位，不连环 poll。闸拦得住工具拦不住习惯——根治靠行为层自觉：后台 notify=true → 返回 → 闭嘴等通知。
- **Hermes 自己跑长任务要分段汇报、可打断，别闷头 tool 循环**（2026-08-16 用户「为什么小天天喊停没用，自顾自的做事」「直接不回复我了」纠正）：agent 进入连续 tool 循环后，用户消息在 turn 队列里排队，**当前循环跑完才响应打断**——实测小鹿数据恢复（压缩/传输/分块/COS 中转）连续 tool 循环 8 分钟零回复，用户喊停没反应、看起来「直接不回复」。纪律：①长任务（>2-3 分钟连续 tool 调用）先报计划 ②tool 循环**分段**，每段结束主动给用户进度/可打断点（别连续 N 个 tool 调用不落一句回复）③用户喊「停」→ 对话回复立即停；**后台进程（codex/claude）不自动杀**，要显式说「停掉 XX 任务」才 kill ④与「先干完再汇报」的关系：普通任务（几分钟内）干完一次性汇报，长任务必须分段——这是「先干完再汇报」的例外。排查「喊停没用」先分两类：对话 turn 挂了（存储故障，见 hermes-storage-health） vs 长任务不响应打断（本条目）。**物理保障（2026-08-16 已落地）**：`hermes config set tool_loop_guardrails.hard_stop_enabled true`——tool 循环无进展/死循环会硬停（默认 false 只警告不硬停）；长任务跑之前先确认这个配置是 true。长任务**一律后台化**（terminal background + notify_on_complete），不在对话 turn 里连续跑 tool 循环——对话 turn 只负责派任务+等通知，用户消息能及时响应。

## 架构修订版必须带「实测基线表 + CR 治理」（2026-08-16 架构 v2.0 定案）

审核发现一堆 P0 后让架构 owner 修订，**修订版怎么保证不再犯同样的错**？v2.0 给了两个可复用机制，审核修订版时重点查这两样：

1. **§1 存量能力实测基线表（M/U 表）**：全文引用任何存量能力（脚本/配置/文件）必须能回指到表里一行；表分「M1-M16 已实测（附实测命令 + 实际输出）」和「U1-U9 待实测（标注谁测、为什么先测）」。表里没有的存量引用 = 不得作为架构承重。**这是「接口签名不是能力」的物理形式**——v1.0 的根因就是「把接口签名当能力，凡沿用存量处都没实测」（如：`check` 有 `--cycle/--piece` 参数 ≠ 系统支持多内容；`TICKET_TTL_SECONDS` 存在 ≠ TTL 生效；`AUTO_PUBLISH_ENABLED` 是常量 ≠ `PAID_API_ENABLED` 也是）。**审核修订版时：抽查 M 表 3-5 条声称，亲自跑命令验证**（本会话抽查 M3/M5/M10/M13/M14 全属实——这次可信了）。同时注意 M 表会纠正前序报告的数字错误（如「13 个 implemented:false 门」实测是「13 个检查项分布在 12 个门」）。

2. **每条 CR 必须带 owner + 批准人 + 终审人 + 降级路径**：v1.0 的 CR-1 没有 owner 导致需求 5 无人可落地；且「禁 codex 改注册表」又「要求 CR 改注册表」自相矛盾。v2.0 改为：每条契约变更（CR）都写明「owner（改的人）/ 批准人（老板）/ 终审人（独立第三方，不得是 owner）」，并给**「若不批的降级路径」**（如授权链平台层断言兜底、SQLite 侧作废 decision）。**无降级路径的 CR 是硬依赖，老板不批则首版不能开工**——审核时把「必须老板优先拍的三条 CR」单独列出来交给老板，别埋在长清单里。

3. **架构修订的纪律固化**（v2.0 §18，可直接抄）：①接口签名不是能力，凡「沿用存量」必附实测命令与输出 ②禁令要禁语义不禁命令名（禁了 `confirm_gate.py skip` 命令，客户一句「直接来吧」同样触发 skip_mode——禁令写在命令层一定能绕过）③门禁可信度必须实测不能引用（实测 12 门全未实现/1 门只扫第一个文件/2 个引用脚本不存在/approve 可无条件放行）④架构里每条依赖都必须有 owner。

4. **修订通过后、写页面之前：先派「失败测试」冻结契约**（2026-08-16 架构 v2.0 → P0-A 落地实测）：架构修订版审过 ≠ 可以写实现。标准工序是**阶段一先写失败测试组（13 条全红是预期，红 = 存量代码按新契约必然失败 = 契约冻结的验收物）→ 阶段二契约冻结（一项目一 piece、CLIENT_VIEW_CATALOG、行业 schema、OpenAPI、SQLite DDL、不变量断言点）→ 阶段三才写页面**。派失败测试任务的 prompt 纪律：①**不许 mock 被测对象**（mock 门禁 = 自欺，必须真实子进程/真实 SQLite/真实路由）②每个测试失败要打印**真实失败原因**（不许吞）③不改被测脚本，只写测试和报告 ④结果表每条对应架构验收项编号（D/B/T/M）⑤「测试全红」明说是预期，避免执行器以为任务失败去「修好」它。**任务内部约束冲突时执行器会选最保守的跳过另一项**（实测：prompt 同时写「只写测试不改脚本」+「归并 .hermes」，codex 跳过归并——审核结果时发现缺口，单独重派归并任务，不责怪执行器，是 prompt 自身冲突）。

## 客户确认节点设计原则（2026-08-16 天行者定案，给「客户用」的工作流平台）

给**完全不懂运营的客户**（如实体店老板）设计可视化工作流平台的确认节点时，用户拍板的原则（星广客户运营工作流可视化平台需求讨论实录）：

1. **客户是「输入需求→拿结果」的盒子**：要做的就是填需求（店名/行业/城市/卖点/素材）→ 最终拿成品。中间大部分节点他不需要参与。
2. **但关键内容产出必须给他看并确认**：文案做完、成片做完 → 发给他 → 两个按钮「[没意见，继续] / [我要修改]」——**软确认**：客户不提意见默认自动往下走，提意见才返回修改。别设计成「必须点确认才继续」的硬门（会卡流程）。
3. **专业展示默认开、可关闭**：策略/方案类产出（诊断报告/洞察/选题方案）展示给客户看——既是确认依据也是**运营专业感的展示**（「显得你很专业」）；页面提示「可选择不展示」，客户可关掉只看进度+结果。
4. **付费环节不设客户确认**：客户确认文案/内容后直接出片，**不要把「付费」这个内部成本问题抛给客户**——付费确认点是后台的事。
5. **交付后要提醒客户后续操作**：交付包之外给「整套打法 + 数据复盘怎么操作」的引导（发出去后 1/3/7 天看什么数据、什么算有效、需要时找我们复盘）——专业感延续，不是交付完撒手。
6. **飞书只是过渡壳**：没有网页/小程序前的临时入口；平台做好后客户直接网页/小程序操作，飞书退居内部工具。架构不要跟飞书耦合。
7. 判定三类：**客户确认（软确认）** / **客户可见不用确认（展示专业）** / **客户不可见（纯后台）**——逐节点判定时先问「客户能看懂并判断这个吗？看不懂就不该让他确认」。

## 跟踪 delegate_task 结果（2026-08-28 实测）

用户问「好了没」「这个好了没」时，**主动查 delegation 缓存**，不要只查 process list 和 session_search：

```bash
# 1. 查所有 delegation manifest（含完成状态和时间）
ls ~/.hermes/cache/delegation/live/deleg_*/manifest.json
# 2. 读 manifest 看 status=completed/running + started/completed 时间
cat ~/.hermes/cache/delegation/live/deleg_*/manifest.json
# 3. 读 task log 看完整执行过程和最终产出
#    log 文件是 append-only transcript，含每步 tool 调用和 final 摘要
```

**关键路径**：`~/.hermes/cache/delegation/live/deleg_<id>/`
- `manifest.json` — 任务 ID、状态（completed/running）、起止时间
- `task-0.log` — 完整执行 transcript（逐行 tool 调用 + result + think + final）

**坑**：`process action=list` 只显示后台 terminal 进程，**不显示 delegate_task 子 agent**（它们是独立会话不是 terminal 进程）。session_search 也可能搜不到（子 agent 会话不一定在主 session DB 里）。delegation 缓存目录是唯一可靠入口。

**坑**：delegate_task 子 agent 可能超出任务范围。任务书写「分析...给出方案」但子 agent 可能直接改了代码/写了文件（2026-08-28 飞书 session 分析任务：子 agent 不光出了方案还直接 patch 了 session.py 5 处 + 写了 SQL 清理脚本 + 写了分析报告）。收到结果后必须：
1. 读 task log 看子 agent 实际做了什么（不只看 manifest 的 status）
2. 如果子 agent 改了代码，核验改动是否合理（patch diff / write_file 路径）
3. 提醒用户哪些改动需要重启/部署才生效
