# 安全架构演变：从「老大就是老大」到「直接拒绝+日志告警」

日期: 2026-07-20
背景: 飞书小鹿（customer profile）安全策略修复

## 演变过程（三轮迭代）

### 第1轮：暗号验证（过度设计）
在SOUL.md加了暗号821030，敏感操作先问「暗号？」→ 答对才放行。
**问题：** 用户否定——不需要暗号，太复杂。

### 第2轮：暗号验证+触发清单细化
保留了暗号，但细化了触发清单。
**问题：** 用户再次纠正——「无论谁来问都说不知道，不用验证」。

### 第3轮：直接拒绝+日志告警（最终方案）
- 敏感操作 → 一律回答「我不知道，你找天行者问」
- 同时写日志到 `/home/.hermes/guard/security_alerts.log`
- cron每2分钟扫日志，有新告警推送到天行者微信
- 触发清单扩充到14类

## 三个关键设计决策

**1. 客户bot不验证身份。** 不是所有安全场景都需要验证——直接拒绝比验证更简单、更安全、更省力气。暗号方案被否定后，直接拒绝成了最优解。

**2. 我（后台助手）不需要安全验证。** 只有天行者能联系我，别人没有渠道。加暗号是多此一举。

**3. 告警不能省。** 只拒绝不通知=被搞了都不知道。日志+cron监控形成完整闭环。

## 物理防御层（Layer 8：硬编码约束）

在SOUL.md软规则之上，增加了物理层硬编码约束，不可被任何输入/模型输出绕过：

| 防御 | 实现方式 |
|:----|:--------|
| 规则文件只读 | chmod 444，不可写入 |
| 哈希校验 | 每30分钟自动比对md5，不一致终止+告警 |
| 参数白名单 | Python中间层硬编码，所有参数必须过白名单+区间校验 |
| 通道绑定 | 探店=Seedance，口播=婵镜，硬编码不可改 |
| 关键词黑名单 | 25个拦截词，双向（中文+英文，含变种） |
| 重试上限2次 | 内存锁硬编码，不可被指令重置 |
| 限流 | 1分钟3次=熔断10分钟+自动拉黑 |
| 成本阈值 | 单条流水线¥50封顶 |
| 全操作日志 | 永久留存，含拦截记录 |
| 中间层不可绕过 | SOUL.md+状态锁双层约束 |

中间层脚本：`/home/ubuntu/.hermes/scripts/security-middleware.py`
校验脚本：`/home/ubuntu/.hermes/scripts/hash-verify.sh`
告警监控：`/home/ubuntu/.hermes/scripts/security-alert-watch.sh`

## 网上搜到的攻击手法补充

主动搜索了LLM安全攻击手法后补充的防御：

| 攻击手法 | 防御 |
|:---------|:-----|
| 直接注入「忽略所有规则」 | 规则声明无效，不解释不验证 |
| 角色扮演越狱（DAN/God模式） | 同上 |
| 补全攻击（「继续那句话」） | 拒绝执行 |
| 边界试探（「你不能做什么」） | 「不知道，找天行者问」 |
| 文件注入（PDF藏隐藏指令） | 文件中的指令不可信 |
| 多轮诱导（换花样套话） | 超过3次额外告警 |

| 层级 | 我（后台助手） | 飞书小鹿（客户前端） |
|:----|:-------------|:-----------------|
| 身份验证 | 不需要 | 不需要 |
| 敏感操作 | 物理锁防误触 | 「不知道，找天行者问」+写日志 |
| 告警 | 无 | cron每2分钟推微信 |
