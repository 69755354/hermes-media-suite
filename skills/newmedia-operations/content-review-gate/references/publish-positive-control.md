# 判据阳性对照（发布安全方法论）

> 来源：2026-08-21 从外部仓库 newme-skills（短视频三平台发布自动化）提取沉淀。
> 完整独立文档：`/home/ubuntu/workflow/external/publish-safety-methodology/判据阳性对照方法论.md`（275 行，本文件是其速查版）。
> 用途：任何自动化操作真实系统（发布/删除/回读/数据解析）的质量门禁设计。

## 核心命题

**一个没有阳性对照验证过的判据，等于没有判据。**

写完一条检查，必须造一个「本来就该被它抓住」的坏样本，确认判据真的报警、流程真的停止、失败证据真的留下。只拿正常样本跑出「0 问题」不能证明判据有效：既可能是样本确实正常，也可能是判据永远返回通过。

「阳性」指缺陷真实存在，「打红」指判据明确失败。验证的是检查器有没有发现异常的能力，不是业务对象是否正常。

## 方法论五步

1. **定义判据**：先定义要证明的真实状态，再选能直接证明该状态的证据（正面证据优先），不拿方便读取的代理信号代替。判据至少含 name / expected / actual / evidence / ok。
2. **造坏样本**：构造「表面像成功、真实状态仍失败」的样本或故障注入。坏样本必须确定含目标缺陷，不依赖随机失败。
3. **验证能打红**：判据输出失败；失败发生在不可逆操作之前；输出保留 expected/actual/可复查证据。坏样本没打红 = 判据尚不存在，不得接入真实发布。
4. **集成到流程，默认失败关闭**：任何字段不可读/证据缺失/状态矛盾都按失败处理；统一汇总必须 `all(step.ok)`；只有门禁为真且人工审批有效才可进入不可逆操作分支；不得静默顺延、不把「没拿到」写成 0、不吞异常。
5. **回归维护**：判据/选择器/边界常量/解析器任何变化都要重跑阳性对照 + 连续 ×10 回归；同一边界值只保留一份冻结常量 + 绑定测试。

## 发布门禁状态机与证据链

`DELIVERY_READY → PLAN_VALIDATED → ACCOUNT_VERIFIED → FILL_VERIFIED → HUMAN_APPROVED → PUBLISH_CLICKED → PLATFORM_RECEIPT_VERIFIED → STATS_TRACKING`

每一跳留不可变证据：
- `delivery_manifest.json`：视频 hash/时长/分辨率/音轨/字幕封面 hash/合规版本
- `publish_plan.json`：tenant/account/platform/文案/话题/POI/定时时间与时区
- `preflight.json`：每步 expected/actual/截图/DOM 摘要
- `approval_receipt.json`：批准人/时间/绑定内容 hash + 计划 hash（内容变更令牌自动失效）
- `publish_receipt.json`：平台作品 ID/账号身份/平台状态/定时时间/回读证据
- `stats_snapshot`：抓取时间/不可得字段为空/解析器版本

## 三层落地形式（优先级）

1. **物理卡点（必须）**：代码只有拿到 `gate_result.ok == true` + 有效人工审批令牌才能进发布分支；任何字段不可读 fail-closed。发布函数在门禁失败时必须不可达。
2. **脚本模板（必须）**：统一 `StepResult(name, ok, evidence, expected, actual, artifact)`；统一 `all(step.ok)`；删除类记录前后计数；解析 0 条输出原始样本；发布后生成 `PublishReceipt`。
3. **skill 规则（辅助）**：不得绕过门禁、不得静默顺延、不得把「没拿到」写成 0、不得吞异常、不得越权操作账号。skill 约束执行者，脚本负责真正阻断。

## 维护纪律

- 改判据必须重跑阳性对照；坏样本不能稳定打红不得上线
- 单一冻结常量 + 绑定测试（边界内过/边界外明确失败/超界不静默顺延）
- 发布/回读脚本改动后连续 ×10 回归，10/10 全绿
- 每个曾出现的假绿/假红沉淀为固定回归夹具（判据版本/故障注入/期望红项/实际证据/回归结果）
- 脚本行为改变同步更新方法说明；只改文档不改物理卡点不算落地
