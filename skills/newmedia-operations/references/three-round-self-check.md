# 三轮自检方法论 — 渠道/工作流适配 + 跨文件一致性

## 用途

为新平台（渠道）适配现有15节点工作流时，执行三轮系统性自检，确保不遗漏、不矛盾、不自欺。
也适用于修改SOUL.md/skills/知识库后的质量复审。

## 触发条件

- 接到新平台适配任务（如：把小红书加进工作流）
- 对已有渠道工作流做质量复审
- 修改SOUL.md/skills/知识库后
- 用户要求「自检三轮」

## 第一轮：平台需求核对

**目标：** 确认你「知道什么」，杜绝凭印象编造。

**动作：**
1. web_search 搜该平台的关键特征（用户画像、内容偏好、推荐算法、合规红线、同城引流方式）
2. web_search 交叉验证（至少搜2个不同来源）
3. 列出平台 vs 当前默认平台（抖音）的核心差异表

**输出：**
```
| 维度 | 抖音（默认） | [新平台] |
|:----|:-----------|:--------|
| 用户画像 | ... | ...（带数据来源） |
| 内容偏好 | ... | ... |
| 合规红线 | ... | ... |
| 同城引流 | ... | ... |
```

**关卡：** 每个特征必须有2个以上独立数据源支撑，不能只有一个来源就下结论。

---

## 第二轮：逐节点适配检查

**目标：** 确认工作流16个节点，每个节点是否适配新平台。

**动作：**
逐节点过一遍，标出三种结果：
- ✅ 直接复用（工具、参数、规则不变）
- ⚠️ 需要微调（同一工具，不同模板/规则/参数）
- ❌ 不适用（该节点对新平台无意义，需跳过或替换）

**特别关注：**
| 节点 | 通常需要改的 | 检查项 |
|:----|:-----------|:------|
| 节点0 | 渠道选择表 | 新平台是否已加入？信息采集内容是否匹配？ |
| 节点3 | 爆款拆解源 | content-hunter 是否支持该平台？不支持则改用 web_search |
| 节点4 | 选题方向 | 选题模板是否匹配平台内容偏好？ |
| 节点5 | 文案风格 | 风格、话术、关键词是否匹配？ |
| 节点6-13 | 视频制作链 | 比例/时长/参数是否需调整？图文模式是否需跳过？ |
| 节点10 | 合规 | 是否有平台专属违禁词？ |
| 节点14 | 交付 | 交付物格式是否不同（视频 vs 图文包）？ |
| 节点16 | 复盘 | 指标是否不同（完播率 vs CES）？ |

**输出：** 改动清单（改哪几个节点、每个改什么）

**关卡：** 不能漏节点。16个节点逐个过，不准跳。

---

## 第三轮：风险点与跨文件一致性检查

**目标：** 检查三个「软性」风险 + 跨文件矛盾。

### 1. 内容一致性
- 节点描述里的规则 ↔ 知识库文档内容 是否一致？
- 例：节点10写了「小红书违禁词7大类」→ 知识库 `xiaohongshu-community-rules.md` 里是否也有同样的7大类？

### 2. 引用完整性
- 工作流节点的「调用文档」是否引用了对应知识库？
- 新增的知识库文档是否被正确引用？
- 路径是否正确（`wiki/concepts/` vs `wiki/strategies/` vs `wiki/references/`）？

### 3. 跨文件矛盾检查（2026-07-16 新增）
逐个验证以下对应关系：

- **SOUL.md 自检**：有无重复规则、安全铁律编号是否连续、有无矛盾
- **SOUL.md vs huoshan SKILL.md**：入口逻辑（"客户说清楚了就不问" vs "先问实体店还是自媒体"）是否一致
- **SOUL.md vs shuziren SKILL.md**：同上
- **工作流引用的所有 wiki 路径**：用 `ls -la` 或 `test -f` 逐一验证文件是否存在

### 4. 遗漏检查
- 有没有平台专属需求但工作流没覆盖的？（如小红书图文需要封面排版，工作流有没有这个步骤？）
- 有没有节点标注了「跳过」但没写清楚的？
- 有没有边缘场景（回头客换平台、多选平台排序）？

**输出：** 修正清单（3-5条）

**关卡：** 修正清单必须全执行完才能说「自检完成」。

---

## 三轮全过后的自检清单

```
□ 第一轮：平台特征核对（2个以上数据源）
□ 第二轮：逐节点适配检查（16节点逐个过）
□ 第三轮：内容一致性 + 引用完整性 + 跨文件矛盾 + 遗漏检查
□ 所有修正清单已执行
□ 文件引用路径全部存在
□ SOUL.md/SKILL.md 无重复/矛盾/跳号
```

---

## 使用铁律

1. **三轮必须全走完，不准跳轮。** 每一轮的输出是下一轮的输入。
2. **每轮结束后必须标注状态**（✅ 通过 / ⚠️ 有遗漏已修正 / ❌ 未通过需重跑）。
3. **修正遗漏后必须重跑受影响轮次**（例：第二轮发现漏了节点 → 修正后第三轮需要重新检查引用完整性）。
4. **三轮全通过后才能交付用户**「某某平台适配完成」。

## 本方法论来源

2026-07-16 小红书渠道适配全流程中定型。小红书适配涉及7个节点改动 + 3份知识库新建，三轮自检共发现3个遗漏点（节点标注缺失、交付话术缺失、复盘指标缺失），三轮后全部修正。

2026-07-16 更新：新增跨文件矛盾检查步骤，三轮全过后的自检清单，以及文件路径验证要求。

### ❌ 常见遗漏（本会话2026-07-17发现）

本轮自检中新发现3类常见遗漏：

1. **行业文档未引用到工作流** — 新建了7份小红书行业文档但节点5的适配表没有引用。检查方法：`grep "xiaohongshu-industry" huoshan/SKILL.md`，确认引用是否存在。
2. **SOUL.md流程未覆盖所有渠道** — 只在小红书流程加了「读行业文档」但抖音/快手/视频号/公众号没加。所有内容产出渠道都必须有读行业文档的步骤。
3. **案例不足** — 行业文档不能只有结构和公式，必须有真实案例和数据支撑

**教训：知识库文档和工作流引用是一对一绑定的，建一份文档就要同步检查一遍引用。**
