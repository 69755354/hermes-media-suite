# 蒸馏能力融合分析模式（2026-08-24 reverse-video-prompt 实录）

## 触发

- 外部/蒸馏获得新 skill 或能力（如 reverse-video-prompt），要分析「怎么跟我们现在有的东西融合」
- 用户给出方向性判断（如「补缺不是替代」），需要执行器把它落成可执行的融合方案
- 新能力涉及多个现有 skill 的交叠（video-remake/video-reproduction/video-reverse-engineering/huoshan/seedance 系）

## 派活姿势（走标准链）

1. Hermes 写传话书（USER_REQ 原话 + DATA_SOURCE + 产出要求一句话）
2. codex 打包 claude 融合分析任务书 + codex 自审（attest）
3. codex 容器无 claude 入口（缺 Bedrock key）→ 宿主机 dispatch 派 claude 执行
4. claude 出融合分析报告 → Hermes 审 → 大白话汇报用户 → 用户拍板 → 分阶段实施

**注意 USER_REQ 引文含「出片」触发 kb_gate（见 task-brief-gate `references/user-req-triggerword-readskill-20260824.md`）**：传话书补 `READ_SKILL=seedance-2-0-mini-workflow` 即过，不改用户原话。

## 报告结构（claude 产出的可复用骨架）

### 分析 A：能力矩阵（对象 × 维度）

- 对象 = 参与对比的 skill/方法论（本次 9 个：蒸馏 SKILL.md / prompt-framework / iteration-workflow / 自有 v4 / video-remake / video-reproduction / video-reverse-engineering / huoshan / seedance 系）
- 维度 = 能力项（本次 23 个：视频源获取/抽帧密度/视觉看图/反推结构/置信度/音频维度/前3秒钩子/产品显著性/出片后对比诊断/差异归因/定向负面/迭代闭环/经验沉淀/像素对照/分镜表/四层结构/台词铁律/声音语速/提交通道/成本记录/门禁绑定/归档索引/外部上传）
- 每格 = 已覆盖 / 缺项 / 与他者重叠 + 证据（来源文件行号）
- 产出：逐对象汇总表（G-A/G-B/G-C 关键缺口）

### 分析 B：五张总表（核心交付）

| 表 | 内容 | 判定依据 |
|:--|:--|:--|
| KEEP 保留表 | 我方能力，不得被蒸馏内容覆盖/改写 | 现有 skill 行号 |
| ADD 补入表 | 蒸馏增量，**切片式**补入指定归属 | 源文件行号 + 目标归属 + 切片边界（禁止整份合入） |
| BRIDGE 接缝表 | 两侧都有但需显式接口才能串成闭环 | 上游/下游/接口约定 |
| CONFLICT 冲突表 | 双侧来源的真实冲突 | 是否阻断闭环 + 建议处置方向（需人裁决的进 U 清单） |
| DEFER 后置表 | 外部上传/第三方推广等整段排除 | 合规/客户素材/授权原因 |

另加 DEDUP 去重表（重叠内容只保留唯一执行源，其余降级为映射/扩展）。

### 分析 C：闭环落位到真实节点

- **先核对真实节点编号与职责**（huoshan 节点 0-17，禁混 Bot 域/API 域编号），`[NEED_INFO]` 的节点不补写、不挂靠
- 用户定案的闭环（如：抽帧+豆包反推 → 出片 → 对比诊断 → 迭代 prompt → 沉淀规则）逐环落位：
  - 现有环 → 挂现有节点
  - 新增动作 → 挂**子节点编号**（如 节点 2.1 / 14.1 / 14.2 / 17.1），不新占主链编号
- 每步 8 项字段：步骤名/节点落位/输入/执行动作/输出产物/判定通过条件/门禁关系/失败回退

### 分析 D：门禁链影响

- 术语先对照（如 G_RENDER = G_RENDER_READY）
- 逐个现有闸评估：新产物会不会被误扫（mtime cap / exclude_path_prefixes）、迭代重跑会不会被人工门卡（迭代轮次 = 人工批准次数）

### 分析 E：分阶段实施（P0-P3）

| 阶段 | 做什么 | 范围边界 |
|:--|:--|:--|
| P0 | 只读对齐 + 冲突裁决（12 条冲突交人拍板） | 零文件改动 |
| P1 | 补 reference 文件 | 只改文档，不改门禁判定 |
| P2 | 闭环流程落位到 huoshan 节点 | 改流程文字，不改闸代码 |
| P3 | 门禁与规格硬化 | 需人批准，最后做，每项单独批 |

阶段间共同约束：实现者≠验收者；付费出片仍走三级人工闸；全过程不整份放入 skills 树。

### 分析 F：风险表 + 待用户选择事项

- 风险 12 类（每条含触发/影响/发现方式/预防/回退/责任位）
- 待用户选择 U1-U13（每项给 A/B/C 选项 + 影响面 + 关联冲突号）——**真实冲突，不是制造选择题**

## 关键纪律（本次实录）

1. **补缺不是替代**：用户方向「咱强的它没有，它强的咱没有，合起来是完整闭环」→ 分析方向 = 保留 + 切片补入，不搞谁覆盖谁
2. **切片合入，拒绝整份覆盖**：蒸馏包自带的 Lark/GitHub 上传 + 第三方引流号（微信号/外部链接）整段 DEFER，不进任何 skill 正文——客户素材外传风险
3. **「一次渲染结果不得直接进入全局规则」**：沉淀分三层准入，第三层必须人批
4. **报告只读不改**：融合分析不改任何 skill/脚本/门禁，只出方案；实施走 P0-P3 分阶段
5. **汇报翻大白话**：1075 行技术报告 → 用户要的是「保留 24 项 / 补进 20 项 / 最要命的 2 个冲突 / 分 4 阶段」这种颗粒度
