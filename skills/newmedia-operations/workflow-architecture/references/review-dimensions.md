# Claude 审查维度框架（2026-08-12 Claude 自述）

来源：天行者问「Claude 做架构时审查维度是哪些」，Claude 自己定义。

## 核心一句话

审的是**状态可达性与真值一致性**；方法是**倒推 + 穷举 + 对抗性假设**；严重度按**不可逆 × 默认路径 × 静默**打分。

## 已用维度（9 类）

| 维度 | 查什么 | 方法 |
|:--|:--|:--|
| 安全 | key 泄漏/SSH 权限/命令注入/凭据暴露 | ps 看 key、authorized_keys 权限、prompt 注入实测 |
| 架构一致性 | 节点/产物/门禁自洽、断链、依赖环 | 读 REGISTRY/SPEC + 拓扑检测 |
| 门禁有效性 | 门禁能不能真拦截 | 穿越测试（touch 空文件/伪造哈希/三步绕过） |
| 引用-加载链 | 纸面引用 vs 实际加载 | grep @skill vs 实际目录/frontmatter |
| 代码质量 | 硬编码/正则漏洞/逻辑错误 | 突变输入、边界值 |
| 状态一致性 | 文件漂移/哈希失效 | 读状态文件对比 |
| 测试可信度 | 测试有没有盲区 | 检查测试是否覆盖绕过路径 |
| 业务 | 交付承诺/人工成本/北极星 | 数据对账 |
| 知识管理 | skills 重复/过时/沉淀机制 | 交叉计数、加载链验证 |

## 未系统用但该用的维度（按收益排序）

1. **突变注入（Mutation Testing）**⭐ 最该加——主动改坏一处（删校验/篡改引用/伪造证据），看门禁/测试能否发现。**唯一能验证「检查本身有效」的方法**，不只验证检查存在。v9 分镜 21 例突变已用过但没沉淀成标准动作
2. **产物生命周期审查**——谁创建/谁是权威版本/谁清理。outputs/ 里 v11/v12/v13 并存是典型症状——没有版本权威性规则，下游会引用错的那份
3. **变更成本地图**——挑 3 个真实需求数「要改几个文件/几处重复」——耦合度实测值，比目测架构可靠
4. **冷启动路径**——新人/新会话零上下文 5 分钟能否跑通一条完整链——直接检验文档与真值一致性，且可执行
5. **演化压力测试**——假设 skills ×3 / 门禁 ×2，哪个环节先崩——判断现有抽象够不够

## 落地建议

把「突变注入」固化为审查标准动作：每次审门禁/校验逻辑，构造破坏性输入（删校验/改坏一处/伪造证据/超边界值）看能否被拦截——验证「检查本身有效」而不只是「检查存在」。
