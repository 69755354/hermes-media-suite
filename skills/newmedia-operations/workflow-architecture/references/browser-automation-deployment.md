# 自动发布执行器部署选型：服务器 vs 桌面机（浏览器自动化）

> 来源：2026-08-21 微信会话「节点13 自动发布环节的适配（NewMe 那套）」。用户问「不是说服务器也可以？跟机器跑有什么利弊」。回答前先查证服务器实际条件（free -h / nproc / ls chromium）+ 复用《短视频自动化适配分析_20260821.md》结论，不脑补。

## 核心判断

NewMe 那套自动发布 = **Playwright 驱动真实 Chrome 浏览器**操作抖音/视频号/小红书网页版（上传、话题、双封面、定时、发布、回读）。它不是平台 API 调用，是「机器替你操作浏览器」。因此**必须跑在一台有真实浏览器的机器上**——但服务器也算机器，不是非得实体电脑。真正的选型问题 = 服务器 vs 桌面机的利弊。

## 服务器（Linux）实际条件（2026-08-21 新加坡机实测）

- 内存 3.6G（可用仅 ~2.2G）、2 核、磁盘剩 ~20G
- 已有 Chromium 1228（`~/.cache/ms-playwright/`）——浏览器环境现成
- 但 NewMe 原版是 8GB Mac 上「单 Chrome 串行」跑的，服务器内存比它小一半多

## 服务器跑：利 vs 弊

**利**
- 7x24 常开，定时任务自己发，不依赖电脑开关机
- 与产线同机：素材/视频生成完直接进发布队列，不用跨机传
- systemd 服务监督，掉线/崩溃能自动拉起

**弊**
- **内存硬伤**：Chrome 无头 + 登录 profile 常驻，与正在跑的 codex/产线抢内存，易 OOM（本机可用仅 2.2G）
- **登录态脆弱**：抖音/视频号对机房 IP 风控更严（非住宅 IP），更易触发验证码/风控
- **扫码麻烦**：视频号要远程出码中转（wx_login_remote 思路），二维码要转到人手上扫，链路长
- **headless 限制**：视频号不可先假定 headless 可用（适配报告原话），可能需虚拟显示，又占内存
- **代码不能原样部署**（适配报告 §七 结论）：三份发布器、登录保活、远程扫码、profile 管理都要 Linux 重写；Mac UA/profile 路径/`$HOME/Movies/...` 全要参数化；`Meta+a`→`Control+a`；`pkill` 只能杀自己 worker 的 cgroup

## 桌面机（Mac/常开电脑）跑：利 vs 弊

**利**
- 8GB Mac 跑过原版全流程，验证过稳定
- 住宅 IP 登录，风控概率低
- 扫码手机直接扫，人工值守顺手
- 不占服务器资源，不影响产线

**弊**
- 要一台常开机，关机/断电发布就停
- 单机单 Chrome，发布任务与其他活抢机器
- 电脑坏了/人不在 = 发布断，无服务监督

## 推荐路径（按适配报告原方案）

1. **先单账号试点**，执行器放一台常开的电脑（Mac 或闲置台式机），服务器只做调度 + 内容生产
2. 试点账号 = 我们长期代运营、有书面授权的**本地生活单账号抖音**（抖音 light DOM 自动化最直接；视频号 26 小时会话 + 远程扫码 + 小红书草稿清理暂不引入）
3. 试点跑稳后再评估是否把执行器挪服务器——**届时先给服务器加内存或上独立小机器**，否则 OOM 风险不可接受

## 回答用户话术（大白话）

「要有一台机器常开跑浏览器，但不是每次都要人手在电脑前点——登录好后定时任务自己发，只有扫码/异常才需要人。」
