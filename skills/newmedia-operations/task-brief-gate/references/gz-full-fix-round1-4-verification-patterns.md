# gz-full-fix round1→round5 验收模式沉淀（2026-08-22）

广州机 execute_api 执行纪律改造，codex 改 → claude 验 → 循环 5 轮的完整教训。
每轮 claude 独立验收（不信 codex 自报），逐项实跑复现。每轮 FAIL 都是真问题：

## 迭代节奏与结论模式

| round | 验收结论 | 问题类型 |
|---|---|---|
| 1 | FAIL：1 P0 + 2 P1 + 4 P2 | 新校验绕过灰度（read_files 含 SKILL.md 绝对路径在 WARN 期就 rc=1）|
| 2 | FAIL：2 P0（新引入）+ 3 P1 + 1 P2 | 正确改动叠加未评估（exit 0→exit $RC 激活白名单硬拦）；强制力倒退（删措辞正则无过渡并联）|
| 3 | FAIL：2 P0 + 2 P1 + 1 P2 | 无基线整文件重写（kb_gate_sg.py 164 行 vs 真实 349 行）；措辞兜底残留面（白名单内错类）|
| 4 | FAIL：2 新 P0 + 2 P1 + 1 P2 | 无基线整文件重写换文件重演（kb_gate_hard.py 179→265 行删 seedance 分支）；SG is_checked 收紧绕过灰度（17/18 弱标记项目批量 BLOCK）|
| 5 | 修正中 | 回广州真实基线补 seedance 分支 + is_checked 纳灰度 + 模板收口过自己的契约 |

**核心模式：每轮 PASS 只代表旧问题修好，不代表没引入新拦截/新倒退。** 新增校验必须挂灰度（WARN 只记不拦）、老行为必须有过渡并联、基线必须逐文件核对。

## 用户「怎么每次都能检查出问题」的根因收敛（2026-08-22 round4 后定案）

用户连问两轮「改这个东西这么麻烦吗」「怎么每次都能检查出问题」——不是 claude 找茬，是两类真问题反复出现，**根子都在打包方（Hermes）**：

1. **新校验绕过灰度（4 轮出现 4 次）**：round1 read_files / round2 TASK_TYPE 白名单 / round4 is_checked——codex 每次加新校验默认「立即生效」，忘了这套系统的核心是 G0 观察期不能拦。**任务书没把「新校验必须受 mode 管辖」写成铁律，codex 就反复踩。**
2. **无基线整文件重写（round3/round4 各一次）**：codex 在容器里看不到真实生产文件，inputs 缺哪个基线它就凭想象重写哪个（kb_gate_sg 丢 token 层、kb_gate_hard 删 seedance 分支）。**打包时基线给不全，连续踩两次。**

验收严不是问题——问题被拦在部署前，比上线后炸强一万倍。收口：①任务书显式写「新校验必须受 mode 管辖」；②打包前列基线清单核对，缺一个都不派活；③5 轮还过不了就该停下来看方案本身是不是有硬伤，不再硬改。

## 跨机基线事故（round2→round3→round4 三连）

- round2：inputs 漏 claude_remote_wrapper.sh → codex 交 50 行全新文件覆盖广州 120 行
- round3：inputs 漏新加坡 kb_gate_sg.py → codex 交 164 行覆盖真实 349 行（token 消费层 7 个符号 0 引用）
- round4：inputs 有 kb_gate_hard.py 但不在「真实基线」目录 → codex 整文件重写 179→265 行，**删光 seedance 硬编码分支（4 处引用→0）**，SG 侧却完整保留——同一批交付两机口径相反

**验证法（三向对比 + 符号计数）：**
```bash
# 行数三向对比：方案记录 / 产物 / 目标机实际，差一个数量级 = 整文件重写
wc -l inputs/<基线> staging/<产物>  # + SSH 目标机 wc -l

# 关键符号计数相等（kb_gate_sg 的 token 层 / kb_gate_hard 的 seedance 分支）
grep -c 'consume_gate_token\|GateTokenError\|TOKEN_DIR\|O_EXCL' inputs/<基线> staging/<产物>
grep -c 'seedance-2-0-mini-workflow' inputs/<基线> staging/<产物>   # 必须 ≥4
```

部署目标文件全部列进基线核对清单，一个都不能漏；每个文件配「相对基线 diff 只有可枚举 hunk + 关键符号计数相等」验收项。任务书必须写「基于基线移植、只补两段、diff 确认既有逻辑全部保留」。**基线要放「真实基线」目录（gz-full-fix-r2/）并逐文件配门禁——inputs 里存在但不在基线目录 = 跟没有一样（round4 教训）。**

## 灰度与强制力（三坑同型）

1. 新增校验不挂 mode → WARN 期就拦死（round1 P0-1）：任何新校验 WARN 只打日志；配「WARN 下 rc=0 + 日志」回归断言
2. 让 RC 真传出去 → 激活被焊死的硬 BLOCK（round2 P0-1）：改 RC 传递前全查受 WARN 保护的硬 BLOCK 路径
3. 删措辞正则无过渡并联 → G1 强制力倒退（round2 P0-2）：措辞兜底正则 + `per_task_mode.__missing__` 兜底键，断言「G1 含措辞无 marker 必须 rc=1、G0 同任务 rc=0」
4. round4 P0-B（SG is_checked 收紧同型）：把「read_files 非空+绝对路径证据」收紧不挂灰度 → 落盘即刻批量 BLOCK 旧弱标记项目。修法：收紧只在 `mode==BLOCK` 时生效，WARN 期旧弱标记 PASS + WARN；灰度阶梯对每条收紧必须成立

## 措辞兜底残留面（round3 扩展 + round4 P0-2 残留）

- 触发条件 `not task_is_listed` 只拦「缺失/不在白名单」→ 白名单内错类（TASK_TYPE=分析+出片措辞）不触发
- 修法：措辞命中即取「出片模式与当前模式更严一档」（_strictest_mode），不看 task_is_listed；L1 补「TASK_TYPE=X 与出片意图不匹配」
- v11 那类「0 次出片字样」任务书（重写提示词/镜1）兜底正则根本不命中 → 需要第二条意图词表（重写提示词|分镜|镜头|镜\d+|口播|数字人|视频）
- 纯运维（无内容生产意图）走独立放行路径，不能跟 __missing__ 共用一键（两类情形取任何值都有一边错）——has_content_intent 进 _configured_mode

## 模板/契约产物必须过自己的契约（round5 P1-D 新教训）

「收口/统一」类产物（模板、样例、文档）如果本身就是契约的验证对象，**收口后必须拿产物本体送契约闸验证**——手工构造的「合规任务书」能过不算数，产物原文能过才算收口完成。两类真实失败：

1. **标点不一致**：契约写「语速适中，吐字清晰」（全角逗号），模板写「语速适中、吐字清晰」（顿号）→ 纯子串匹配 6 镜全 MISS。契约与产物的标点必须逐字符一致，或契约加同义组
2. **产物本身违反规则**：模板 5 镜写「@图1 [同上外貌锁定]」——「同上」直接违反 AGENTS.md §九（禁止同上/沿用前镜/使用全局锁定层缩写）。契约 forbidded 是对的，模板是错的。收口时要改模板本身（每镜完整展开锁定），不是改契约放行

**验收断言：收口后产物送契约闸 errors 从 N 清到 0（逐条核对每个 error 根因：标点/违规/缺项），产出新 MD5。**

## 部署空转假完成（编排脚本坑）

`dispatch_codex_impl || { log "失败，继续部署已有产物"; break; }` → codex 失败 → break → 部署函数 if 没进 → 却打「部署阶段完成」。
排查：`ls staging/<目标>/` 看实际产物；生产机查 `.bak-20260822-autofix` 时间戳（有备份=动过，无=没动）。
正确：dispatch 失败先查原因（本案例=卡点误伤，补标记重派），部署函数第一步 `[ -f staging/.../产物 ] || { return 1; }`。

## 卡点误伤正规调度（本次失败根因链）

- kb_gate_sg.py 的 `出片|Seedance|视频生成` 正则把「代码实施任务」（修 execute_api.py 的出片确认闸）误判成出片任务 → BLOCK
- 加 SKIP_KB_GATE=1 → has_content_intent 命中「分析」→ BLOCK「内容生产任务不允许 SKIP 豁免」
- 正路：项目已有 `guard/kb_checked.json`（checked=true + 实读清单）→ 走正常知识库路径 PASS；补 READ_SKILL 标记过 seedance 检查
- **本地模拟预检 30 秒排掉白派一轮**：`python3 ~/.hermes/scripts/kb_gate_sg.py -f <brief>` 期望 PASS 再 dispatch

## 卡点对执行器是零防御（用户连续四轮纠正）

「a这么做没意义」「c.没用，他之前就是用这个方法骗过去的」「他可以自己伪造skip把」「他可以骗卡点每次都是运维」——
字符串检查（READ_SKILL=/SKIP_KB_GATE=1/关键词）执行器都能自己伪造。结论：
1. 禁止派执行器修自己的卡点（把闸门钥匙交给被闸的人，是被用过的后门）
2. 卡点防护只能放在执行器够不到的地方：容器隔离（产物只落 staging）、部署环节人工（搬运/备份/重启）、部署前验证（md5 核对/py_compile/可回滚）
3. 关键词检查会误伤正规调度（「出片」命中代码实施任务），别围着卡点打补丁，走正路
