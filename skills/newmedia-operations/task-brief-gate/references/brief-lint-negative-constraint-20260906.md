# brief_lint.py：负向约束=反向激励 + 任务书自作主张检测

## 问题

用户明确说了"不用 hermes -z、不用 task_api.py、不用文件接力"，但 GLM 写出的任务书里自己加了这三样。用户没要求，GLM 自作主张添加了用户没有要求的技术方案。

## 根因分析（Claude 2026-09-06 四层分析）

### 1. 为什么 GLM 会自作主张

1. **负向约束是反向激励** — 用户说"不用 hermes -z、不用 task_api.py"，这三个词进了上下文，反而抬高了它们在生成时的概率。越强调"不要什么"，越容易生成什么。这是 LLM 的注意力机制特性：被提到的 token（即使是否定语境）概率都会上升。
2. **规格有洞，模型在补** — 用户说了"单会话连续跑17节点"，但没说靠什么机制串起来。模型面对空位就从先验里抓最像的填进去。
3. **历史任务书模板惯性** — 项目里几十份 brief 都是 GLM 的隐式 few-shot，如果旧 brief 里出现过 hermes -z，就会被复制。
4. **没有惩罚信号** — GLM 加的东西下游照样跑，跑完报成功，没有任何一环告诉 GLM"你多写了"，行为永远不收敛。

### 2. 四层解决方案

**第1层（今天能上，1小时）** — 写个 `brief_lint.py`，接在 Hermes 派单前：
- 从用户消息自动提取"不用X"里的X，在任务书里 grep，命中直接打回
- 新增实体差集扫描：任务书里的技术实体减去用户原话里的实体，残差非空=自作主张
- 拦到就打回重写，重写 prompt 只给正向白名单，不复述被拦的 token

**第2层** — USER_REQ 由代码逐字拷贝+哈希，GLM 无权改写；加 CONSTRAINTS 机器可读块

**第3层（根治）** — 结构化任务书，把"执行方式"整节从 GLM 手里拿走，由代码按 EXEC_MODE 枚举查模板库贴入。GLM 只写诊断/验收/基线事实。写任务书 temperature 压到 ≤0.2

**第4层（长期）** — 每次拦截记录回流，攒样本编译规则卡放进系统提示词

### 3. Claude 直说的两个关键点

1. **"单会话跑17节点到底靠什么串"这个空位你不填上，闸能拦住 GLM 乱填，但拦住之后它写不出可执行的任务书，只会反复被打回。** 这是当前唯一缺的信息——必须用正向规范填空位，不只靠负向禁止。
2. 不要指望靠加强 prompt 措辞解决——已经写了三条"不用X"，三条全被违反，不是措辞不够强，是方向错了。加更多"严禁"只会进一步预热那些 token。

## 正确做法（用户 2026-09-06 定案）

用户填上了空位：**串17个节点的机制 = 飞书会话本身。**
- 不是 hermes -z 逐节点调，不是 task_api.py 启动，不是文件接力
- 是 GLM 在飞书会话里一个节点一个节点往下跑
- 中间在节点8和节点12停住等客户确认，确认完了继续跑
- DB 只管存订单状态和交付物，不做流程调度
- 三个确认停点：节点8文案、节点12出片、最终成品

## brief_lint.py 实现要点

```python
#!/usr/bin/env python3
# 两层检查：
# 1. 硬拦：从用户消息提取"不用X"里的X，在任务书里grep，命中即BLOCK
# 2. 软拦：任务书里的技术实体减去用户原话里的实体，残差非空=WARN

# 用法：python3 brief_lint.py <brief文件> <用户消息文件>
# 退出码：0=PASS, 1=WARN, 2=BLOCK
```

关键技术点：
- 技术实体词表包括：hermes -z, task_api.py, hermes_task_dispatch, codex_glm_fallback, 等已知执行器脚本名
- 负向约束提取：正则匹配"不用X"、"不要X"、"禁止X"里的X
- 拦截后重写 prompt 只给正向白名单（"按飞书会话连续执行"），不复述被拦的 token（避免再次预热）
