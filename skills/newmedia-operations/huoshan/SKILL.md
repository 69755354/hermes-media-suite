## 📐 两段架构 + 段1产出复用规则（2026-07-12 会话定稿）

> **核心原则：只管两段，不分三段。** 段1（客户服务）和段2（视频工作流）共用节点0（信息采集）作为统一入口。

### 段1：客户服务（小鹿干，纯文本输出给客户）

**入口条件：** 客户提出任何需求（搜爆款/写文案/做分析/做视频）→ 先走节点0收信息

**四个功能（均需带分析理由）：**
| 功能 | 输出 | 深度要求 |
|:----|:----|:--------|
| 搜爆款 | 爆款列表 + **拆解为什么爆**（钩子类型/情绪节奏/转化路径/同城属性） | 结构拆解 |
| 写文案 | 文本文案 + **拆解为什么这么写**（钩子选择/痛点人群/情绪链条/价格逻辑） | 心理学模板 |
| 做分析 | 深度报告 + **结论**（地域/客群分层/驱动力/共情策略/风险提示） | **Pro深度** |
| 🌄 **生图** | 单张AI图片（封面/配图/海报/角色设计稿） | **经 `hermes_task_dispatch.py` 调用（不直连ARK）** |

**每个功能结尾必问：** 「要不要做成视频🔥？」
- 客户说搞 → 进段2
- 客户说不搞 → 完事

### 段2：视频工作流（从节点0往后走）

**触发条件：** 客户说「做视频」或段1结尾客户选「做视频」

**段1产出复用规则（节约一轮工作）：**
| 段1干了什么 | 段2跳过什么 | 原因 |
|:----------|:-----------|:-----|
| 搜了爆款 | ✅ 跳过节点2（爆款拆解） | 已有爆款素材 |
| 写了文案 | ✅ 文案直接当剧本底稿 | 内容已定方向 |
| 做了分析 | ✅ 跳过节点1（用户分析） | 已有客群结论 |
| 收了信息 | ✅ 节点0已走完 | 店名/照片/价格均在 |
| **自备文案** | ✅ 跳过节点0-4 | 客户给了成品文案，不重做采集/分析/选题/写文案 |
| **只改文案不改画面** | ✅ 跳过节点6-13 | 只改文案→直接改口播稿→重新出片（默认快乐马 happyhorse-1.1-r2v） |
| **只改某镜画面** | ✅ 只重做该镜8→12 | 其他镜不动，只改提示词→重新生成该镜→合成 |

### 两段关系图

```
客户说需求
  │
  ▼
节点0：信息采集 ─── 统一入口
  │
  ▼
段1：搜爆款/写文案/做分析 → 纯文本 + 拆解为什么
  │                              （Pro深度当需要时）
  │
  ├─ 客户说「做个视频」→ 进段2
  │      │
  │      ▼
  │     段2：复用段1产出 → 继续走剩下节点 → API出片
  │
  └─ 客户说「不用了」→ 🎉 完事
```

**铁律：** 段1的信息采集（节点0）后，段2绝不再重复问同一个问题。节点0存好了就用。

## 🚨 知识库内容来源铁律（2026-07-19 新增/2026-07-20 补充：搜索后必须读全文）

**核心规则：所有知识库文档内容必须来自真实网上来源，标注来源，不得AI编造。**

用户多次纠正（「你是网上搜的吗」「你不搜你那里知道具体内容是什么」「全部去网上搜完整内容，确保引用的是真实完整内容，而不是你自己编造的」「你都不知道内容你引用个屁啊」）。

### ⚠️ 仅搜索不等于验证（2026-07-20 补充：本会话用户明确纠正）

**搜索出来源后，必须实际读取全文内容再下笔。只看搜索摘要/描述就写引用=编造。**

| ❌ 错误做法 | ✅ 正确做法 |
|:-----------|:-----------|
| 搜索到James Clear文章→只看标题和描述→写「据James Clear引用Aristotle定义」 | 搜索后web_extract实际内容→确认Aristotle原话是"The first basis from which a thing is known"→再写 |
| 搜索到Kahneman & Tversky→只看摘要→写「损失厌恶2:1比率」 | 提取SCU商学院文章或Wikipedia Prospect Theory页面→确认实验细节再引用 |
| 看到文件名就写进【依赖资源】 | 先read_file确认内容真实存在、标注了来源，再写进人设 |

| 类型 | 处理方式 |
|:----|:---------|
| 学术理论（行为经济学/心理学等） | 必须搜到可验证的原始研究来源（论文/教科书/权威平台） |
| 行业数据（下沉市场/平台用户等） | 必须搜到可查的公开报告（CIC灼识/麦肯锡/QuestMobile等） |
| 平台规则/合规红线 | 必须搜到平台官方文档或权威解读 |
| 用户提供的定稿内容 | 可直接使用，但需标注来源为用户定稿 |
| 行业案例/创作示例 | 可基于理论自行创作，但需声明为示例 |

**执行规则：**
- 写文档前先搜，搜到真实来源再动笔，不凭已有知识编造
- 每份文档头部必须标注来源，格式：`> 来源：[机构/论文]，[年份]`
- 引用的所有数据必须有可查来源，禁止虚构引用
- 理论框架可复用，但具体话术案例/示例数据需标注为创作示例

| **basic（默认）** | ❌ | ❌ | ✅ | 0 |

### 工作边界：商业走流程 vs 娱乐直出

| 场景 | 走法 |
|:----|:-----|

### ⚠️ ARK看图端点可靠性警示（2026-07-11 新增，本会话实测）

**端点：** `ep-20260710211910-f65h9`（`doubao-seed-2-0-mini-260215`）

**问题：** 本端点在2026-07-11会话中对同一批熹园门头照片的分析结果，与用户直接在豆包App中看到的结果**完全不符**。用户已验证并确认API分析结果是错误的（门的位置/材质与实际不符）。

**结论：ARK看图端点的输出不可全信。** 它可能返回编造的描述（如指着一张宣传单说「这是门头实景照，门在左侧」）。

**应对策略（优先级从高到低）：**

| 优先级 | 方案 | 说明 |
|:-----:|:-----|:------|
| 1 🥇 | **换图／以档案为准** | 图看不清就换图，不问用户；ARK看图结果与wiki档案冲突时以档案为准。 |
| 2 🥈 | **交叉验证** | 如果必须用ARK看图，把分析结果拿着去和已有的wiki档案、用户历史描述做比对，有明显矛盾就弃用 |
| 3 ❌ | ~~全信端点输出~~ | 已证实不可靠，禁止把端点的单次输出当作事实用于写prompt |

**铁律：** 写prompt时涉及门的位置/材质、桌椅布局、招牌文字等**具体视觉细节**，以**wiki档案和用户已给的描述为准**，不以ARK看图端点输出为准；看不清就换图，不追问用户。

### 🆕 轻量级模式：娱乐向/跟拍模板短视频

**适用场景：** 纯娱乐内容（甜妹摇头晃脑/跟拍热门模板/萌宠/卡点变装/手势舞等），**非实体店推广**。

**触发判断（满足任意一条即走轻量级）：**
- 参考视频是纯娱乐/跟拍模板，无门店推广属性
- 用户说的是「做个一样的视频」而不是「帮我推广XX店」
- 内容不需要门头/店内实景/套餐价格/地址露出
- 时长≤15秒，BGM驱动而非文案驱动

**与完整18节点工作流的区别：**

| 维度 | 完整探店19节点 | 轻量级模式 |
|:----|:-------------|:-----------|
| 前置分析 | 用户分析→爆款拆解→选题→文案→分镜 | 直接拆参考视频结构→出方案 |
| 文案 | 台词+人设+情绪节点（5段式） | **无需文案**（纯BGM+画面） |
| 分镜 | 6镜30秒带台词+场景切换 | **单镜5-10秒**或2-3镜递进 |
| 声音模式 | 口播/旁白/内心独白三选一 | **无台词**（Seedance不生成人声） |
| BGM | 平台发布时挂同款/本地SoundHelix叠轨 | 同左，见 `references/trending-content-bgm-strategy.md` |
| 时长 | 30秒 | 5-10秒（跟热门模板节奏） |
| @图2场景 | 需要门店实景照 | **不需要@图2**，背景照参考片具体描述（禁写纯色/干净背景） |

**执行流程：**
```
① 分析参考视频（结构/节奏/数据/抖音是否标注AI生成）
② 简化方案：去除非核心元素（用户说「不要猫也可以」就简化）
③ 写单镜出片 prompt（纯动作描述+无台词+无@图2）
④ 调快乐马 happyhorse-1.1-r2v 生成（Seedance 仅用户点名） → 下载视频
⑤ ffmpeg叠BGM（SoundHelix免费曲目截取）→ 出片
⑥ 告知用户在发布平台挂同款热门BGM蹭流量池
```

**Seedance prompt写法（无台词纯画面版）：**
```python
@图1 作为甜妹探店博主小鹿，保留全部面部特征和穿搭不变；
照片级写实，无CG感，天然肌肤质感，明亮自然光线；
中近景镜头，画面稳定柔和，背景按参考片或实景具体描述；
[动作描述：跟着节奏摇头晃脑/甜笑/眨眼等]；
动态强度按 `director-thinking` 对应镜头类型的起测区间选择；
# 不加"同步生成中文探店人声"
# 不加任何台词内容
# 不需要@图2场景引用
```

**抖音「疑似AI生成」标签陷阱（轻量级内容尤其高发）：** 抖音会对大量真实拍摄内容打上「疑似使用了AI生成技术」标签（触发因素可能是美颜滤镜、贴纸、特效等）。**不能基于这个标签判断参考视频的内容来源。** 必须通过帧分析确认是真人实拍还是AI生成（见节点3 - 爆款拆解 > 参考视频画面逐帧分析工作流）。如果确认是真人实拍+贴纸，复刻方案应说明「小鹿是AI角色模仿真人风格」，而非宣称技术路线一致。

**BGM处理（重要）：**
- 参考视频使用平台内置热门音乐模板时 → 优先告知用户发平台时挂同款BGM（0版权风险+蹭流量池）
- 用户要求直接出片带BGM → 本地SoundHelix免费曲目截取+ffmpeg叠轨
- BGM音量固定0.25，参考 `references/trending-content-bgm-strategy.md`

**交付：** 发视频下载链接（上传到可访问URL），告知发布时挂 #热门标签 + 同款BGM。禁止用MEDIA格式发文件。

### 核心流程

1. 启动预检通过后，有图就调豆包Vision批量分析

     ```
   - **铁律：** 用户发的人物/身份照片，**第一问永远是文字提取，不是外貌描述**。人物外貌是次要信息，姓名/资质/品牌名/联系方式才是关键业务信息。
5. 输出门店信息JSON + 用户确认后进节点1
6. **自动存档：** 确认后的门店信息同时写入 `~/wiki/assets/shops/<客户名>.md`（见newmedia-operations知识库wiki规范）

### 本节点铁律

- **禁止问视觉细节：** 用户发了实景照，直接调豆包看。不问他招牌写什么、装修什么风格、门口有什么。这是被多次纠正的行为。
- **回头客不准再问：** 已有 wiki 档案+缓存图的客户，直接恢复项目信息，不准重复索要。这是被本次会话纠正的行为。
- **同城引流电话地址要露出：** 电话和地址必须在交付物（视频字幕/文案/口播）中明确显示。同城引流客户靠电话地址到店，不是隐私保护场景。

- **照片分析优先级：文字大于视觉。** 用户发人物/身份照片时，第一问必须是提取文字（姓名/资质/品牌名/机构信息），再问外貌特征。2026-07-14 用户明确纠正："我让你看照片里的文字"——凭印象看人跳过了关键业务信息。

## 节点2：爆款拆解

**输出：** `节点2_爆款分析.md`+ `节点2_素材过滤清单.md`（被剔除的编造素材）

#### 完整工作流（CDP看→下载源视频→全帧提取→Vision分析→出方案）

```

  ↓ 拿到原始mp4文件

### 🚨 参考视频画面逐帧分析工作流（2026-07-19 新增：本会话用户连续纠正后沉淀）

**触发条件：** 用户说了「做一个一样的」「参考这个视频」「按这个风格做」等涉及具体参考视频的指令。

**背景（本会话的教训）：** 用户发了一个抖音参考视频，我只看页面元数据（标题/时长/点赞/标签）就凭想象写prompt出片，导致内容方向全错。用户连续纠正后，正确的流程是**下载原视频→逐帧分析画面内容**，而非仅看页面数据推演。

**完整流程：**

```text
① CDP浏览器打开视频页 → 获取页面元数据（标题/时长/赞评藏/标签）
  ↓
② 确认视频已加载（看snapshot中进度条显示00:XX/00:YY）
   如果被登录弹窗挡住 → 刷新或点击页面其他区域
  ↓
③ 用 browser_console 获取视频源地址：
   browser_console(expression='document.querySelector("video").currentSrc')
  ↓
④ 用 curl 下载原视频：
   curl -sL -o /tmp/reference_video.mp4 "<source_url>"
  ↓
⑤ ffmpeg 抽帧（短视频<30秒建议用fps=2，即每0.5秒一帧）：
   ffmpeg -i /tmp/reference_video.mp4 -vf "fps=2" -q:v 2 /tmp/frames/frame_%02d.jpg
   ⚠️ fps=1会漏掉关键动作变化（如张嘴→闭嘴切换），10.5秒视频应抽21帧而非11帧
  ↓
⑥ 用 ARK Vision（doubao-seed-2-0-mini-260428）逐帧分析内容：
   每帧分析6个维度：人物/动作（嘴巴张闭+眼睛睁闭+头部位置）/表情/背景/贴纸/风格
   分批分析（每批7-10帧）
   输出格式：帧X: 嘴巴[张/闭], 眼睛[睁/闭], 头部[位置], 表情[描述]
  ↓
⑦ 根据分析结果输出帧序列表，明确动作节奏后再动笔写prompt
```

**分析的6个维度（每帧必问）：**

| 维度 | 具体问题 |
|:----|:---------|
| 人物 | 有人物吗？性别/年龄/长相/穿搭？正脸还是侧脸？全程位置是否变化？ |
| 动作节奏 | 嘴巴张开/闭合？眼睛睁开/闭着？头部有无移动？每个状态持续几帧？ |
| 表情变化 | 微笑/张嘴惊喜/嘟嘴/眨眼？表情切换节奏是否卡BGM节拍？ |
| 背景 | 室内/户外？纯色还是实景？颜色？光线（暖/冷/自然光）？ |
| 贴纸/特效 | 有没有贴纸覆盖？位置在哪？是否和人物动作同步？ |
| 画面风格 | 真人实拍（有无美颜滤镜）/AI生成/二次元？ |

**⚠️ ARK Vision 分析存在局限性：**
- 对画面细节描述可能出错（已验证会编造细节）
- **关键结论必须交叉验证：** 对比多帧之间的变化是否自洽
- 最终以wiki档案为准，不盲信分析结果；看不清就换图，不追问用户

**⚠️ 抖音「疑似AI生成」标签陷阱（本会话关键发现）：**
- **「疑似AI生成」标签不代表画面是AI生成的。** 真人实拍+美颜滤镜/贴纸的视频也会被标注AI生成
- **必须通过帧分析确认画面风格**，而不是凭标签推演（本会话中一个真人女生+贴纸被错误判断为AI生成）

**公众号：** 不走爆款拆解节点。直接采集客户开店故事/产品工艺/创始人背景，写公众号长文。

### 选题打分表（量化版）

**打分权重（冷启动期）：** 传播性×4 + 差异化×3 + 转化力×2 + 合规×1

每个维度按1-5分打，乘权重后算总分。

| 维度 | 权重 | 1分 | 3分 | 5分 | 理由 |
|:----|:---:|:----|:----|:----|:-----|
| **传播性** | ×4 | 只有特定人群能共鸣 | 30-50%目标人群有共鸣 | 80%以上的人刷到会停 | 冷启动看跑量 |
| **差异化** | ×3 | 同赛道已经有很多类似选题 | 有1-2个差异点 | 没人做过这个角度 | 同质化严重必死 |
| **转化力** | ×2 | 看了没行动冲动 | 有点想去了解 | 看完就想下单/私信 | 冷启动先不急转化 |
| **合规** | ×1 | 大概率踩红线 | 边缘词要包装 | 完全安全 | 红线不能踩 |

**流程：** 三分向各出1个候选 → 填打分表 → 最高分入选

**🔒 物理卡点（2026-08-07 新增）：** 候选方向先落盘内部文件 `节点3_候选方向.md`（≥2个方向，含方向名+核心逻辑），进节点4前 `review_gate.py check <项目目录> node3_candidate` 返回ALLOWED，非0退出=终止。**该文件不交付客户**——客户交付仍只给最终选题+一句话理由（SPEC 2026-08-04 要求）。

### 🚨 行业特异性合规规则（2026-07-11 新增，2026-08-07 从节点11 移入节点4）

**原则：** 不同行业有不同合规红线。视频发布前必须按行业类型逐条检查，不准只用通用词表扫一遍就过。

#### 茶馆/运势类（熹园示例）

| ❌ 直接违规（平台限流/下架） | ✅ 合规包装 |
|:--------------------------|:-----------|
| 算命、占卜、命理、测算运势 | 聊聊心里话、人生探讨、解惑 |
| 桃花运、财运、事业运 | 情感疏导、人生方向探讨 |
| 保证显灵、灵验、必脱单 | 引导到店私聊 |
| 封建迷信类总纲词 | 传统文化、文化体验 |

**合规翻墙原则：**
- 视频画面：正常喝茶、聊天、氛围展示
- 视频文案：只说「解惑」「聊聊心里话」「人生探讨」
- 到店后：线下怎么聊、具体服务叫什么名，跟视频无关
- 套餐名/宣传语中文化感软词可保留（「纳福」「卦象指路」），只要不注明具体服务

#### 医疗/护眼类（亮瞳示例）

| ❌ 直接违规 | ✅ 合规包装 |
|:-----------|:-----------|
| 治疗近视、矫正视力、恢复视力 | 放松眼睛、缓解疲劳、养护 |
| 降低度数、摘镜 | 控制增长、预防加深 |
| 保证效果、100%有效 | 因人而异、坚持使用效果更佳 |
| 对比其他医院/品牌 | 只说自家优势，不贬竞品 |

#### 通用违禁词（所有行业）

- 治疗、矫正、恢复（医疗相关）
- 第一、最好、唯一（绝对化用语）
- 无效退款（保健品类可能违规）

### 📕 小红书文案（图文/视频）

**工具同左，模板不同。不走抖音五段式结构和6种口播风格。**

**小红书图文文案结构：**
1. **标题**（15-25字）：痛点+数字+方案+emoji，前10字含核心搜索词

### 🚨 脚本逻辑一致性检查（2026-07-12 新增，熹园6镜实战沉淀）

**写完全部镜号的prompt后，逐镜强制自检，缺一不可：**

**1. 因果链检查**
□ 相邻两镜的独白/台词之间有没有「因为A所以B」的逻辑关联？断链了吗？
□ 把每镜的独白连起来读一遍，是一句完整的起承转合叙事吗？
□ 抽掉任意一镜，叙事链会不会断？

**2. 动作×独白情绪匹配**
□ 这个镜头的动作情绪（走进院子/落座/品茶/走远）和独白情绪（沉重/安静/内省/释然）是否一致？
□ 有没有出现「动作在欣赏环境，独白在讲沉重的事」这样的情绪错位？

**3. 空间连贯性**
□ 镜N+1的场景和镜N的场景之间有没有合理的过渡逻辑？
□ 从户外到室内/从门头到院内/从茶座到包间——观众会不会觉得「她怎么突然到这儿了？」

**4. 语气一致性**
□ 内心独白的语气像对自己说的话吗？还是像对外推销/介绍？
□ 有没有出现「价格数字+算账感」这种广告口吻的内心独白？
□ 整片6镜的语气是统一的（都是内心独白）还是混用了（镜1内心独白、镜5推销口吻）？

**5. 时间/光线连贯性**
□ 每镜的光线/天气是否随时间线合理变化？（午后→傍晚，不能前后颠倒）
□ 镜6的光线是否和镜1形成时间上的闭环感？（开场午后的暖光→收尾傍晚的灯亮）

**检查口诀：因果→情绪匹配→空间过渡→语气统一→光线闭环**

### 🚨 抖音探店脚本质量铁律（2026-07-10 新增，用户纠正点）

**核心原则：脚本要像闺蜜聊天，不是产品说明书。**

| 铁律 | 正确 ✅ | 错误 ❌ |
|:----|:--------|:--------|
| 台词必须像人话 | 「株洲姐妹，失恋别躲被窝哭」 | 「本公司推出情缘套餐，包含鲜果茶一杯」 |
| 价格融入剧情，不罗列 | 「358块，买不了吃亏，买你人生剧本」 | 「情缘套餐358元，纳福套餐95元」 |
| 用「你」不用「您」 | 「你多久没跟自己待一会儿了？」 | 「您是否需要预约我们的套餐？」 |
| 口语＞书面语 | 「哭了就点，茶凉前心先暖」 | 「欢迎到店体验，我们提供优质服务」 |
| 每句读出来必须顺口 | 写完自己读一遍，别扭就改 | 拗口的书面语直接过 |
| 0-3秒钩子让人停不下 | 「听说这家店的茶，能喝出你的心事」 | 「今天给大家介绍一家位于…的店」 |

### 🚨 台词连贯性检查（2026-07-11 新增，本会话用户纠正）

**核心原则：每镜说不同的话，推进不同的叙事功能。** 用户原话「你这几个镜头的台词都是重复的 重新生成意思连贯的剧本」。

**错误示范❌：**
```
镜1：有人帮你解
镜2：有人帮你解
镜3：有人帮你解
→ 三镜说同一件事，用户骂「重复」
```

**正确做法✅：每镜只推进一个叙事功能：**
```
镜1：我是谁（心理工作）
镜2：我看见什么（大家被困住）
镜3：所以我开了这里（绿植环绕安静）
镜4：在这里怎么解（喝茶安抚内心）
镜5：套餐价格地址
镜6：收尾邀约
```

**检查清单（剧本写完后逐镜打钩）：**
□ 每镜的台词在讲不一样的事
□ 把全部台词连起来读，是一句完整的起承转合叙事
□ 抽掉任意一镜，叙事链会断——即每镜都有存在必要
□ 没有两镜在表达同一个意思（如都在说「有人帮你」、都在说「解疙瘩」）
□ 各镜功能不重复；固定六镜只在用户或项目明确要求时使用

### 🚨 导演思维前置铁律：剧本阶段必须代入角色写情绪（2026-07-11 新增）

**原则：** 导演思维不是节点8才想的事。从节点4写剧本开始，就要代入角色的身份和情绪。

**错误做法（旧流程）：**
```
节点4 → 填模板套台词（凑字数，没情绪）
节点8 → 硬写一句「像闺蜜说秘密」（情绪是贴上去的，跟台词接不上）
       ↓
结果：Seedance出片，声音和表情脱节
```

**正确做法（新流程）：**
```
节点4 → 代入角色写纯台词（情绪是写台词时想好的，但不写进节点4输出）
        └ 例：小鹿说「说出来你可能不信」→ 贱兮兮欠揍感（心里有数）
             说「工作卷不动」→ 无奈自嘲（心里有数）
             说「情缘套餐358」→ 帮朋友算账的小得意（心里有数）
节点5 → 分镜表承载说话人/语气/情绪（2026-08-07 对齐：情绪归节点5）
        └ 小鹿：温柔细腻型，高兴时眼神亮不咧嘴，无奈时偏头不看镜头
节点8 → 把节点5的情绪翻译成机器微表情语言
        └ 贱兮兮 → 身体前倾+左右瞟一眼+压低声音
          无奈 → 偏头看左上方+嘴角快速收一下
          小得意 → 眉毛微挑+嘴角上扬
```

**节点4输出格式（纯文本台词本，无说话人/语气/情绪，2026-08-07 对齐）：**

```

台词：说出来你可能不信…
```

**自检清单（剧本写完逐项打钩）：**
□ 只有台词，没有说话人/语气/情绪标注（那些在节点5分镜表）

### 🚨 场景-动线叙事铁律：所有实景图都要走一遍（2026-07-11 新增，本会话用户纠正点）

**原则：** 用户提供了多个场景的实景照片时，每个主要场景至少要在视频叙事中露一次面。不要只用其中一两张。

**常见错误（本会话实例）：**
用户给了多张实景图但只有部分出现在叙事中 → 用户反馈「给你这么多实景图你都不用啊」

**正确做法：**
1. 列出所有用户提供的实景图 → 按探店动线排序
2. 给每个主要场景分配至少一个镜头
3. 动线逻辑：街边→走进第一景→穿过第二景→在第三景坐下体验→走向第四景→回到第一景收尾

**检查清单：**
□ 拿出了所有用户提供的实景图
□ 按探店动线排序：从外到内→走过→坐下→体验→走出
□ 每个显著的场景（门头、茶座、包间等）至少出现一次
□ 不重复用同一个场景超过2个连续镜头（除非动线需要）
□ 收尾镜与开场镜是同一场景形成闭环

| 维度 | 口播探店风格 ❌ | 文艺短剧风格 ✅ |
|:----|:--------------|:--------------|
| 节奏 | 信息密度较高 | 语义更舒缓 |
| 时长 | 字数÷5.5向上取整 | 字数÷5.5向上取整 |
| 语调 | 推销感，尾音上扬急促 | 邀请感，尾音轻缓柔和 |
| 钩子 | 「说出来你可能不信」「别划走」 | 「老街边上藏了一家不太一样的茶馆」「有空来坐坐」 |
| CTA | 「左下角先囤券，反正不去能退」 | 「珠江北路，熹园知味，有空来坐坐」 |
| 价格 | 融入剧情带紧迫感「才38」 | 轻描淡写带过「情缘38纳福98，一杯奶茶钱换一个下午」 |

**台词校准（文艺版）：** 两种风格的段时长都按字数÷5.5向上取整，不靠提速或放慢凑时长；配音提示词不写语速、停顿留白描述。

**自检：**
□ 台词风格与画面风格匹配（快画面快台词/慢画面慢台词）
□ 所有价格信息写的是照片上实际看到的价格（熹园实际是38/98，不是358/95）
□ 读一遍，语气像邀请不像推销

### 🎯 分镜做什么

```
剧本说「什么时间说什么话」
分镜说「每个镜头怎么拍」
```

| 剧本给的 | 分镜要定的 |
|:---------|:-----------|
| 台词 | 每段台词对应几个镜头 |
| 说话人 | 每镜的景别（远景/中景/近景/特写） |
| 情绪状态 | 每镜的运镜（固定/推/拉/摇/移/跟） |
| 场景 | 每镜的场景图对应（门头/凉亭/室内等） |
| 时长 | 每镜的秒数分配 |

### 🚨 分镜规则

**1. 动线逻辑**
- 参观动线：门头→走进→落座→体验→收尾（场景切换有过渡理由）
- 禁止场景硬跳（门头→站着说→坐下→跳回门头）
- 场景切换次数不设上限：有参考片照参考片拍位，没有按叙事定；每镜不超过15秒

**2. 景别分配**
```
全景/远景（环境展示）— 人物占¼，背景占¾
  → 进门/走动/环境展示
中景（人物互动）— 人物占½，背景占½
  → 落座/点茶/正常对话
中近景/特写（情绪）— 人物占⅔以上
  → 品茶/感动/关键金句
```

**3. 每镜只推进一个叙事功能**
```
镜1：我是谁/钩子
镜2：我看见什么（痛点）
镜3：所以我做了什么（动机）
镜4：在这里怎么解决（方案）
镜5：价格地址
镜6：收尾邀约
```

**4. 场景-文件对照表（必须建）**
| 镜号 | 场景 | 实景图文件 | base64路径 |
|:---:|:----|:----------|:-----------|
| 镜1 | 门头 | xxx.jpg | /path/xxx.b64 |
| 镜2 | 凉亭 | xxx.jpg | /path/xxx.b64 |

**字段规范：**

- 备注：转场（硬切/叠化/淡入淡出）、光影、道具、AI生图提示要点

### 🚨 彩铅升级方案：超写实素描（2026-07-10 定稿）

当标准彩铅三视图的还原度不够、微表情僵硬时，可用**超写实素描**替代原有彩铅风格：

| 配套Seedance prompt | 「从彩绘/素描还原为真人照片级写实」 | 可用婵静格式：直接写「照片级写实，无CG感」 |

### 🚨 用户提供新人物照片的处理流程（2026-07-11 新增，本会话用户纠正）

**正确三步流程：**

2. **Seedream生成彩铅三视图** — 基于豆包分析的特征描述，以真人照为参考图(垫图)，生成彩铅风格三视图设计稿

### 🚨 火山真人检测绕检：三视图+脸部特写设计稿格式（2026-07-11 新增）

**背景：** 火山引擎ARK对真实人物照片有严格的检测机制（`InputImageSensitiveContentDetected.PrivacyInformation`），直接传真人棚拍图会被拦截。经验证，以下参考图格式成功绕检。

#### ✅ 已证实的成功格式：中文三视图+特写设计稿

**布局结构（从上到下）：**
```
┌────────────────────────────────┐
│     正面     侧面     背面      │  ← 顶部文字（中文「正面 侧面 背面」+ 英文 FRONT SIDE BACK）
│     FRONT    SIDE    BACK      │
├────────────────────────────────┤
│   [三张真人半身/全身照横排]      │  ← 主内容区：三张真人照，白底
├────────────────────────────────┤
│   [多张细节/全身/半身补充图]     │  ← 中间补充区域
├────────────────────────────────┤
│ ┌──┐ ┌──┐ ┌──┐ ┌──┐         │
│ │眼│ │嘴│ │鼻│ │耳│  ...   │  ← 底部：脸部各部位特写放大窗
│ └──┘ └──┘ └──┘ └──┘         │  ← 可带标注文字（眼睛/嘴巴等）
└────────────────────────────────┘
```

**关键特征：**
1. **中文标签**（正面/侧面/背面），不是英文
2. **真人照片**（非AI生成）直接排入三视图布局
3. **底部有脸部特写放大窗**（眼睛、嘴巴等部位的放大图）
4. **白底背景**，无外围边框
5. **整体看起来像角色设计参考图**，而非普通照片

#### ❌ 已证实的失败格式

| 失败格式 | 原因 |
|:---------|:-----|
| 真人棚拍单图直传 | 直接被检测为真实人物拦截 |
| 单图+标注线/框线 | 仍包含真人面部像素，拦截 |
| 英文标题设计稿（"CHARACTER DESIGN REFERENCE SHEET"） | 格式不对，不满足火山检测的期望布局 |

#### 📝 实操指南

**如果需要在火山通道使用真人参考图：**

1. **首选用预生成彩铅三视图**（assets中已有郭襄/小鹿彩铅图）— 最可靠
2. **次选用Seedream生成的写实三视图**（assets中有的角色可直接复用）
3. **如果必须用真人棚拍图，必须排成中文三视图+脸部特写窗的设计稿格式**

**设计稿制作流程（用ffmpeg/ImageMagick/Python PIL排布）：**
```python

1. 白底画布（如 1440x2560 或 1280x2275）
2. 顶部写「正面 侧面 背面」+「FRONT SIDE BACK」
3. 上半部分：三张真人照裁剪后横向排列（同一人的正面/侧面/背面角度）
4. 中部：补充细节/角度图
5. 底部：裁剪眼睛、嘴巴、耳朵等部位放大后以矩形窗排列

### 🚨 参考视频运镜分析法（2026-07-11 新增，本会话实测）

**原则：** 当用户提供了参考视频时，拆解其运镜并复用到Seedance prompt中，不要凭想象写固定机位。

**标准流程：**

1. **抽帧** — `ffmpeg -i 参考视频.mp4 -vf "fps=2" -q:v 2 /tmp/frames/frame_%02d.jpg`（短视频至少fps=2，禁止fps=1，同节点2抽帧规则）
2. **分批分析** — 每18-20秒一批，用ARK看图端点分析运镜类型：
   ```
   分析prompt：这是参考视频第X-Y秒的连续帧。只分析运镜：
   1. 固定机位还是移动机位？如果有移动是推/拉/摇/移/跟拍？
   2. 景别变化了吗？全景→中景→近景？
   3. 具体在哪个时间点运镜发生了变化？
   ```
3. **映射到本视频** — 按参考运镜序列写镜号对照表：
   ```
   跟摇(入场)→推近(进门)→固定(场景展示)→推(室内)→固定特写→固定收尾
   ```
4. **写入prompt** — 将运镜描述写到Seedance prompt的动作段，与场景描述融合

**典型运镜-场景映射：**

| 运镜 | 适用场景 | Seedance prompt写法 |
|:-----|:--------|:-------------------|
| 跟摇/横移 | 人物入场/沿街走来 | 横向跟摇镜头从右侧跟拍人物沿街走来，镜头跟随人物移动平行摇摄 |
| 推近 | 从全景到人物近景 | 从XX机位平稳推近到人物上半身占画面约三分之二 |

### 🚨 角色动作自然度检查（2026-07-11 新增，本会话用户纠正点）

**原则：** Seedance prompt中的人物动作应该模仿真实探店者的自然行为，不要写多余的设计感动作。

**对比：**

| ❌ 多余动作（被用户纠正） | ✅ 自然动作 |
|:------------------------|:------------|
| 走到入口前停步微微侧身，**抬头看了一眼青瓦屋檐和左侧木柱发光字** | 从街边走向凉亭，**视线看向凉亭方向**，走到入口前自然停步 |
| **抬头看了一眼青瓦屋檐**，然后走进…… | 视线看向目的地，自然走进 |
| **侧身回头**看了一眼凉亭的方向 | 走到门口自然停住，**略微侧身回头**看了一眼 |

**写前自问：** 一个真实客人来探店，她会做这个动作吗？→ 不会就删掉。

**正确的动作原则（参考参考视频）：**
- 视线始终看向目的地（走路看路，不东张西望）
- 脚步自然，手臂随步伐摆动
- 停步就是停步，不需要额外加「抬头看招牌」「看屋檐」等表演
- 回头只看一次、自然、不刻意停留太久

### 🚨 人声一致性铁律（2026-07-11 新增）

**问题：** Seedance每镜独立生成人声，各镜声音描述不一致→出片后音色不同→拼接违和。

**解决：所有镜共用一个 BASE VOICE 模板，只改每镜的表演指导行。**

**BASE VOICE（全片统一，复制粘贴）：**
```

```

**PER SHOT（每镜只改逐句情绪这一行，不写语速/段首段尾/停顿留白）：**
```
镜1（钩子）：情绪俏皮卖关子，音量充足
镜2（痛点）：情绪无奈，逐句渐沉
镜3（方案）：情绪轻松，关键词带笑意

镜5（价格）：情绪开心，价格数字带笑意
镜6（CTA）：情绪轻松自然，不带推销感像顺口一提的邀请
```

**⚠️ 声音描述的质感铁律（2026-07-11 新增，本会话用户纠正点）：**
- ❌ 笼统写法：「年轻女声28岁，音色清亮偏甜，语速偏慢」
- ✅ 具体写法：「年轻女声28岁，音色清亮偏甜带温暖沙感，逐句情绪写清，音量充足，不说任何多余的字」（不写语速、停顿留气口、尾音等段首段尾描述）

**规则：**
1. BASE VOICE 的性别/年龄/音色描述在所有镜中完全一致，一字不差
2. 每镜只改逐句情绪，不改音色描述，不写语速/停顿/段首段尾

### 🚨 Seedance不渲染环境音（2026-07-11 新增，本会话实测）

**问题：** Seedance 2.0 Mini 的prompt中写了「环境音」，但生成视频中**没有**对应的环境音轨。Seedance只处理人声（探店人声/旁白），背景环境音不会被渲染到输出中。

**正确做法：环境音在节点13（ffmpeg合成）阶段手动叠轨。** 节点8写prompt时，环境音描述只作为「氛围提示」写在prompt中，不要期望Seedance直接生成。

**节点13环境音叠轨方案：**
- 从FreeSound/Pixabay等免费音效库下载环境音轨
- 用ffmpeg的amix叠到目标镜头的音频层上，音量0.22
- 或使用白噪音/粉红噪音模拟环境氛围

**自检：** 节点8 prompt中的环境音描述仅作为氛围提示，节点13必须准备对应的环境音wav/mp3文件并手动叠轨。

**每镜必须明确指定 @图1（角色）和 @图2（场景）的真实图片文件引用，禁止只用「背景XX完整保留」让Seedance脑补。**

**正确写法 ✅**
```

@图2 作为熹园门头实景照，木质青瓦招牌「熹园」暖黄灯光完整露出不虚化；
```

**错误写法 ❌**
```
@图1 作为小鹿严格保留全部特征不变；
背景熹园门头绿植暖黄灯光完整保留不虚化；
```

**规则：**
1. 每镜全局锁定段必须有明确的 `@图2 作为[场景类型]实景照，[场景特征]完整露出不虚化`
2. @图2引用的场景必须与镜号对应（门头→门头照，店内→店内照，茶台→茶台照）
3. 禁止写「背景XXX完整保留」——那是让AI脑补，不是引用实景
4. 节点10传reference_image时，必须按照prompt中的@图1/@图2顺序传入对应的base64文件
5. **写完prompt后，去节点7和节点10确认场景图base64文件实际存在再继续。** 只在文字里写「@图2 作为门头实景照」但节点10不传文件 = 违纪。

**输出格式：** 质检报告 → `节点11_质检报告.md`；Flash抽样复核（10%）；不通过 → 打回节点10修正提示词。

> ⚠️ 统一口径（2026-10-01）：默认出片只走快乐马 happyhorse-1.1-r2v；本节点的 Seedance 通道只在用户明确点名时使用。

**🚨 物理兜底：生成后立刻下载本地，禁止依赖TOS链接。**

### 📕 小红书视频参数（不同抖音）

| 参数 | 抖音 | 小红书 |
|:----|:----|:-------|
| 画幅 | 按用户当次要求（竖版720×1280／横版1280×720） | 同左 |
| 时长 | ceil(字数÷5.5) | 同左 |
| 分辨率 | 1280×720 或 720×1280 | 同左 |
| prompt开头 | 照片级写实，无CG感 | 同左，但文案输出时长控制不同 |

**小红书视频时长控制：** 每个分镜段时长＝字数÷5.5向上取整，单段≤15秒，视频长短由字数决定。

**工具：** 默认快乐马 happyhorse-1.1-r2v（接口文档／引用语法文档由 Hermes 提供）；Seedance 2.0 Mini API（model: `doubao-seedance-2-0-mini-260615`）仅在用户点名时使用
**调用文档：** 知识库 `wiki/concepts/seedance-prompt-template-library.md`（提示词模板库） | 知识库 `wiki/concepts/seedance-director-prompt-dual-system.md`（提示词双核体系） | **`references/seedance-api-format.md`**（已验证的API调用格式）

**固定模式：全能参考多图。** 多张reference_image（角色参考图+实景图），prompt用`@图1 @图2 @图3`引用各图，prompt第一句走V2格式「照片级写实，无CG感，天然肌肤质感」，含「同步生成中文探店人声」——Seedance自带配音，无需TTS。参考图传base64 data URI。

### 🚨 API调用铁律（2026-07-11 新增，本会话实测）

1. **正确端点：** `https://ark.cn-beijing.volces.com/api/v3/contents/generations/tasks`（不是 `/api/v3/video/generations`）
2. **content字段是数组（类chat格式），不是字典：**
   ```python
   content = [
       {"type": "text", "text": "prompt"},
       {"type": "image_url", "image_url": {"url": "data:image/png;base64,角色图b64"}, "role": "reference_image"},
       {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,场景图b64"}, "role": "reference_image"}
   ]
   ```
3. **duration参数在顶层**（`payload["duration"] = 5`），不在content里
4. **提交前检查：** 先调一次简单的test ping确认端点活着的再传大payload
5. **轮询：** 单镜生成约2-4分钟，每5秒poll一次，超时5分钟
6. **容错：** 失败重试最多5次，每张图用不同seed

**注意：** 火山引擎ARK拦截写实人物图，必须用彩铅三视图绕检。容错重试5次。

### 🚨 Seedance任务卡住处理（2026-07-11 新增，本会话实测）

**现象：** 任务提交成功（HTTP 200），但 `status` 持续为 `running`，`created_at` 和 `updated_at` 时间戳相同且长期不变（超过5分钟），说明任务被接受但从未实际开始处理。

**处理流程：**

```
任务提交后轮询5分钟，status仍为"running"且updated_at没变过？
  ↓ 是
1. 检查账户余额（问用户：是不是没钱了？）
2. 如果余额没问题 → 取消任务重提
   DELETE /api/v3/contents/generations/tasks/{task_id}  → HTTP 200
   重新POST提交同一个任务（prompt和参数不变）
3. 如果重提后仍卡住 → 换seed（不给seed参数让API自动分配）
4. 如果连续3次卡住 → 告知用户换时间再试
```

**注意事项：**
- 取消后任务资源立即删除，无法恢复。取消前先查一次状态确认真实情况
- 取消后必须重提交，不能只取消不等
- 如果取消时状态已是 `succeeded`，视频URL已不可用（资源已删），需要重新生成

### 🚨 Seedance的极限：不适合精确帧级表情动画（2026-07-19 新增，本会话实测）

**问题：** Seedance 2.0 Mini 是文生视频模型，不是人脸关键点驱动工具。它无法做到：
- 精确到0.5秒的张嘴/闭眼切换（写「闭眼微笑→张嘴惊喜」它会"自由发挥"过渡）
- 帧级同步的人物+贴纸镜像动作
- 按预设时间轴执行7个表情的顺序切换
- 高频小幅度的头部摆动（写了「快速」可能生成慢摇）

**什么时候该换工具：**
- 内容需要精确卡BGM节拍做张闭嘴表情 → **换即梦/抖音模板/人脸驱动工具**
- 内容需要人物+贴画/贴纸同步动作 → **换后期剪辑或人脸驱动工具**
- 纯娱乐向跟拍模板（摇头晃脑/手势舞/变装）→ **优先推荐即梦模板或抖音特效**

**什么时候Seedance依然是最佳选择：**
- 实体店探店口播（有台词有场景切换）
- 需要不同场景切换+连贯叙事
- 动作描述是自然行为（走路/喝茶/展示）而非精确帧级表情切换

**背景：** 一张戴墨镜的户外真人照成功绕过火山引擎真人检测，还原度显著优于彩铅→真人两步走方案。

#### 执行流程（优先级从高到低）

1. 🥇 **先试真人照直传** — 直接传用户真人照作为@图1 reference_image
   - 通过标准：API返回HTTP 200 + task_id（无InputImageSensitiveContentDetected错误）
   - 拦截时切换方案2
   - 不走人/不用参考图片做任何预处理
   
2. 🥈 **被拦截后走彩铅三视图** — Seedream生成彩铅三视图作为@图1，prompt用V2格式「照片级写实，无CG感」

3. **prompt写法（与彩铅版相同）：**
   ```python
   @图1 作为真人[性别][年龄][脸型五官发型穿搭]全部特征不变不戴墨镜眼神自然；
   照片级写实，无CG感，天然肌肤质感；
   @图2 作为[场景]实景照[场景特征]；
   [景别+运镜+动作+台词]；
   ```

#### 🚨 景别原则（2026-07-11 用户确认）

| 镜头类型 | 景别 | 人物占比 | 背景占比 | 适用场景 |
|:--------|:----|:--------:|:--------:|:---------|
| 环境展示 | 全景（远景） | ¼ | ¾ | 进门/走向/出门回头/走环境 |
| **走动/行走** | **远景** | **¼** | **¾** | **人物从街边走来/穿过庭院/走远出画** |
| 人物互动 | 中景 | ½ | ½ | 点茶/端杯/看周围/落座 |
| 情绪特写 | 中近景 | ⅔ | ⅓ | 品茶闻香小抿等需要看表情的瞬间 |

**🚨 走动景别铁律（2026-07-11 本会话用户纠正）：**
- 凡是人物行走/走动的镜头（走来、穿过、走远），一律用**远景**，人物占¼
- ❌ 错误：走动用中景人物占太多，看不到环境
- ❌ 错误：走动用全景描述但人物占比不对
- ✅ 正确：「远景机位门头绿植木廊占三分之二人物从右侧走向门头占四分之一」

**prompt景别描述写法对照：**
```
❌ 错误（人物占太多）：正面微侧中近景人物上半身占三分之二浅景深虚化背景
✅ 正确（环境展示）：全景机位凉亭门头和庭院环境占画面三分之二人物站姿占四分之一
✅ 正确（人物互动）：中景人物坐姿占画面约三分之一竹桌竹椅庭院环境完整露出
✅ 正确（情绪特写）：中近景人物手部和面部占画面一半串灯区布幔背景仍可见
```

**每镜景别自查清单：**
□ 这镜是展示环境还是展示人物情绪？
□ 展示环境→全景，人物¼背景¾
□ 展示人物情绪→中近景，人物½-⅔背景仍留¼以上
□ 背景不能全挡（同城引流需要让人看到门店环境）

**背景：** 传统认为火山引擎拦截所有真人照片。本案例中，一张戴墨镜的户外真人照成功绕过检测并生成视频，还原度显著优于彩铅再还原方案。

**流程（优先级从高到低）：**

| 优先级 | 方案 | 说明 |
|:-----:|:-----|:------|
| 1 🥇 | **真人照直传** | 直接传用户提供的真人照片作为@图1 reference_image。不走人、prompt用V2格式「照片级写实，无CG感，天然肌肤质感」 |
| 2 🥈 | **彩铅三视图垫图** | 被InputImageSensitiveContentDetected拦截后，用Seedream生成彩铅三视图，再用彩铅图传reference_image |

**已知风险：**
- 标准棚拍/证件照类真人照大概率被拦截
- 非标准角度/戴墨镜/户外抓拍类照片通过率较高
- 无统一规律，每次以实际API返回为准（200+task_id=通过，400+PrivacyInformation=拦截）

**示例（熹园验证通过的prompt）：**
```python
@图1 作为真人女性30岁鹅蛋脸鼻梁挺直，全部特征不变不戴墨镜眼神自然；
照片级写实，无CG感，天然肌肤质感；
@图2 作为场景实景照...[场景特征]；
[动作/微表情描述]；
[动态强度]；
[负面词]
```

**自检清单：**
□ 先试真人照直传（不带任何预处理）
□ 通过→直接用；拦截→切彩铅方案
□ prompt中描述的人物特征和参考图实际一致（不写墨镜但照片有墨镜=矛盾）

**铁律：节点8写了 @图2 场景引用并建了场景-镜头对照表，节点10调用API时就**必须**传对应的场景图base64文件。对照表是传递凭证，不是摆设。**

**预检流程（调用Seedance API之前逐条打钩，缺一不可）：**

□ 从节点8的场景-镜头对照表中读取本镜的 @图2 文件路径
□ 确认该文件在文件系统中实际存在（`os.path.exists()`）
□ 确认文件的base64编码成功（文件大小>0）
□ @图1 = 角色参考图（已确认路径存在）
□ @图2 = 场景实景图（已确认路径存在，与对照表一致）
□ 场景图是真实的用户实景照片，不是AI生成的幻视图
□ 图片传参顺序与prompt中的 @图1 @图2 顺序一致（顺序错了画面会乱）
□ content数组的结构正确：text + image_url(role=reference_image) + image_url(role=reference_image)

**典型错误（已在本会话中被用户纠正）：**
```python
# ❌ 错误：只传了角色图，场景图没传
content = [
    {"type": "text", "text": "@图1 作为小鹿...@图2 作为门头实景照，门在画面左侧..."},
    {"type": "image_url", "image_url": {"url": f"data:image/png;base64,{char_b64}"}, "role": "reference_image"}
]
# 结果：@图2 的prompt描述无实际图片支撑 → Seedance脑补场景 → 门位/布局全错

# ✅ 正确：角色图+场景图都传
content = [
    {"type": "text", "text": "prompt内容..."},
    {"type": "image_url", "image_url": {"url": f"data:image/png;base64,{char_b64}"}, "role": "reference_image"},
    {"type": "image_url", "image_url": {"url": f"data:image/jpeg;base64,{scene_b64}"}, "role": "reference_image"}
]
```

**已确认的参考图路径规则（每次从文件系统读取，不凭记忆）：**
```
角色图：/home/ubuntu/assets/characters/<角色名>_<风格>.png → base64
场景图：/home/ubuntu/.hermes/image_cache/<场景文件名> → base64
```

**本铁律与节点8的 @图2 场景实景引用强制铁律联动：**
- 节点8：在prompt文本中写 `@图2 作为...实景照，门在左侧/桌椅居中/招牌在上方完整露出不虚化`
- 节点7（素材汇总）：确认场景图文件存在，准备好base64
- 节点10（本节点）：API调用时实际传入对应base64文件
- 缺任何一个环节 → 场景全凭Seedance脑补 → 门的位置/桌椅布局全部跑偏

**自检:** 本镜prompt中提到的所有场景细节（门的位置、桌椅布局、招牌文字），在端到端流程中都有实际文件支撑。不是文字描述在骗自己。

### ✅ 本会话验证的完整合成流程（熹园案例 · 35s文艺探店）

**场景描述：** 户外庭院+凉亭+串灯区+包间，6镜拼接，全程人声+环境音+BGM三轨混合。

**第一步：准备BGM（统一曲目，不跳段）**
```bash
# 从本地已有的完整BGM曲截取35-40秒版本
ffmpeg -i /tmp/bgm_free.mp3 -t 36 -c copy bgm_35s.mp3 -y
```
**注意：** 选一首匹配整体调性的曲目，全程不换曲。BGM音量固定0.25。

**第二步：准备环境音（粉红噪音底噪+鸟鸣混合）**
```bash
# 1. 下载康奈尔实验室免费鸟鸣包（⏱～30秒）
curl -L -o bird_sounds.zip "https://dl.allaboutbirds.org/hubfs/Voices%20of%20Eastern%20Backyard%20Birds2.zip"
unzip -o bird_sounds.zip -d bird_sounds

# 2. 混合粉红噪音底噪+鸟鸣
ffmpeg -f lavfi -i "anoisesrc=color=pink:duration=36:seed=42" \
  -i "bird_sounds/Voices of Eastern Backyard Birds/01 Eastern Backyard Birds.mp3" \
  -i "bird_sounds/Voices of Eastern Backyard Birds/02 Mourning Dove Song.mp3" \
  -i "bird_sounds/Voices of Eastern Backyard Birds/11 Black-capped Chickadee Song.mp3" \
  -filter_complex "\
    [0:a]volume=0.15[a_base];\
    [1:a]adelay=2000|2000,volume=0.12[a_bird1];\
    [2:a]adelay=12000|12000,volume=0.10[a_bird2];\
    [3:a]adelay=22000|22000,volume=0.08[a_bird3];\
    [a_base][a_bird1][a_bird2][a_bird3]amix=inputs=4:duration=first:dropout_transition=2[a_out]" \
  -map "[a_out]" -ac 2 -ar 44100 ambient_36s.mp3 -y
```

**第三步：拼接视频（concat demuxer）**
```bash
# 创建文件列表（按顺序）
echo "file '/path/to/镜1.mp4'" > /tmp/video_list.txt
echo "file '/path/to/镜2.mp4'" >> /tmp/video_list.txt
# ... 依次添加所有镜

# concat拼接
ffmpeg -f concat -safe 0 -i /tmp/video_list.txt -c copy concat_raw.mp4 -y
```

**第四步：制作字幕（SRT→ASS→改字体）**
```bash
# 1. 写SRT文件
# 参见下方「中文字幕烧录铁律」的SRT格式模板

# 2. SRT转ASS
ffmpeg -i subtitles.srt subtitles.ass -y

# 3. 改ASS字体为WenQuanYi Zen Hei、字号54（不改=方框）；PlayResX/PlayResY 改成当次成片分辨率
# 原行：Style: Default,Arial,16,...
# 改为：Style: Default,WenQuanYi Zen Hei,54,&H00ffffff,&H00ffffff,&H00000000,&H80000000,0,0,0,0,100,100,0,0,1,2,1,2,10,10,20,1
```

**第五步：三轨混合+字幕烧录（最终合成）**
```bash
VOICE_GAIN=<照激励-06实存脚本的人声增益值>
ffmpeg -i concat_raw.mp4 -i bgm_35s.mp3 -i ambient_36s.mp3 \
  -filter_complex "\
    [0:a]volume=${VOICE_GAIN}[a_voice];\
    [1:a]volume=0.25[a_bgm];\
    [2:a]volume=0.22[a_ambient];\
    [a_voice][a_bgm][a_ambient]amix=inputs=3:duration=first:dropout_transition=2[a_pre];\
    [a_pre]loudnorm=I=-14:TP=-1.5:LRA=11[a_mix];\
    [0:v]subtitles=/tmp/subtitles.ass:fontsdir=/usr/share/fonts/truetype/wqy:charenc=UTF-8[v_out]" \
  -map "[v_out]" -map "[a_mix]" \
  -c:v libx264 -preset medium -crf 18 -r 24 -pix_fmt yuv420p \
  -c:a aac -b:a 128k -ar 48000 -ac 2 \
  -movflags +faststart \
  final.mp4 -y
```
**说明：** 人声增益 `VOICE_GAIN` 照激励-06实存脚本取值（两套模板统一）；loudnorm 放在三轨混合之后作用于整片，保证成片响度 I=-14、TP=-1.5、LRA=11 达标（⑪）。

**音量比例参考：**
- 视频人声：增益 `VOICE_GAIN`（照激励-06实存脚本取值）；三轨混合后整片 loudnorm=I=-14:TP=-1.5:LRA=11
- 环境音（底噪+鸟鸣）：22%（0.22）
- BGM：25%（0.25，已确认不准再改）

### ⚠️ 三个常见故障及修复（本会话实测纠正）

| 故障 | 原因 | 修复 |
|:---|:------|:-----|
| 字幕显示方框 | ASS文件中Fontname=Arial，中文字体不支持 | 必须用文泉驿正黑 WenQuanYi Zen Hei（`/usr/share/fonts/truetype/wqy/wqy-zenhei.ttc`，缺字体时 apt install fonts-wqy-zenhei）；Noto 作废 |
| 只有BGM没人声 | 未保留视频原始音频流 | amix时视频原声占100%权重，BGM和环境音降低音量 |
| BGM每段不同跳戏 | 为每镜选了不同曲目 | 统一BGM，全程同一曲，不跳段 |

### 🚨 统一BGM铁律（2026-07-11 新增，用户纠正点）

**原则：全程同一曲BGM，不按镜分段。** 用户原话「整个视频要统一bgm，每段用不一样的跳戏」。

| ❌ 错误（每段不同曲目） | ✅ 正确（全片统一） |
|:----------------------|:------------------|
| 镜1-3轻快吉他，镜4舒缓钢琴，镜5-6渐弱收尾 | 全程同一首温暖原声吉他曲，35+秒版本整曲用到底 |
| 根据每镜情绪换BGM | 选一首匹配整体调性的曲目，通过调整音量/淡入淡出适配情绪变化 |

**选曲规则：**
- 匹配视频整体调性（温暖/治愈/国风/轻快/文艺）
- 选一首剪出35-40秒版本，留2秒淡出
- 音量固定：BGM 0.25（已确认，不准再改）
**曲目来源：** `wiki/concepts/bgm-library.md` 或 FreeSound/Pixabay免费曲库
**平台热门BGM策略：** `references/trending-content-bgm-strategy.md` — 当参考视频使用平台内置音乐模板时，优先用平台音乐库而非自己叠轨

### 🚨 环境音叠轨铁律（2026-07-11 新增，本会话实测）

**背景：** Seedance 2.0 Mini 不渲染环境音（节点8已记载）。但节点8仅提示「环境音描述作为氛围提示」，节点13必须实际操作（ffmpeg叠轨）才能让视频有环境音。

**必做步骤（不跳过）：**

1. **准备环境音素材**（以下方式任选一种）：
   - **方案A（推荐·本会话已验证）：** 用ffmpeg生成粉红噪音+免费鸟鸣混合
     ```bash
     ffmpeg -f lavfi -i "anoisesrc=color=pink:duration=36:seed=42" \
       -i "free_bird_ambience.mp3" \
       -filter_complex "[0:a]volume=0.15[a_base];[1:a]adelay=2000|2000,volume=0.12[a_bird];[a_base][a_bird]amix=inputs=2:duration=first[a_out]" \
       ambient_36s.mp3
     ```
   - **方案B：** 从Pixabay/FreeSound/Mixkit等免费音效库下载户外环境音
   - **方案C（国内网络友好）：** 康奈尔实验室免费鸟鸣包（dl.allaboutbirds.org）+ ffmpeg粉红噪音
   
2. **音轨混合比例（经验值）：**
   - 视频人声（从concat视频提取）：增益 `VOICE_GAIN`（照激励-06实存脚本取值，和上方模板统一）
   - 环境音（底噪+鸟鸣/户外氛围）：**0.22**（背景，不压人声）
   - BGM：**0.25**（已确认，不准再改）

3. **ffmpeg三轨混合命令模板：**
   ```bash
   ffmpeg -i concat_video.mp4 -i bgm_35s.mp3 -i ambient_36s.mp3 \
     -filter_complex "\
       [0:a]volume=${VOICE_GAIN}[a_voice];\
       [1:a]volume=0.25[a_bgm];\
       [2:a]volume=0.22[a_ambient];\
       [a_voice][a_bgm][a_ambient]amix=inputs=3:duration=first:dropout_transition=2[a_pre];\
       [a_pre]loudnorm=I=-14:TP=-1.5:LRA=11[a_mix];\
       [0:v]subtitles=/tmp/subtitles.ass:fontsdir=/usr/share/fonts/truetype/wqy:charenc=UTF-8[v_out]" \
     -map "[v_out]" -map "[a_mix]" \
     -c:v libx264 -preset medium -crf 18 -r 24 -pix_fmt yuv420p \
     -c:a aac -b:a 128k -ar 48000 -ac 2 \
     -movflags +faststart \
     final.mp4
   ```

**自检清单：**
□ 环境音已准备（生成或下载了ambient音轨文件）
□ 环境音时长≥视频总时长（建议多2秒）
□ 三条音频的人声/环境音/BGM比例在合理范围（人声清晰可辨）
□ BGM全程统一，不是每段不同曲目

### 🚨 中文字幕烧录铁律（2026-07-11 新增，本会话实测）

**问题：** ffmpeg ASS字幕默认用Arial字体→中文字符显示为方框。必须在ASS文件中明确指定中文字体。

**正确流程（两步走）：**

**第一步：写SRT字幕文件**
```srt
1
00:00:00,000 --> 00:00:04,100
第一段台词
跨行用空行

2
00:00:04,100 --> 00:00:09,200
第二段台词
```

**第二步：SRT→ASS转换+字体修正**
```bash
# 1. 转ASS
ffmpeg -i subtitles.srt subtitles.ass -y

# 2. 修改ASS文件中的字体行（必须改），PlayResX/PlayResY 跟当次成片画幅一致
# 原：Style: Default,Arial,16,&Hffffff,&Hffffff,&H0,&H0,...
# 改：Style: Default,WenQuanYi Zen Hei,54,&H00ffffff,&H00ffffff,&H00000000,&H80000000,...
# 用patch工具或sed修改ASS文件的第二行（Style行）
```

**ASS样式参数参考：**
| 参数 | 值 | 说明 |
|:----|:---|:-----|
| Fontname | `WenQuanYi Zen Hei` | 文泉驿正黑（Noto 作废），路径 `/usr/share/fonts/truetype/wqy/wqy-zenhei.ttc`（缺字体时 apt install fonts-wqy-zenhei） |
| Fontsize | 54px（横竖屏统一） | 54px（横竖屏统一）；PlayRes 必须和成片分辨率一致 |
| PrimaryColour | `&H00ffffff` | ABGR格式白色 |
| OutlineColour | `&H00000000` | 黑色描边；BorderStyle=1，禁止黑底/半透明背景条 |
| Outline | 2 | 描边宽度 |
| Shadow | 1 | 阴影宽度 |
| Alignment | 2 | 底部居中 |

**第三步：subtitles filter加载ASS文件**
```bash
subtitles=/tmp/xiyuan_subtitles.ass:fontsdir=/usr/share/fonts/truetype/wqy:charenc=UTF-8
```

**禁止的操作：**
- ❌ 种子在Seedance prompt里写「画面叠白色字幕」（AI生成字幕乱码）
- ❌ 用Arial/默认字体烧中文字幕（显示方框）
- ❌ 在ASS文件中用中文引号或emoji（libass渲染可能走形）
- ❌ 在prompt中使用任何引号（`「」`）— Seedance会渲染为字幕

### 核心步骤（完整流程）

1. **拼接视频** — concat demuxer 拼接所有镜
   ```bash
   echo "file '/path/to/镜1.mp4'" > /tmp/video_list.txt
   echo "file '/path/to/镜2.mp4'" >> /tmp/video_list.txt
   ffmpeg -f concat -safe 0 -i /tmp/video_list.txt -c copy concat_raw.mp4
   ```

2. **准备BGM** — 选一首统一曲目，截取35s+版，音量标准化
   ```bash
   ffmpeg -i bgm_source.mp3 -t <视频总时长+1> -c copy bgm_35s.mp3
   ```

3. **准备环境音** — 生成/下载户外氛围环境音（见上方环境音叠轨铁律）

4. **写SRT→转ASS→改字体**（见上方中文字幕铁律）

5. **三轨混合+字幕烧录**（见上方ffmpeg命令模板）
   - concat视频的原音频按 `VOICE_GAIN` 增益（人声层，照激励-06实存值），三轨混合后整片过 loudnorm=I=-14:TP=-1.5:LRA=11
   - BGM 0.25音量
   - 环境音 0.22音量
   - 字幕用ASS+fontsdir加载

6. **输出** — 画幅按用户当次要求（横版1280×720／竖版720×1280；用户没说时含双人段就整片横版1280×720，纯单人片出竖版720×1280），24fps，h264+aac 48kHz，+faststart

**自检清单（出片前逐项）：**
□ BGM全程统一（查一次各镜BGM是否同一曲目）
□ 中文字幕无方框（ASS中Fontname=WenQuanYi Zen Hei、54px、白字黑描边无黑底，非Arial）
□ 人声清晰（三条音频混音后听一遍人声是否被压）
□ 环境音存在（不是静音，能听到环境氛围）
□ 仅当 PROJECT_CHARTER 声明目标时长时才检查总时长（默认时长＝ceil(字数÷5.5)）
□ 🚨 物理兜底：ffprobe查音轨vs剧本匹配——剧本"无台词"但视频有audio track→不合格，打回重做

## 节点14：视频最终检验（自动）

**输出：** `节点14_质检报告.md`（终审依赖）

**工具：** ffprobe + ffmpeg黑帧检测 + Python脚本

输入：节点13成片

**自动检查项（全通过才进节点15，不通过回节点12/13重修）：**
- ffprobe：分辨率与用户当次要求的画幅一致（用户没说时：含双人段整片横版1280×720，纯单人片竖版720×1280）；24fps；响度 I=-14、TP=-1.5；仅当项目 `PROJECT_CHARTER` 声明目标总时长时才按其容差检查；h264+aac流；音频码率≥128k
- ffmpeg blackdetect: 无≥0.5s黑帧
- 文件大小≤50MB（抖音）/ ≤50MB 或 ≤10GB（小红书视频）；飞书交付时超过20MB先压缩
- 实念率（无BGM原段ASR回读）≥90%，低于90%不准交付、必须重出；>105%视为转写不可信，要人耳复核
- 成片合规复查：左下角风险提示小字按类型取⑩原文（免费类4句／种草·激励类5句）＋侧边竖排「累计签到后可提现」；话题标签 #火龙漫剧 #漫剧 #腾讯漫剧；LOGO 只在念到 CTA 时淡入、保持1.5秒后撤下，不常驻

## 🚨 API打包：两域架构（2026-07-12 本会话定稿）

**场景：** 用户问「怎么封装成api」「打包成接口」「搞个后端」。

**答案：** 视频工作流拆成两域——

| 域 | 内容 | 运行位置 |
|:---|:-----|:---------|
| **Bot域** | 节点0-5（信息采集→用户分析→爆款拆解→选题→文案→分镜） | 小鹿（Hermes）中用huoshan模板跑 |
| **API域** | 内部节点6-13（角色图→素材→提示词→合规→快乐马出片→ffmpeg→检验→交付） | Execute API `localhost:1889/execute` |

**⚠️ Bot域可以碰【搜爆款/写文案/做分析/生图/写剧本】，生图一律经 `hermes_task_dispatch.py` 调用（不直连ARK）。不能调Seedance/ffmpeg/火山直连（需API域）。**

**⚠️ API域不能自己启动——必须Bot输出剧本JSON → POST `/execute` 才触发。**

| 用户说「我想……」 | 对应谁干 | 调用方式 |
|:-----------------|:---------|:---------|

**⚠️ 如果用户说「封装成API」但紧接着又说「给客户直接调用」→ 不是纯API封装，是服务化部署。先走「前置需求澄清三问」（见上方部署意图三问）。**
