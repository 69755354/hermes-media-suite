# AI 执行器共识收敛（互评定稿 + 六顶帽子人审）

## When to Use

触发：用户说「让他们互相评价」「一致率90%就定稿」「你用六顶帽子评判」「把 A 的判断发给 B 看」。典型场景：Claude 和 codex 对方案/架构/质量方案有分歧，需要收敛成一份定稿（如分工规则、写作质量方案、软链可靠性方案）。已实测多次（2026-08-12/13），是「多执行器协作」的核心流程。

## 流程

```
① 原话打包互评：把 A 的判断发给 B 评、B 的判断发给 A 评（各问各的，锁串行）
② 收敛循环：A 终版 → B 评 → A 再评 → …直到一方明确说「一致率90%+可定稿」
③ 人做终审：Hermes 用六顶帽子评判定稿，给「通过 + N 个条件」，不照单全收
④ 落盘 + 可沉淀：定稿产物写文件，跨会话可复用的沉淀成 skill
```

## 关键规则

1. **必须原话转发，不加 Hermes 判断**——用户明确要求「不要加你的判断，按我的原话」。Hermes 只做打包转发，不夹带观点（夹带 = 污染互评独立性）
2. **90% 是定稿线**——让执行器自己报一致率（「一致率90%+可定稿」），到线才停；不到线列出剩余分歧点继续收敛（通常 2-3 轮收敛到）
3. **互评的价值是补盲区**——codex 评 Claude 发现「跨切面任务单侧端到端不成立」；Claude 评 codex 发现「不可 diff 时终审是空转」「人是第三个代理」。互评不是走形式，是真能暴露各自看不到的问题
4. **执行器共识 ≠ 正确**——定稿后 Hermes 用六顶帽子终审（⚪白帽事实 / 🔴红帽直觉 / 🟡黄帽价值 / 🟢绿帽替代 / ⚫黑帽风险 / 🎯裁决），给「通过+条件」结论（如「通过，3 个条件：①…②…③…」）
5. **锁串行**——Claude 和 codex 共用 flock 锁（防 OOM），互评任务排队执行，别并行发

## 六顶帽子终审模板（Hermes 用）

```
⚪ 白帽（事实）：实测数据/已验证的事实清单
🔴 红帽（直觉）：方向对不对的整体感觉
🟡 黄帽（价值）：方案最值钱的 3 点
🟢 绿帽（替代）：还能怎么做得更好（补充建议）
⚫ 黑帽（风险）：执行复杂度/未验证假设/会被绕过的点
🎯 裁决：通过 or 打回 + 条件清单
```

## 分工路由（2026-08-12/13 互评定稿的最终规则）

- **CC（Claude）**：架构约束/契约设计/对抗审查/终审；不作其所审实现的 owner
- **Codex**：仓库实现/事实审计/跑测试收敛；实现与验证同一 owner，不自行终审
- **DS（DeepSeek）**：主通道不可用时的容灾降级（产物打 DS_DEGRADED 标记）
- **Hermes**：调度/质检/交付；不改代码、不替人批准门禁
- **人**：唯一持久记忆与唯一不可逆授权主体

路由判据：按「可逆性 × 事实不确定度」路由（项目大小次之）——事实不确定度高先审计再设计；不可逆/不可 diff 事前授权+恢复演练，不靠终审；可逆且事实清楚单主代理端到端 + 一次异构复核。分工写入 AGENTS.md 角色分工节。

## 踩坑

- **别替执行器做判断**：用户要的是「它们互评」，Hermes 夹带自己观点会毁掉独立性——原话转发是硬要求
- **session jsonl 缓存干扰**：Claude 回答容易复用旧 session 内容（读到的还是门禁 P0 旧报告）——检查输出是否与本次问题匹配，不匹配要从 /tmp 日志 tail 提取真实回答
- **互评会互相推翻**：codex 评 Claude 时可能「同意七成」、Claude 评 codex 时「同意前提不同意定型规则」——分歧是正常的，收敛循环就是消化这些分歧
- **一致率是执行器自报**：没有客观度量，但「明确说可定稿」已是够用的停止条件；人对终稿的六顶帽子才是最终防线

## 🚨 架构三审合一 + 失败测试先行（2026-08-16 客户运营平台案例，血泪固化）

**教训源：** 平台架构 v1.0（Claude 593 行）表面完整，被老板一个 403/404 问题戳穿——「把接口签名当能力、凡沿用存量处都没实测」：approve 可无条件放行授权链、红线门只扫第一个文件（return 缩进在循环体内）、客户一句「直接来吧」触发 skip_mode 全放行、引用的两个门禁脚本根本不存在。**第一版按原样实现必然返工 + 合规事故。**

**正确的架构评审流程（写死）：**
```
① 三审合一：Claude 自审（架构 owner 自我批判）+ codex 评审（实现视角挑毛病）
   + codex 补漏扫描（运营/商业/信任层）→ Hermes 合并成总清单（P0/P1/P2 分级）
② 老板发现单点问题（如 403/404）→ 扩展成「一类语义」系统性检查，不只改一处
③ 实测核验：对执行器声称「已实测」的每一条，Hermes 亲自跑命令验证——不信自证
④ 失败测试先行：写 P0-A 失败测试组（13 条，全部应为红）——红 = 契约冻结验收物，
   不是 bug；测试必须真实验证存量代码行为，不许 mock 被测对象（mocking = 自欺）
⑤ 契约冻结：一项目一 piece、D_* 目录、行业 schema、DDL、API 状态码判据
   （404 防枚举 vs 403 权限、列表 200+空数组 vs 详情 404）
⑥ 实现：按冻结契约写页面闭环
```

**执行器分工硬约束：** 架构文档引用存量能力必须带「已实测/待实测」标注表（M1-M16 实测 / U1-U9 待实测，每条附命令+输出）；每条 CR 带 owner+批准人+终审人+不批时降级路径；终审另派（实现者不自行终审）。

**状态码语义铁律（老板 08-16 拍板）：** 客户侧「资源存在但不给看/已删除/不存在/越权」一律 404（防枚举，不泄露存在性）；只有「身份合法但本次动作违反策略」才 403。列表无可见项返回 200+空数组，详情不可见返回 404。
