# 禁止盲改协议（2026-10-10 用户拍板入规）

来源：用户发来的调试方法论（AI 修 bug 越修越多，根因是提示习惯——直接命令「把这个错修了」）。
**触发场景**：任何「AI 修 bug / 报错 / 故障排查」的任务。

## 硬性流程（顺序不可换）

1. **先不改一行代码**。第一阶段只读：追完整调用链，找到**最初的出错点**。
2. **三层分离**，逐层写清、各附证据（文件行号 / SQL / 日志片段）：
   - 表象 = 用户看到的现象
   - 直接诱因 = 触发报错的那一步
   - 根因 = 谁该做而没做的那一步（不猜，读代码坐实）
3. **给 2–3 个修复方案，每个都带副作用**，标明哪个断根、哪个兜底、哪个是事后补。
4. **用户选定之后才允许改代码**。

## 为什么（血泪依据）

- 只治「不崩」的降级补丁（try/except、return None、跳过校验）会让故障换一层再冒出来，客户侧表现仍是「挂了」——看似修好，实际没修。
- 反复盲改会引入新 bug，且掩盖根因，后续排查成本翻倍。

## 反例（本项目真实教训）

会话代际漂移致网关失联：先被改成 `raise → log+return None`（降级），错误立刻换一层暴露为 `context conversation unavailable`。
正确做法是当时就停下来追调用链、定位「滚动流程漏更新了哪一处」，而不是连打两个降级补丁。

## 与既有规则的关系

- 与 `systematic-debugging`（4 阶段根因调试）一致：本协议是其「AI 协作版」执行细则。
- 与「禁 AI 自批」「实现与终审独立」同源：改动前必须有人类选择方案的环节。
