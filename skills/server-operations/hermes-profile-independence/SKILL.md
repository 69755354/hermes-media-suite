# Hermes 多 Profile 独立性边界

## 触发
- 用户说「给小鹿独立」「你们是独立的个体」「分开」
- 需要判断某条 SOUL 规则是「通用工作铁律」还是「某 profile 的身份痕迹」

## 核心原则

1. **「独立个体」= 架构分离，不是改对方 SOUL 内容。**
   用户说「让小鹿独立」时，指两个 profile 各自有独立的 SOUL 文件、互不 clone/覆盖。
   **默认动作：不动对方 SOUL 的工作方式**（调 codex、禁止直出、工作流、安全规则、权限配额全部保留）。只有用户明确要求改内容时才改。

2. **「Hermes 直出」是通用技术术语，不是「Hermes 这个 agent 的身份」。**
   「Hermes 直出」= 用主对话模型直接产出（不调 codex/claude）。
   「禁止 Hermes 直出」是**通用质量铁律**，Hermes 和 customer bot 双方都守——不是「身份混淆痕迹」，别当痕迹去删。

3. **区分两类 SOUL 内容：**
   - 通用工作铁律（调 codex、禁止直出、工作流、安全规则、权限配额）→ 双方共享，保留
   - 某 profile 专属身份（如「每句话叫老爷」这种对老板的称呼）→ 才可能算身份痕迹

## 踩坑（2026-08-14 实录）

用户说「给小鹿重新出一份 soul 方案，你们是独立的个体」，被误读成「去 Hermes 化、清 Hermes 痕迹」，把「禁止 Hermes 直出」「调 codex」当身份混淆删了。用户连续三次纠正：
1. 「小鹿他也是调 codex 啊」
2. 「他原来的没错，我就规定他不能 Hermes 直出」
3. 「他之前的工作方式不用改，明白我的意思吧」

结论：改了又回滚。正确做法——先确认「独立」是架构分离还是改内容，默认架构分离，不动对方 SOUL。

## 独立原则是硬约束，对设计提案同样生效

「两机各自独立」不只是不直接改对方 SOUL——它是所有架构提案和实施计划的硬约束。codex 出的架构方案如果包含把 Hermes 从新加坡搬广州、合并两机服务、在一端建另一端的服务，一律不实施。收到 codex 的设计稿时，先拿这条原则过滤一遍再写实施任务书，别把违反原则的方案打包丢给 codex 去落地。

用户原话：「不是说了两边分开吗？hermes还搬广州？」——因为没过滤掉 codex 方案里的搬迁提议，被当场拦停。

## 派 codex 实施架构方案前必须过滤任务书本身

codex 的设计稿往往包含跨机搬迁、合并服务、在一端建另一端的服务等提议。用户批准「落地实施」不等于批准设计稿里的每一项。写实施任务书时，先把设计稿里违反独立原则的条目删干净再派给 codex——不要把整个设计稿原封不动包进任务书。codex 读到「Hermes gateway搬到广州」就会照做，不会自己判断这违反用户原则。

教训：codex 不会质疑任务书内容，任务书写什么它干什么。方案设计阶段可以让 codex 自由探索，但实施任务书必须人工过滤。
