# 服务入口可否下线：零调用验证法（2026-08-23 execute_api P0-1 实测）

判定「一个自带完整功能的 HTTP 入口能否直接封死/下线」前，必须收集四路证据确认零调用，再决定方向——不要凭「感觉没人用」就下线。

## 四路证据

1. **持久化任务目录全空**：`ls /tmp/execute_api/jobs/`——22 个 job 目录全部无 state.json = 入口从未成功跑通过（或从未被用）
2. **审计日志无该入口记录**：`grep -cE "entry=execute|entry=job|entry=seedance_exact" ~/.hermes/guard/gate_chain_audit.log` 返回 0 = 闸链从未见过它
3. **无活跃连接**：`ss -tnp | grep <端口>` 空 = 没有客户端在连
4. **生产实际走另一入口**：确认当前生产链路走别的端口/入口（如 helper-api 1888 helper_seedance），被审入口是旁路

## 判定

- 四路全零 → 可安全封死（返回 blocked 提示走标准工作流）；**内部自带创作/生成流水线的入口必须封**（零调用 + 有绕过风险 = 封死零代价）
- 有任一路非零 → 先加过渡闸，不直接下线

## 同源教训：让用户跑 root 终端命令后必须贴回输出验证

本会话用户跑 `hermes gateway restart`（重启服务）误当清空命令，文件根本没改，`cat` 验证才发现。

改 root 属主文件（如 `/etc/hermes/render_authorized.list`）时 AI 无 sudo 权限只能用户终端执行，流程必须是：
1. 给命令
2. 用户执行
3. **要求贴回 `cat` 输出**
4. 比对内容/时间戳确认生效
5. 才继续下一步

不信「好了」——用户可能跑错命令、跑错机器（Termux 连广州 vs 新加坡）、或压根没跑。验证永远看文件本体，不看用户口头确认。
