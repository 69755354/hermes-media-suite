# 双执行器交叉互评 + 多执行器分工定稿（2026-08-12 定案）

> 背景：天行者问「cc 做架构 + codex 写代码的组合是最好的吗」「把两个 AI 的判断互相发给对方去判断」「判断依据是什么」「cc/codex 都挂了用 DS 替代怎么弄」。完整流程与结论沉淀于此。

## 双执行器交叉互评流程（老板的提问方式）

老板问「cc 和 codex 哪个方案对」这类判断题时，标准流程：

1. **用户原话原样打包**分别问 Claude 一次、codex 一次——**不加 Hermes 判断/翻译/润色/倾向**（用户明确要求「不要加你的判断，按照我的原话」）
2. **互评**：拿双方回答 → 分别打包给对方评：「这是对方的判断，你同意哪些/不同意哪些/补充什么」（不要客套，直接给结论）
3. **追问依据**：「你的判断依据是什么？哪些是实测/推演/假设？去掉依据方案还成立吗？」（依据分级：A 行业标准 / B 逻辑推演 / C 仓库事实 / D 拍脑袋——与 workflow-architecture 依据审计一致）
4. **原话汇总**给用户，标清哪边说的，不夹带 Hermes 倾向

### 踩坑
- 打包必须用**用户原话**——Hermes 一旦「翻译/总结/加倾向」就破坏互评独立性
- 两个任务共 flock 锁会**串行排队**，别误判为卡死——`ps aux | grep claude` 看到 CPU>0 就是真在跑
- Claude 可能**复用 session 缓存旧报告**（如把门禁 P0 旧报告当本次回答）——tail 有真正回答时以新输出为准，缓存内容跳过
- wrapper 日志 tee 只留 tail 会丢结论——完整输出从 `~/.claude/projects/*.jsonl` 提取（逐行 json.loads，assistant 消息 text 拼接）

## 互评收敛到一致率 ≥90% 才定稿（2026-08-13 天行者定案，写作方案定稿实测）

老板要求方案定稿时，不是「互评一轮就定」，而是**循环收敛到一致率阈值**：

1. A 给终版方案 → 发给 B 评（「你同意哪些/不同意哪些/剩余分歧点」）
2. B 回应 → **B 的回应原样发回 A 再评**（「Claude 补了 3 点+新第0步，你评判对不对/要不要改/还一致吗」）
3. 循环直到**一方明确说「一致率 90%+，可定稿」**（或列出剩余分歧点）
4. 定稿后 Hermes 用**六顶帽子法评判**（白帽事实/红帽直觉/黄帽价值/绿帽创意/黑帽风险/主席裁决）——给「通过 + N 个条件」的结论，不空夸
5. 定稿文件落盘 `outputs/<项目>_方案最终定稿_<日期>.md`

### 一致率评估写法
- 收敛方要**给数字**：「双方一致率 92%，可定稿」——不模糊说「基本一致」
- 修正点显式列出：「修正 2 点：①…②…；无剩余阻断分歧」
- 双方有分歧时**继续循环**，不许一方说定稿就定

### 六顶帽子评判模板（Hermes 用）
```
白帽(事实): 实测数据/文件证据
红帽(直觉): 这方案让人放心还是发怵
黄帽(价值): 最值钱的 N 点
绿帽(创意): 可补充的替代做法 N 条
黑帽(风险): 会翻车的地方 N 条（含执行成本/流于形式风险）
主席裁决: 通过 + 前置条件
```

### 实战案例（三层衣长篇写作质量方案）
codex 终版 → Claude 评（补 3 点+新第0步：git 救资产/刘奕王奕范围/错例表）→ codex 再评（修正 Claude 2 处诊断：通知书冲突定位 /tmp 清理解读）→ **一致率 92% 定稿** → 六顶帽子通过 + 3 条件 → 沉淀为 `long-form-writing-quality` skill（user-owned，需 adopt 后才能 curator 改）

## 分工定稿（Claude 吸收全部讨论后给出，codex 共识）

**核心结论：不是固定最优。路由轴 = 可逆性 × 事实不确定度（不是项目大小）。**

### 路由规则
- **事实不确定度高** → 先由能执行的一侧做仓库事实审计，此前任何方案都算草稿
- **不可逆/不可 diff** → 事前授权 + 恢复演练，不靠终审（skills 树在 Git 外，删了没法比对 = 事后 review 空转）
- **可逆且事实清楚** → 单主代理端到端 + 一次异构复核
- 每个任务**恒定单一 owner**；复核独立性靠**输入不同源**（不靠角色名）

### 五方角色边界
| 角色 | 职责 | 备注 |
|:--|:--|:--|
| CC（Claude） | 架构约束/契约设计/对抗审查/终审 | 攻击路径构造（找绕过）是核心贡献，DS 替代不了 |
| codex | 实现/审计/跑测试/收敛 | 优势是直接读真实仓库、修改、跑测试、失败收敛 |
| DS | 容灾降级（见 ds-fallback-plan.md） | **能验证，不能发现** |
| Hermes | 调度/质检/交付 | 打包/落盘/汇报 |
| **人** | **唯一持久记忆 + 唯一不可逆操作授权方** | 两个 AI 规则里都容易漏掉人 |

### 什么时候换配置（Claude 版）
- 大批量机械改动/长文件编辑/成本敏感 → cc 定约束 + codex 实现划算，继续用
- 跨切面语义/状态机/门禁类设计/不可逆操作 → **单侧端到端做，别分工**（交接损耗最大）
- 已经出现回归 → 不是换模型，是**补契约测试**（codex 反驳：按缺陷分类——契约缺失补测试；上下文丢失/理解不足则调 owner/模型，假二选一）

### 容灾（cc/codex 挂 → DS 顶班）
- cc 挂 → DS 顶 cc 位（pro 档）
- codex 挂 → **让 CC 端到端做完**（不是 DS 顶 codex！codex 壳降级只能 flash 比 pro 弱一档）
- 都挂 → DS 顶全部：内容生产几乎无损（本来就跑 DS）/ 写代码降级（分支+单文件+测试兜底）/ **架构审查冻结排队不降级**
- 硬红线：门禁状态机/skills 树删除/主干 push/数据迁移/安全边界/客户方案定稿——禁止降级

### 诚实标注（§7）
- 「CC 更会审查、Codex 更会实现」仍是**工作假设**（无对照组数据）
- DS 顶 cc 位只有一个样本且是已知答案复现
- v11/v12/v13 案例只支持「单模型自产自评会漂移」，**不支持「CC 普遍优于 Codex」**
- codex 建议：选真实任务对比 A/B 流程（CC→Codex 固定流水线 vs Codex 端到端→CC 复核），记录墙钟/消耗/返工/通过率/逃逸缺陷，**用数据定最终默认**
